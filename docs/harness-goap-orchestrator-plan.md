# План: харнесс как GOAP-оркестратор (Laya + albedo + tools/MCP)

## Контекст и цель

`apps/alpha-orchestrator` сейчас — тонкий проксирующий слой: `POST /v1/messages` напрямую зовёт
`agent.handleMessageStream` (единственная модель, `albedo`/Vikhr-Llama-3.2-1B), `POST /v1/decisions`
напрямую зовёт `decisionAgent.decide` (Laya). Оркестрации между ними нет — выбор, что вызывать,
делает вызывающая сторона (клиент), а не харнесс.

Цель: харнесс сам решает, что делать с входящим промптом — вызвать Laya (typed decision), albedo
(генерация текста), внешний tool/MCP, или комбинацию — и делает это через настоящий GOAP-планировщик
(в духе F.E.A.R.), а не через LLM, которая на каждом шаге импровизирует роутинг. Плюс: модуль
tools/MCP должен быть спроектирован достаточно общо, чтобы позже (отдельным планом) в него
подключился WebMCP-источник тулов с сайтов через будущее browser-extension (см. память
`laya-webmcp-extension-plan` — референс `sdras/jev-webmcp-extension`, `src/jev.js`, конвертация
WebMCP tool-схемы → typed Laya-вопросы).

Домены первого использования: интернет-магазины, поиск билетов — то есть сессии с настоящими
составными целями (найти → показать → подтвердить → купить), не одноразовые Q&A.

## Ограничения по железу — не опция, а жёсткий бюджет

Целевая/dev-машина: AMD Ryzen 5 5600H (6 ядер/12 потоков), встроенная Vega (без CUDA/ROCm — реального
ускорения инференса нет, всё CPU-only, как уже и есть у `albedo`/Laya), 32GB RAM, но реальный headroom
меньше — ~11GB уже занято в простое системой и окружением. Это распространяет уже существующий вывод
из IronClaw-урока (CLAUDE.md: "для маленькой self-hosted модели нужен минимальный, полностью
подконтрольный промпт") на весь стек оркестратора, а не только на промпт: **каждая модель в цепочке —
маленькая и CPU-only, без исключений**, и сам оркестратор не должен добавлять накладных расходов, которые
на этом железе заметны (лишние аллокации, ненужные копии текста, синхронные блокировки event loop).

Нефункциональные требования, которые из этого следуют и становятся частью дизайна planner'а, а не
довеском:

- **Blazing**: низкая latency на путь "сообщение → ответ", особенно там, где Laya может закрыть вопрос
  без обращения к albedo.
- **Низкое потребление ресурсов**: не держать несколько параллельных генераций на albedo одновременно
  (llama-server на 6 ядрах при параллельных запросах деградирует резко, не линейно) — конкурентность
  ограничивать целенаправленно, а не полагаться на то, что ОС/рантайм сами разрулят.
- **Устойчивость к нагрузке**: система должна деградировать предсказуемо (очередь/backpressure/явный
  отказ) при превышении пропускной способности CPU, а не пытаться исполнить всё параллельно и упасть
  в своп.

## Почему буквальный GOAP, а не агентный роутинг

Классический GOAP (F.E.A.R.): world state — набор фактов, actions — precondition/effect/cost,
goal — целевое подмножество фактов, planner ищет план (обычно regressive-поиск от цели назад,
не полный forward A* по всему state-space — так дешевле). Здесь это ложится естественно, потому что:

- Составные многошаговые цели реально есть (не просто "ответить одним сообщением").
- Laya — готовый дешёвый typed-classifier — идеально подходит на роль "сенсора", который
  переводит нечёткий текст/голос пользователя в факты world-state (`intent`, `needsClarification`,
  `confidence`, ...), а не на роль генератора текста.
- albedo/Vikhr и внешние tools — explicit actions с известными effects, а не что-то, что LLM
  выбирает "на глаз" каждый раз заново.
- Модуль tools/MCP подключается в ту же abstraction (action), без отдельного слоя "агентных решений".

Отличие от игрового GOAP: там world state — ground truth (игра сама его знает). Здесь часть фактов —
вероятностные оценки (LLM/Laya classification), поэтому нужен replanning-цикл после каждого action,
а не одноразовое построение плана.

## Архитектура

### World state

```ts
type WorldState = Record<string, boolean | number | string | undefined>;
```

Простой key-value bag фактов, не строгая схема — actions сами документируют, какие ключи читают/пишут.
Живёт per-thread. Сейчас `ThreadHistory` в `@repo/core` — in-memory, персистентности нет (см.
CLAUDE.md: turingdb — запланированный, но ещё не подключённый бэкенд для истории). GOAP world state
логично хранить рядом/тем же способом — открытый вопрос ниже.

### Actions

```ts
interface GoapAction {
	name: string;
	cost: number;
	preconditions: Partial<WorldState>;
	effects: Partial<WorldState>; // ожидаемые — то, что action ДОЛЖЕН произвести
	execute(ctx: ActionContext): Promise<Partial<WorldState>>; // фактические — могут отличаться (ошибка tool'а, отказ модели и т.д.)
}
```

**`cost` — это реальная ресурсная стоимость, не абстрактное число.** На ограниченном CPU-only железе
(см. секцию выше) planner, предпочитающий дешёвые планы, должен на практике означать "предпочитает
Laya-классификацию генерации через albedo, а кэш/no-op — обоим". Практически: `cost` калибруется по
измеренной latency/CPU-time каждого типа action на целевом железе (Laya-decision — самый дешёвый порядок
величины, albedo-generation — на порядки дороже, MCP-tool — где-то между, в зависимости от tool'а).
Это одновременно решает и "какой action выбрать", и "как оптимизировать под blazing + низкое
потребление ресурсов" — одной и той же механикой, без отдельного слоя оптимизации поверх planner'а.

Это единственная точка расширения. Три источника actions на старте:

1. **Laya-actions** — обёртки над существующим `DecisionAgent.decide` (`packages/core/src/decision-agent.ts`,
   не меняется). Каждая заводится как action вида `classifyIntent`, `checkAmbiguous` и т.п., effect —
   запись типизированного факта в world state. Дешёвые, идут первыми в большинстве планов
   (perception/state-estimation, не генерация).
2. **albedo-action(s)** — обёртки над существующим `Agent.handleMessage`/`handleMessageStream`
   (не меняется). Actions вида `generateReply`, `extractToolArgs`, `summarizeResults` — всё, что требует
   свободной генерации текста.
3. **Tool actions (MCP)** — `ToolSource` интерфейс:

   ```ts
   interface ToolSource {
   	listActions(): Promise<GoapAction[]>;
   }
   ```

   Первая реализация — стандартный MCP client (`@modelcontextprotocol/sdk`) поверх `tools/list`/`tools/call`,
   каждый MCP tool механически становится `GoapAction` (effects по умолчанию — `{ [toolResult:<name>]: true }`,
   если сервер не даёт более точной семантики). Именно эта абстракция — то место, куда позже (отдельным
   планом, после browser extension) встанет `WebMCPToolSource`: страница отдаёт WebMCP tool-схему, она
   конвертируется в Laya `choice`/`score`/`noul` вопросы для *выбора* тула (как в `jev-webmcp-extension`'s
   `src/jev.js`), а сам вызов исполняет extension на странице. Planner не должен знать, откуда action —
   MCP stdio-сервер или страница в браузере.

### Planner

Regressive (backward-chaining) поиск от goal к текущему state, а не forward-поиск по всему
пространству состояний — так делает сам F.E.A.R., и на небольшом наборе actions (сейчас предполагается
до ~15-20) этого достаточно, полноценный A* по forward state-space не нужен.

```ts
function plan(state: WorldState, goal: Partial<WorldState>, actions: GoapAction[]): GoapAction[] | undefined
```

Чистая функция, без I/O — легко тестировать unit-тестами (test-first).

### Replanning-цикл

```
plan = planner.plan(state, goal, actions)
for action in plan:
  observedEffects = await action.execute(ctx)
  state = { ...state, ...observedEffects }
  if state больше не удовлетворяет preconditions оставшейся части плана:
    replan from current state
```

Нужен, потому что: (а) Laya-факты вероятностные, а не точные, (б) tool call может упасть/вернуть не то,
(в) новое сообщение пользователя посреди диалога может поменять goal.

## Где живёт код

Транспорт-агностичная логика (world state, actions, planner, `ToolSource`) — новый модуль
`packages/core/src/goap/` (по аналогии с тем, что `packages/core` уже владеет `Agent`/`DecisionAgent`
портами и не содержит HTTP-специфики). `apps/alpha-orchestrator` собирает конкретные `ToolSource`'ы (Laya-actions,
albedo-actions, MCP tool source) и дергает planner вместо/поверх прямого вызова
`agent.handleMessageStream` в `server.ts`.

## Фазы реализации (test-first, по одному PR-размеру на фазу)

1. ✅ **Ядро planner'а** (2026-09-23): типы `WorldState`/`GoapAction`/`Goal`/`ActionContext` +
   чистая `plan()` (regressive/uniform-cost search) в `packages/core/src/goap/{types,plan}.ts`.
   9 юнит-тестов на искусственных action-графах (пустая/уже достигнутая цель, прямое действие,
   правильный порядок цепочки, выбор дешёвого действия и дешёвой цепочки над дорогим прямым,
   недостижимая цель → `undefined`, защита от циклов), без реального Laya/albedo/MCP.
2. ✅ **Executor с replanning-циклом** (2026-09-23): `runPlan({state, goal, actions, ctx, maxReplans})`
   в `packages/core/src/goap/executor.ts` — исполняет план, проверяет preconditions перед каждым
   action'ом, после прогона сверяет достигнута ли цель; если нет — перепланирует с текущего state,
   с ограничением `maxReplans` (default 10). 6 тестов на моках `execute()`: успех в один шаг,
   успешная цепочка, недостижимость сразу, **успешное восстановление через replan** (дешёвый action
   на деле не делает то, что заявляет, дорогой fallback подхватывает), replan упирается в
   недостижимость, `maxReplans` останавливает вечный "flaky"-action.
3. ✅ **Адаптеры существующих портов в actions** (2026-09-23): `createDecisionAction`
   (`packages/core/src/goap/decision-action.ts`) оборачивает `DecisionAgent.decide` в Laya-action —
   один config = один фиксированный typed-вопрос, ключуется именем action'а в `decide()`, `toEffects`
   мапит реальный `DecisionAnswer` в факты world state. `createTextAction`
   (`packages/core/src/goap/text-action.ts`) оборачивает `Agent.handleMessageStream` в albedo-action —
   вычитывает `delta`-события в один текст, `toEffects` мапит его в факты. Оба порта (`DecisionAgent`,
   `Agent`) не изменены, только обёртка. По пути расширен `ActionContext` (был плейсхолдер) —
   разделён на `BaseContext` (что передаёт вызывающая сторона в `runPlan`, без state) и `ActionContext`
   (что реально получает `execute()` — `BaseContext` + живой `state` на момент именно этого action'а,
   инжектится executor'ом на каждом шаге, а не один раз на весь прогон) — понадобилось, чтобы адаптеры
   могли читать `state.userMessage` и т.п. 14 новых тестов (5 decision-action + 3 text-action + сборка).
   Важный design-момент: `effects` в конфиге — это план-тайм обещание (что нужно planner'у для
   regression-поиска), а не то, что реально произойдёт — для вероятностных Laya-ответов (`choice`
   может выбрать любой из criteria) это разруливается не спецсимволами в `plan()`, а уже готовым
   replanning-циклом из Фазы 2: если реальный ответ разошёлся с обещанным `effects`, следующая
   итерация просто перепланирует с фактическим state.
4. ✅ **Минимальный `ToolSource` поверх MCP** (2026-09-23): `packages/core/src/goap/tool-source.ts` —
   `createMcpToolSource({client, costFor?})` механически превращает каждый tool из `tools/list` в

   Узкий порт `McpClient` (не сырой тип из SDK) — тот же паттерн, что `DecisionAgent`/`Agent`, тестируем

   Реальное подключение к MCP-серверу подтверждено отдельным тестом
   (`tool-source.mcp.test.ts`) — настоящий `McpServer` из `@modelcontextprotocol/server`, связанный с

   `/v1/messages` напрямую, отдельного `/v1/orchestrate` нет. Каталог action'ов пока из одного
   `generateReply` (`createTextAction` вокруг существующего `deps.agent`, `effects: {replied:true}`),
   собирается один раз на инстанс приложения в `buildActions(deps)`, не на каждый запрос. Хендлер
   строит начальный `WorldState` (`{userMessage: normalizeText.apply(body.text), threadId, userId}`)
   и гоняет `runPlan({state, goal: {replied:true}, actions, ctx})` вместо прямого
   `agent.handleMessageStream`.

   По пути пришлось закрыть реальную деградацию, а не просто "провести": `runPlan()` возвращает один
   `Promise`, а `createTextAction` (Фаза 3) уже вычитывал стрим целиком до возврата — в лоб это значило
   бы потерять live-токены (важное для "blazing") и данные о токенах, которые `apps/cli`'s usage-строка
   читает из `done`-события. Решено без искажения GOAP-модели: (а) `StreamingContext.onDelta` —
   опциональное расширение `BaseContext`, `createTextAction` зовёт его на каждый `delta` по мере
   стриминга — единственный способ остаться "blazing" сквозь planner, раз `execute()` — не стрим; (б)
   `elapsedMs`/`inputTokens`/`outputTokens` из agent'ского `done`-события едут через обычный механизм
   `toEffects` как world-state факты, а сервер после `runPlan()` читает их обратно из `finalState` —
   никакого отдельного side-channel для этого не понадобилось, ровно та же модель "effects как факты".
   Итоговый NDJSON-контракт: `delta` стримится живьём как раньше, `done` несёт те же поля, что и до
   planner'а (обратная совместимость для `apps/cli`/`apps/telegram-bot`), `progress`-событий больше нет
   (были специфичны для старого multi-chunk ingest-пайплайна, не имеют аналога в текущем минимальном
   каталоге), `error` — и при throw внутри action'а, и при `!result.succeeded` (недостижимая цель).
   26/26 тестов харнесса + 46/46 core — все зелёные, Docker-сборка подтверждена вручную.

**Все 5 фаз из исходного плана выполнены.** Дальше — не запланированные явно фазы, а расширение

## Guardrails

Нагрузка на общий CPU и появление tool/WebMCP-actions с реальными побочными эффектами (покупка,
отправка данных на сайт) требуют защиты на нескольких уровнях — это часть дизайна planner'а/executor'а,
а не отдельная фича поверх:

1. **Защита от runaway-планирования.** Жёсткий предел на длину плана и на число replanning-итераций за
   один запрос (например, N=10) — без него зацикленные/противоречивые effects/preconditions могут
   вогнать executor в бесконечный replanning-цикл и съесть весь CPU одним запросом. Плюс per-action
   timeout — переиспользуем существующий `withTimeout` из `packages/core/src/timeout.ts`, оборачивая
   каждый `execute()`, а не только LLM-вызовы как сейчас.
2. **Concurrency limit на уровне харнесса — admission control с явными состояниями, не бесконечная
   очередь и не тихий обрыв.** На 6 ядрах параллельные генерации через albedo деградируют резко (не
   линейно) — нужен явный семафор/пул на `apps/alpha-orchestrator` (нового кода, `server.ts` сейчас его не имеет:
   ни семафора, ни таймаута на сам LLM-вызов — `withTimeout` из `packages/core/src/timeout.ts`
   существует, но нигде не применяется в `agent.ts`). Гейт стоит не на весь `/v1/messages`, а конкретно
   на момент, когда исполнение плана доходит до **albedo-generation action** — Laya-only actions
   (и весь `/v1/decisions`) под этот лимит не попадают вообще, даже если albedo перегружен (тот же
   cost-first принцип, что и в выборе action'ов, применённый к admission control). Три состояния:
   - свободный слот → выполняется сразу;
   - слоты заняты, но буфер очереди не переполнен → запрос принят, в NDJSON-стрим сразу уходит новое
     событие `queued` (позиция/оценка ожидания) — не тишина, ограниченное по буферу ожидание;
   - буфер очереди тоже полон → немедленный явный отказ (`503` + `Retry-After`), никогда не "принять
     соединение и молча уронить позже".
   Ни один локальный лимит не делает 6 ядер способными обслужить тысячи одновременных generation-запросов
   с приемлемой latency — это физический потолок железа; если такой трафик реален, это вопрос
   горизонтального масштабирования (несколько albedo-реплик), не тюнинга одного хоста. Отдельная,
   пока не спроектированная задача: `telegram-bot`/`cli`/будущее extension должны переводить `queued`/503
   в понятное пользователю сообщение, а не проглатывать молча.
3. **Rate/concurrency per-thread.** Существующий Bearer-auth + `ALLOWED_TELEGRAM_USER_IDS` whitelist
   (в `apps/telegram-bot`) ограничивает, кто вообще может достучаться, но не защищает от одного шумного
   треда, забирающего весь CPU у остальных — нужен лимит параллельных/за-период запросов на
   `threadId`/`userId` внутри `apps/alpha-orchestrator`.
4. **Tool/page-контент — данные, не инструкции.** Результат MCP tool'а и (позже) содержимое веб-страницы
   через WebMCP — untrusted data. Он не должен попадать в системную/инструктивную часть промпта для
   albedo без явной маркировки границы (как в этой самой сессии tool-результаты помечены как данные, а
   не команды) — иначе сайт с prompt-injection в описании товара может переписать поведение агента.
5. **Явное подтверждение для необратимых actions.** Actions с реальными побочными эффектами (например
   `confirmPurchase`) обязаны требовать precondition-факт (`userConfirmed: true`), который выставляется
   только отдельным confirmation-шагом — Laya `noul`-вопросом с порогом уверенности по явному
   да/нет-ответу пользователя, а не побочным эффектом обычного generate-action или домысливанием из
   контекста.
6. **Eviction по числу тредов, не только по сообщениям внутри треда.** Текущий `ThreadHistory`
   (`packages/core/src/history.ts`) — `Map<string, ModelMessage[]>` без TTL/лимита на количество разных
   `threadId`, только на длину истории внутри одного треда. Много разных пользователей/тредов за время
   жизни процесса = карта растёт неограниченно, память не освобождается — это нужно чинить (TTL или
   LRU по числу тредов) независимо от concurrency-guardrails выше, и относится и к будущему world-state
   хранилищу (та же структура, тот же риск).

## Промпт-бюджет для generation-actions (почему это не Smolagents/ReAct)

Smolagents и классический ReAct-агент устроены так, что LLM на каждом шаге сама выбирает, какой tool
вызвать — значит ей нужно видеть описания всех доступных tools в промпте каждый раз (Smolagents снижает
вес за счёт компактного code-as-action формата вместо verbose JSON tool-calling, но директорию tools всё
равно показывает). У нас **planner выбирает action символьно, до вызова albedo** — LLM никогда не должна
видеть "вот весь список tools, выбери сам". Это структурно устраняет главный источник раздутых промптов
(тот самый, что сделал IronClaw неюзабельным на 1B-модели — см. CLAUDE.md). Правила для авторов
generation-actions (обязательны, не рекомендация):

1. **Однотул-scoped промпт.** Раз planner уже выбрал конкретный action/tool, generation-action (например
   `extractPurchaseArgs`) получает в промпт схему только этого одного tool'а — никогда весь реестр.
2. **Урезанная схема, не полный JSON Schema.** Модели для генерации аргументов нужны имя + короткое
   описание + имена полей; типы/constraints проверяет валидатор (zod) после генерации, не промпт.
3. **World state — единственный источник контекста.** Никакого raw history/tool-output replay целиком —
   каждый action явно перечисляет, какие конкретно facts из world state ему нужны для шаблона.
4. **Хард-кап длины любого текста до попадания в world state.** Переиспользуем `chunkText`/`normalizeText`
   (`apps/alpha-orchestrator`), применяя их и к MCP/tool-результатам, а не только к вводу пользователя.
5. **Явный token-budget на каждый generation-action**, задокументированный при регистрации — аналог
   того, как `apps/cli` уже отслеживает `LLM_CONTEXT_SIZE` в usage-строке.

Плата за это — больше дисциплины при написании каждого action (нужно явно решить, что именно ему нужно),
против общего цикла, где модель "сама разбирается" из полного контекста. На CPU-only железе с ограниченным
контекстом эта расточительность и есть то, что один раз уже всё сломало.

## Длинный ввод с множеством критериев (например, поиск товара) — структурная экстракция, не prose-дайджест

Сейчас в `packages/core/src/agent.ts` уже есть map-reduce для длинных сообщений: каждый чанк, кроме
последнего, сжимается дешёвым "ingest"-проходом (`INGEST_SYSTEM_PROMPT`, лимит `maxIngestTokens=96`,
"1-2 предложения фактов") в прозовый дайджест, дайджесты конкатенируются и попадают в финальную генерацию
вместе с последним чанком. Это нормально для обычного чата (character-reply через `Agent.handleMessageStream`,
не трогаем), но **лоссово для доменов с множеством конкретных критериев** (поиск товара/билетов): сжатие
до 1-2 предложений на 96 токенов легко теряет точные значения (цена, бренд, размер, модель), а следующий
чанк-дайджест уже не видит и не может их восстановить — это и есть проблема, о которой был вопрос.

Решение — не улучшать prose-дайджест, а заменить его для этого случая **структурной экстракцией прямо в
GOAP world state**, отдельным узким action'ом (`extractSearchCriteria` или похожий), а не общим
character-чатом:

- Каждый чанк даёт `Partial<WorldState>` с фиксированным набором типизированных полей
  (`category`, `priceMin`/`priceMax`, `brand`, `color`, `size`, ...) — не прозу.
- Мерж чанков — тот же механизм, что уже в executor'е: `state = {...state, ...effects}`. Даёт override
  "бесплатно": если пользователь на середине сообщения передумал, поздний чанк просто перезаписывает
  факт того же ключа — специально проектировать перезапись не нужно.
- Чанки в этом виде независимы друг от друга (в отличие от текущего sequential prose-refine, где
  следующий дайджест мог бы зависеть от контекста предыдущего) — в принципе параллелизуемы, но с учётом
  concurrency-guardrail на 6 ядрах по умолчанию гоняются последовательно с лимитом, не всей пачкой сразу.
- Дешёвый Laya-фильтр перед extraction-вызовом ("этот чанк вообще про критерии поиска, или шум?") —
  тот же cost-first принцип, что и везде в этом плане: не тратить albedo-вызов на нерелевантный чанк.
- Недостающие/неоднозначные поля после экстракции — не отдельная проверка, а естественное следствие
  GOAP: goal не satisfied → `askClarification` становится достижимым/предпочтительным следующим шагом
  сам по себе, без дополнительной логики "проверить, всё ли собрали".

`Agent.handleMessageStream` и его текущий chunk/ingest-пайплайн не меняются — это отдельный,
самостоятельный generation-action для character-ответов, а не механизм, который нужно чинить под
структурные домены.

## Явно не в этой фазе

- Выбор голосовой rus-STT модели (whisper слишком тяжёл) — отдельный план.
- Browser extension (Chrome/Firefox, WXT) и сам мост к WebMCP — отдельный план, `ToolSource`
  абстракция выше специально спроектирована так, чтобы его подключить без переделки ядра planner'а.
- RAG — отдельный план.
- Ollama как рантайм — не рассматривается, текстовая модель остаётся `albedo`/Vikhr-Llama-3.2-1B-Q4_K_M.

## Открытые вопросы (обсудить перед реализацией)

- **Где живёт per-thread world state — решено: in-memory, не turingDB.** World state сейчас — плоский
  `Record<string, ...>` на тред с семантикой "последний effect по ключу побеждает"; это key-value bag,
  не граф, так что graph DB тут не оправдана. turingDB (`apps/memory` — сейчас заготовка: Dockerfile +
  volume, закомментирована в `compose.yml`, клиента нет) — отдельный always-on sidecar с собственным
  RAM-footprint (in-memory по природе даже с volume под диск) и без официального JS/Bun-клиента
  (см. CLAUDE.md), это overhead против "низкое потребление ресурсов" при текущей задаче. Она станет
  оправдана, когда появятся реально graph-shaped запросы (связи товар↔категория↔бренд, рекомендации по
  истории) — то есть в RAG-фазе, не раньше. Если до RAG понадобится персистентность world state между
  рестартами (сейчас — тот же caveat, что у `ThreadHistory`, не переживает рестарт) — брать `bun:sqlite`
  на volume (embedded, ноль доп. сервисов/сетевых хопов, уже стандарт проекта), не turingDB.
- **Конкретный список actions/goals для домена "магазин/билеты".** Нужно 4-5 реальных actions
  (`searchTickets`, `addToCart`, `confirmPurchase`, `askClarification`, ...), чтобы провалидировать
  дизайн planner'а на реальном сценарии, а не в абстракции.
- **`/v1/messages` меняется на planner-режим, или добавляется отдельный endpoint** (`/v1/orchestrate`
  или похожий), а `/v1/messages` остаётся как есть для прямого чата без оркестрации?
- **MCP-тулы с авторизацией** (например, тул требует быть залогиненным в магазин) — как это попадает
  в `ActionContext`/`execute()`? Пока не спроектировано.
- **Как калибровать cost по факту**, а не на глаз — нужен простой прогон-бенчмарк (latency Laya vs
  albedo vs типичный tool) на целевом железе (Ryzen 5 5600H, CPU-only), прежде чем зашивать числа в
  action-registry.
- **Стартовые числа для concurrency-лимита и rate-лимита per-thread** (guardrails 2-3 выше) — нужно
  выбрать на основе того же бенчмарка, а не произвольно; отложено до фазы 5 (проводка в харнесс).
