# Трассы Gemini на демо-магазине: что нужно повторить

Три трассы Gemini (`gemini-3.6-flash`, расширение Chrome, WebMCP-тулы демо-магазина Basketful, 11 тулов) и то, как те же задачи сейчас проходит наш конвейер. Цель — тот же результат на маленьких локальных моделях и за меньшее время.

|---|---|---|---|---|---|---|
| `gemini_buy_few_products.json` | «купи Medium Roast Coffee Beans, Orange Juice,Paper Towels» | 4 | 6.9 с | 25.9k | ✅ 3 товара в корзине | ❌ один `query` «Honeycrisp Apples, Oat Milk» → ничего не найдено (`314a68f0…`) |
| `gemini_tomatoes.json` | «купи ингредиенты для Simple Tomato Pasta» | 5 | 11.0 с | 15.0k | ✅ рецепт целиком (10 позиций) | ❌ «успех», но в корзине 1 × Ground Beef вместо рецепта (`62581a65…`, Beef Tacos) |
| `remove_cart.json` | «очисти корзину» | 4 | 9.8 с | 20.7k | ✅ корзина пуста | ❌ план не построен, ответ «Корзина не содержит товаров», хотя это не так (`3aa52ff3…`) |

## Что делает Gemini

### Несколько товаров
1. Три `search_products` параллельно, по одному на товар: `"Medium Roast Coffee Beans"`, `"Orange Juice"`, `"Paper Towels"`.
2. Один `add_to_cart` с `items: [{product, quantity: 1} × 3]`, названия взяты из ответов поиска.
3. `get_cart`, потом текст с итогом.

Список делится на позиции по запятой. `add_to_cart` и так принимает массив `items`, то есть отдельный тул «со списком» не нужен.

### Рецепт
1. `add_recipe_to_cart {recipe: "Simple Tomato Pasta"}`: название рецепта есть в `enum` параметра `recipe`.
2. Ошибка «No store is open yet. Call choose_store first with one of: …» → `choose_store {store: "Greenleaf Market"}`, то есть первый вариант из текста ошибки.
3. Повтор `add_recipe_to_cart` → `get_cart` → текст.

Gemini восстанавливается по подсказке в тексте ошибки, а не по заранее известным предусловиям.

### Очистка корзины
1. `get_cart`, чтобы узнать, что в ней лежит.
2. Девять `update_cart_item {product, quantity: 0}` параллельно, по одному на строку корзины.
3. `get_cart` для проверки → «Корзина очищена».

Тула `clear_cart` нет. «Очистить» = прочитать корзину и обнулить каждую позицию.

## Общий шаблон
- **Разворачивание (fan-out):** одна команда превращается в N однотипных вызовов, и все они идут в одном ходе: поиск по каждому товару, удаление каждой строки.
- **Чтение перед записью:** `get_cart` перед удалением. Аргументы следующего шага копируются из ответа предыдущего (названия из поиска и из корзины).
- **Финальный `get_cart`** в конце каждой трассы, то есть отдельный круг модели. Для ответа он не обязателен: `add_to_cart` и `update_cart_item` уже возвращают итог.
- **Восстановление по тексту ошибки** (`choose_store`).
- Почти всё время уходит на круги модели: 4–5 кругов по 1–5 с, и на каждом заново отправляются 3–7k токенов схем тулов.

## Как получить то же на маленьких моделях
Модель ничего не перебирает, всё разворачивает код:

1. **Список товаров** — разбивать сообщение на позиции в коде (запятые, «и»/«and», числа перед словом) в `product-request.ts`. Каждый `query` искать отдельно, параллельно (все `search_products` в одном ожидании браузера), потом один `add_to_cart` с массивом `items`: значения берутся из фактов, delta не нужна.
2. **Рецепт / готовый набор** — если в тексте есть значение `enum` какого-то тула (`recipe: "Simple Tomato Pasta"`), выбирать этот тул: его специализация как раз подходит к запросу. Сейчас штраф `specialistPenalty` всегда делает его дороже `add_to_cart`. Совпадение искать по самой схеме, не по словарю продуктов.
3. **Действие над всеми позициями** («очисти корзину», «удали всё») — не отдельный сценарий, а тот же общий механизм развёртывания, что и в п. 1, только список берётся из ответа тула, а не из сообщения. Ничего не пишется под конкретный сайт:
   - тул, который читает текущее состояние (`get_cart`), Laya находит по имени и описанию (нужно намерение «прочитать состояние»; сейчас такого нет);
   - «всё/all/each» — короткий закрытый список в `message-cues.ts` (слой домена магазина);
   - позиции из ответа — строки списка (эвристика `firstListedProductName`, расширенная на все строки); если формат другой, их достаёт delta по схеме «массив строк»;
   - тул, который меняет позицию, — намерение `removeFromCart`. Что заполнять, видно из схемы: строка с именем позиции и, если есть, число с `minimum: 0` («0 removes»);
   - если у сайта есть `clear_cart`, планировщик выберет его, потому что он дешевле развёртывания.

   Сейчас `removeFromCart` вообще не строит план. Не сработает на сайтах, где позицию можно удалить только по внутреннему id, которого нет в ответе.
4. **Предусловие из текста ошибки** — ответ с `isError` и списком «one of: …» превращать в шаг `choose_store` с первым вариантом и перепланировать. У нас такой шаг есть, но запускается по факту `storeOpen`, а не по ошибке.
5. **Без финального `get_cart`** — итог берётся из ответа `add_to_cart` / `update_cart_item` (там есть subtotal), а ответ собирается шаблоном (`replyFromTemplate`).

С пунктами 1–5 каждой из трёх задач нужно 1–2 круга к браузеру и ноль–один вызов LLM (только перевод/классификация). У Gemini — 4–5 кругов и ~7–11 с работы модели.
