# План: свой Telegram-бот на Bun + Vercel AI SDK вместо IronClaw

## Почему не IronClaw

IronClaw — agentic-фреймворк, рассчитанный на модели уровня GPT-4/Claude с большим контекстом.
Его системный промпт + JSON-схемы встроенных тулов (File Tools, Shell) занимают **~15000 токенов**
ещё до первого сообщения пользователя, независимо от настроек (проверено: отключение local tools
размер промпта не изменило). На 1B-модели (`albedo`, CPU-only на Railway) обработка такого промпта
занимает 60-100+ секунд, а внутренний таймаут IronClaw на LLM-запрос — около 30 секунд. Итог: связка
принципиально не работает, это не баг конфигурации.

Вывод: для маленькой self-hosted модели нужен минимальный, полностью подконтрольный промпт — то есть
свой код, а не универсальный agent-фреймворк.

## Идея

Простой Telegram-бот на Bun, использующий Vercel AI SDK (`ai` пакет) для общения с `albedo`
(`llama-server`, OpenAI-совместимый API, уже задеплоен и работает). Никаких встроенных тулов —
только чат, при необходимости можно добавить 1-2 тула вручную позже, явно считая их "вес" в токенах.

## Компоненты

1. **Telegram-транспорт**: long polling через `getUpdates` (Bot API). Не webhook — не нужен
   публичный HTTPS-эндпоинт, меньше поверхности, проще для личного бота с низкой нагрузкой.
2. **Whitelist по user ID**: раз в IronClaw не было явного allowlist (только pairing-флоу),
   тут сделаем проще и прозрачнее — переменная окружения `ALLOWED_TELEGRAM_USER_IDS` со списком ID
   (у нас уже есть свой: `868076136`). Сообщения от остальных id игнорируются на входе, ещё до LLM-вызова.
3. **LLM-вызов**: Vercel AI SDK, `createOpenAI({ baseURL, apiKey })` → `generateText` / `streamText`,
   указывает на `https://albedo-production.up.railway.app/v1` с тем же `LLM_API_KEY`.
4. **Системный промпт**: короткий, в пару сотен токенов, полностью наш — без готового agent harness.
5. **История диалога**: храним последние N сообщений на chat_id в памяти процесса (сбрасывается при
   рестарте — для личного бота это ок). Если понадобится персистентность — `bun:sqlite` на Railway
   Volume, по той же схеме, что уже используется у `albedo`/`ironclaw`.
6. **Без встроенных тулов на старте.** Если позже понадобится что-то (веб-поиск, память, cron) —
   добавляем вручную через `tools` в Vercel AI SDK, каждый раз сознательно считая, сколько токенов
   он добавляет к промпту — с учётом бюджета контекста модели (сейчас `CTX_SIZE=16384` на `albedo`).

## Деплой

- Новый Railway-сервис (например `telegram-bot`) в том же проекте `grand-stillness`.
- Bun-рантайм: либо простой `Dockerfile` (`FROM oven/bun:alpine`), либо нативная детекция Railway
  без Dockerfile — решим на этапе реализации.
- Переменные: `TELEGRAM_TOKEN` (уже есть в `.env`), `LLM_BASE_URL`, `LLM_API_KEY` (переиспользуем
  значения `albedo`), `ALLOWED_TELEGRAM_USER_IDS`.
- Тестирование по аналогии с `albedo`: локальный `bun test`, прогон через docker перед реальным деплоем.

## Судьба IronClaw-сервиса

Не трогаем прямо сейчас — решим отдельно после того, как новый бот заработает: либо удалить
(`ironclaw` сервис + volume + переменные в Railway), либо оставить на будущее под более крупный
облачный провайдер, если он когда-нибудь понадобится.

## Открытые вопросы (обсудить перед реализацией)

- Long polling vs webhook — long polling выбран по умолчанию, но если важна мгновенная доставка,
  можно пересмотреть.
- Формат хранения истории диалога — in-memory (просто) vs sqlite на volume (переживает рестарты).
- Нужны ли вообще какие-то тулы на старте, или чистый чат достаточно.
