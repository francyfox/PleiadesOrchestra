# План: пользователи, белый список и блокировки, учёт токенов, веб-каналы магазинов, админка с визуализацией GOAP

## Контекст и цель

Сейчас:

- история диалога — in-memory `ThreadHistory` (`packages/core/src/history.ts`), последние 10
  сообщений на тред, теряется при рестарте `alpha-orchestrator`;
- белый список есть только в `apps/telegram-bot` — env `ALLOWED_TELEGRAM_USER_IDS`, проверка в
  `handlers/message.ts` и `handlers/start.ts`, чужим бот молча не отвечает. Чтобы добавить
  человека, нужно править env и перезапускать бота. Блокировок нет;
- `userId` приходит в `POST /v1/messages`, но нигде не сохраняется;
- токены видны только в stdout-телеметрии (`logLlmState`), и неполно (см. «Учёт токенов»);
- что делал GOAP-планировщик, не видно — `runPlan` отдаёт только `executedActions: string[]`.

Новое требование к каналам: Плеяда — ещё и чат-бот интернет-магазинов, **магазинов/сайтов может
быть много**. У магазина бывают анонимные посетители, а у сайта может не быть своих сессий, —
оркестратор должен сам выдавать id посетителя.

Цели:

1. Пользователи в SQLite (`drizzle-orm` + `bun:sqlite`), для каждого хранятся **только последние
   10 сообщений**.
2. Белый список и блокировки — в БД, управляются из админки. Заблокированному или не
   допущенному пользователю **API просто перестаёт отвечать**.
3. Учёт расхода токенов по пользователям. **Квоты — не в этом плане.**
4. Веб-каналы для множества сайтов с анонимными посетителями.
5. Админка `apps/admin`: SvelteKit (Svelte 5) + shadcn-svelte + TanStack Table — пользователи,
   расход, блокировка, белый список, последние сообщения, визуализация GOAP-прогонов.

Не цель: turingdb (`apps/memory`), квоты, сам JS-виджет для сайта магазина (UI в браузере
покупателя — отдельный план; здесь только серверная сторона).

## Ключевые решения

### Базой владеет только `alpha-orchestrator`

SQLite-файл открывает один процесс. Админка ходит по HTTP (`/v1/admin/*`), `telegram-bot` — как
и сейчас, по HTTP. Шарить файл между контейнерами — скрытая связка в обход HTTP-схемы, плюс
SQLite — один писатель.

### Порты в `packages/core`, адаптеры в оркестраторе

- `HistoryStore` (async `get`/`append`/`reset`) вместо `ThreadHistory`; in-memory реализация
  остаётся для тестов.
- `UsageRecorder` — вызывается на **каждый** вызов модели.
- `PlanTracer` — опциональный колбэк `runPlan`.

Drizzle-схема и реализации — `apps/alpha-orchestrator/src/db/`. `Agent.resetThread` →
`Promise<void>`, HTTP-контракт `/v1/threads/:id/reset` не меняется.

### Проверка доступа переезжает из `telegram-bot` в оркестратор

Чтобы админка могла показать и пользователя, который ещё не в белом списке, и добавить его туда
кнопкой, оркестратор должен узнавать о каждом, кто пишет. Поэтому:

- `telegram-bot` больше не проверяет `ALLOWED_TELEGRAM_USER_IDS` сам. На каждое сообщение и
  `/start` он сначала вызывает `POST /v1/access` (`{ channel, externalUserId, displayName }`) —
  оркестратор регистрирует пользователя, если его ещё нет, обновляет `lastSeenAt`/`displayName`
  и отвечает `{ allowed: boolean }`. При `allowed: false` бот молча ничего не делает — ровно
  как сейчас, **до** того как показать статус-сообщение «думаю…».
- `/v1/messages` проверяет доступ ещё раз и при отказе отвечает `403` без тела, модель не
  вызывается (защита, если какой-то клиент пропустит `/v1/access`).
- Текст сообщений недопущенных пользователей не сохраняется — только сам пользователь.
- Env `ALLOWED_TELEGRAM_USER_IDS` и обе проверки в хендлерах удаляются после переноса (разовый
  скрипт импорта текущих id в БД, см. фазы) — confirmed-dead код не оставляем.

«Перестаёт отвечать» реализуется как «молча не отвечает пользователю», а не как зависшее
HTTP-соединение: висящие запросы держали бы ресурсы на и так ограниченном железе.

## Модель данных

### Роли: пользователь и администратор

В системе ровно две роли, и они не пересекаются:

- **Пользователь** — тот, кто пользуется чатом: через Telegram или через виджет на сайте
  магазина. В админку не входит. Бывает *identified* (известен id от канала: Telegram id или
  id аккаунта магазина) и *anonymous* (посетитель сайта без аккаунта, id выдаёт оркестратор).
  Anonymous — это не отдельная роль, а тот же пользователь, только без внешнего id.
- **Администратор** — тот, кто входит в админку: смотрит пользователей и расход, блокирует,
  ведёт белый список, настраивает каналы. Через чат не работает, в `users` не хранится.

Поэтому роли живут в разных местах:

- пользователи чата — таблица `users` в БД оркестратора (приходят через каналы);
- администраторы — учётные записи **better-auth в `apps/admin`**, в отдельной SQLite-базе
  админки (см. «Авторизация администраторов»). Оркестратор про учётки администраторов ничего не
  знает: ему приходит только id администратора, выполнившего действие.

У пользователя нет пароля, у администратора — канала, белого списка и сообщений, так что общей
таблицы с полем `role` нет.

### Каналы

Каждый вход в систему — канал: Telegram-бот, CLI, каждый сайт магазина. Сайтов много, в будущем
может быть и несколько ботов — поэтому одна таблица:

```ts
channels { id, slug (unique, напр. "telegram", "cli", "shop-foo"), kind ("telegram" | "cli" | "web"),
           name, accessMode ("whitelist" | "open"),
           publishableKey?, secretKeyHash?, allowedOrigins? (json),   // только web
           disabledAt?, createdAt }
```

- `telegram` — `whitelist` (как сейчас), `cli` — `open` (и так закрыт `HARNESS_API_KEY`),
  сайты магазинов — обычно `open`, но режим переключается в админке.
- Server-to-server клиенты (`telegram-bot`, `cli`, бэкенд магазина) передают `channel` (slug)
  в теле запроса; поле опциональное с дефолтом по `source`-совместимости, чтобы старые клиенты
  не сломались до обновления.

### Пользователи

```ts
users { id (uuid, наш), channelId → channels.id, externalUserId?, kind ("identified" | "anonymous"),
        displayName?, createdAt, lastSeenAt,
        whitelistedAt?, whitelistedBy?,          // id администратора из better-auth (без FK — другая БД)
        blockedAt?, blockedReason?, blockedBy? }
  unique(channelId, externalUserId)
```

Правило доступа (одна чистая функция, тестируется отдельно):

1. канал отключён → нет;
2. `blockedAt` → нет (блокировка сильнее белого списка);
3. канал `whitelist` → только при `whitelistedAt`;
4. иначе → да.

Статус доступа кэшируется в памяти процесса и инвалидируется admin-эндпоинтами — процесс один,
так что инвалидация тривиальна и БД не дёргается на каждое сообщение.

### Сообщения — только последние 10 на пользователя

```ts
threads  { id, userId → users.id, channelId, externalThreadId?, createdAt }
messages { id, threadId → threads.id, userId, role ("user" | "assistant"), content, createdAt, planRunId? }
  index(userId, createdAt), index(threadId, createdAt)
```

- При вставке, в той же транзакции, удаляются сообщения пользователя старше 10-го
  (`DELETE ... WHERE userId = ? AND id NOT IN (последние 10)`). Лимит — env
  `MESSAGE_RETENTION_PER_USER=10`. Он должен быть не меньше `maxHistoryMessages` агента (сейчас
  тоже 10), иначе модель потеряет контекст, который раньше видела. Это проверяется при старте.
- Контекст для модели — последние N сообщений **треда** из этой же таблицы. То есть хранилище и
  контекст — одно и то же, отдельного in-memory кэша нет.
- Лимит считается **на пользователя, а не на тред** (решено). Следствие, принятое осознанно: если
  у пользователя несколько тредов (например, Telegram-группы), переписка в одном вытесняет
  контекст другого. Это покрывается тестом, чтобы поведение было задокументировано.
- `reset` удаляет сообщения треда (как и сейчас — поведение не меняется).
- Трейсы GOAP удаляются вместе со своими сообщениями (`ON DELETE CASCADE` по `planRunId`), чтобы
  трейсы не пережили сообщения, к которым относятся.
- **Журнал токенов при этом не удаляется** — он не содержит текста и нужен для статистики расхода
  за любой период (см. ниже).

**Конфиденциальность**: раньше текст чатов нигде не сохранялся. Теперь до 10 последних сообщений
каждого пользователя (включая покупателей магазинов) лежат на диске. Файл БД — только в named
volume (`*.db*` в `.gitignore`/`.dockerignore`), `/v1/admin/*` — под отдельным ключом.

## Учёт расхода токенов

### Что сейчас не так

- В `packages/core/src/agent.ts` длинное сообщение режется на чанки, и на каждый чанк, кроме
  последнего, делается отдельный ingest-вызов `generateText`. Его токены уходят только в
  `logLlmState`, а в `done` (и дальше в `toEffects` у `generateReply`, и в usage-строку `apps/cli`)
  попадают **только токены финальной генерации**. Длинные сообщения недосчитываются.
- `llama-server` может не вернуть usage — тогда токены `undefined`, это не 0.

### Решение: журнал вызовов, агрегаты — запросом

```ts
llm_calls { id, createdAt, userId?, channelId?, threadId?, planRunId?, actionName?,
            kind ("ingest" | "generate" | "decision"), provider, model,
            inputTokens?, outputTokens?, latencyMs, ok, error? }
  index(userId, createdAt), index(channelId, createdAt)
```

- `UsageRecorder` в core вызывается рядом с каждым `telemetry.logLlmState`, включая ingest-вызовы,
  с контекстом (`threadId`, `userId`, `kind`), переданным через `IncomingMessage`.
- Laya (`DecisionAgent`) пишется как `kind = "decision"`: токенов у неё нет, но латентность — это
  расход CPU на этом железе.
- `done` получает дополнительно `totalInputTokens`/`totalOutputTokens` за сообщение
  (существующие поля не меняются — на них завязана usage-строка `apps/cli`).
- `null`-токены показываются в админке как «нет данных» и считаются отдельным счётчиком.
- Запись — одна транзакция на сообщение после отправки `done`, чтобы не задерживать стриминг.
- `llm_calls` не чистится вместе с сообщениями. Это одна короткая строка на вызов модели, для
  SQLite это немного. Если вырастет — свёртка старых строк в дневные агрегаты, отдельной задачей.
- Если пользователь удалён, его строки остаются с `userId = null`, и суммарный расход за период
  не меняется.

## Трассировка и визуализация GOAP

### Что записывать

В `RunPlanOptions` (`packages/core/src/goap/executor.ts`) добавляется опциональный
`tracer?: (event: PlanTraceEvent) => void`. Это чистый колбэк без зависимости от БД:

```ts
type PlanTraceEvent =
  | { type: "planned"; attempt: number; plan: { name: string; cost: number }[]; totalCost: number; state: WorldState }
  | { type: "no_plan"; attempt: number; state: WorldState }
  | { type: "action_skipped"; attempt: number; action: string; unmetPreconditions: Partial<WorldState> }
  | { type: "action_started"; attempt: number; action: string; at: number }
  | { type: "action_finished"; attempt: number; action: string; durationMs: number;
      expectedEffects: Partial<WorldState>; observedEffects: Partial<WorldState> }
  | { type: "action_failed"; attempt: number; action: string; durationMs: number; error: string }
  | { type: "replan"; attempt: number; state: WorldState }
  | { type: "finished"; succeeded: boolean; attempts: number; durationMs: number };
```

```ts
plan_runs   { id, userId, threadId, goal (json), succeeded, attempts, durationMs, createdAt }
plan_events { runId → plan_runs.id (cascade), seq, type, attempt, action?, payload (json), at }
```

- События копятся в памяти за прогон и пишутся одной транзакцией после завершения, а не на
  каждое действие.
- Длинные строки в `state` обрезаются (~500 символов): полный текст и так лежит в `messages`.
- Трейс не добавляется в публичный NDJSON-поток `/v1/messages`.
- `llm_calls.planRunId`/`actionName` связывают расход токенов с конкретным действием плана. При
  удалении прогона ставится `null`, сами строки не удаляются.

### Визуализация в админке

У каждого ответа ассистента — ссылка на страницу прогона `/runs/[id]`:

1. **Граф плана** (`@xyflow/svelte`): узлы — действия в порядке плана, по дорожке на каждую
   попытку (перепланирование = новая дорожка), последний узел — цель. Цвет узла — статус
   (выполнено / пропущено по предусловиям / упало / не дошли). На узле — `cost`, длительность,
   токены.
2. **Таймлайн**: полосы действий по времени.
3. **Ожидаемые и фактические эффекты**: таблица с подсвеченными расхождениями. Расхождения
   объясняют перепланирование.

`/goap/actions` — каталог действий как граф «факт → действие → факт» из
`GET /v1/admin/goap/actions` (имя, `cost`, `preconditions`, `effects`, без `execute`).

Преобразование событий трейса в узлы и рёбра графа — чистая функция в `apps/admin`, покрывается
тестами.

## Веб-каналы магазинов (много сайтов, анонимные посетители)

### Visitor-токены

```ts
visitor_tokens { tokenHash (pk, sha256), userId → users.id, channelId, createdAt, lastUsedAt, expiresAt }
```

1. Виджет без токена → `POST /v1/widget/visitors` (publishable-ключ канала + `Origin` из
   `allowedOrigins`) → оркестратор создаёт anonymous-пользователя и возвращает случайный токен
   (32 байта). В БД хранится только хеш.
2. Виджет хранит токен на домене магазина (cookie/`localStorage`). Срок жизни — **1 день**
   с последней активности (каждый запрос продлевает `expiresAt`).
3. Потерян или истёк токен — новый анонимный пользователь. Это нормальное свойство анонимности.

### Хранение анонимных пользователей — один день

Касается только анонимных пользователей чата (посетителей сайтов без аккаунта). Пользователи из
Telegram и identified-посетители магазинов под это правило не попадают, администраторы — тем
более.

Если анонимный пользователь не писал в чат больше 24 часов, удаляются:

- его запись в `users`;
- его треды и сообщения;
- его visitor-идентификатор (`visitor_tokens`) — виджет при следующем визите получит новый;
- GOAP-трейсы его ответов (каскадом).

Не удаляется журнал расхода LLM-токенов (`llm_calls`): строки остаются, у них только обнуляется
ссылка на пользователя (`userId = null`), канал сохраняется. Поэтому статистика расхода по
каналам и по дням в админке не меняется после очистки. Пропадает только разбивка по этому
конкретному анонимному пользователю.

- Очистка — периодическая задача внутри оркестратора (`setInterval` раз в час, один
  `DELETE ... WHERE kind = 'anonymous' AND lastSeenAt < now - 24h` в транзакции) плюс запуск при
  старте. Отдельный cron-сервис не нужен: процесс один.
- Порог — env `ANON_RETENTION_HOURS=24`, логика отбора — чистая функция с тестом.
- Identified-пользователи (включая бывших анонимов после `identify`) под очистку не попадают.
- Заблокированные анонимы тоже удаляются: блокировка по токену всё равно живёт не дольше
  токена (1 день). Долгосрочная защита от анонимов — блокировка по IP-хешу, у неё свой срок.
- При слиянии с существующим пользователем анонимная запись удаляется сразу, ждать сутки не нужно.

### Связывание с аккаунтом магазина

Бэкенд магазина (не браузер), когда покупатель залогинился:
`POST /v1/channels/:slug/identify` с секретным ключом канала, тело
`{ visitorToken, externalUserId }`. Анонимный пользователь становится identified, либо, если
такой identified уже есть, сливается с ним: переносятся сообщения (с повторной обрезкой до 10),
строки `llm_calls` и токены посетителя, анонимная запись удаляется. Флаги
`blockedAt`/`whitelistedAt` при слиянии объединяются в пользу более строгого: блокировка любой из
двух записей сохраняется.

Если у магазина нет своих аккаунтов — шаг не используется. Если у магазина есть свой id корзины
или сессии — бэкенд магазина может слать его как `externalUserId` через server-to-server канал,
тогда visitor-токены не нужны.

### Защита публичного канала

Без квот, но открытый анонимный доступ к CPU-only модели всё равно требует базовой защиты:
CORS/`Origin` по `allowedOrigins`, rate limit на токен и на IP (in-memory), лимит длины текста,
лимит на выдачу visitor-токенов с одного IP. IP хранится только как солёный хеш — для rate limit
и блокировки. Блокировка анонимного посетителя по токену слабая (очистил cookies — и он новый),
поэтому для веб-каналов есть блокировка по хешу IP (`blocked_ips { ipHash, channelId?, reason,
createdAt, expiresAt }`), обязательно со сроком: IP бывают общими.

### Эндпоинты

| Метод | Путь | Auth | Что |
|---|---|---|---|
| POST | `/v1/widget/visitors` | publishable key + Origin | выдать visitor-токен |
| POST | `/v1/widget/threads` | + visitor-токен | новый разговор |
| POST | `/v1/widget/messages` | + visitor-токен | как `/v1/messages`, NDJSON; только в свои треды |
| GET | `/v1/widget/threads/:id/messages` | + visitor-токен | последние сообщения своего треда |
| POST | `/v1/channels/:slug/identify` | секретный ключ канала | связать посетителя с аккаунтом магазина |

Посетитель читает и пишет **только в свои треды** — проверка по `threads.userId`, не по id из
запроса.

## Admin API в `alpha-orchestrator`

Отдельный секрет `ADMIN_API_KEY`. Проверка в том же `onRequest`-хуке по префиксу `/v1/admin`
(см. Lessons learned про порядок хуков Elysia).

| Метод | Путь | Что |
|---|---|---|
| GET | `/v1/admin/users?channel&kind&status&q&sort&cursor&limit` | пользователи: канал, статус (разрешён / ждёт белого списка / заблокирован), `lastSeenAt`, токены за период |
| GET | `/v1/admin/users/:id` | карточка: статус, расход по дням, последние сообщения |
| POST | `/v1/admin/users/:id/whitelist` · `unwhitelist` | белый список |
| POST | `/v1/admin/users/:id/block` · `unblock` | блокировка с причиной |
| DELETE | `/v1/admin/users/:id/messages` | стереть сообщения пользователя |
| GET | `/v1/admin/usage?groupBy=day\|user\|channel\|model&from&to` | агрегаты из `llm_calls` |
| GET | `/v1/admin/runs/:id` | прогон GOAP + события |
| GET | `/v1/admin/goap/actions` | каталог действий |
| CRUD | `/v1/admin/channels` | каналы/сайты: режим доступа, ключи (ротация), домены, отключение |
| CRUD | `/v1/admin/blocked-ips` | блокировки по IP |

Список пользователей отдаётся с серверной сортировкой, фильтрами и курсорной пагинацией: при
множестве сайтов с анонимными посетителями пользователей будет много, и держать их всех в
браузере нельзя. Тесты — через `app.handle(request)` с `new Database(":memory:")` и теми же
миграциями.

## Миграции и деплой

- `drizzle-kit generate` → SQL в `apps/alpha-orchestrator/drizzle/` (коммитится); `migrate()` из
  `drizzle-orm/bun-sqlite/migrator` на старте до `.listen()`.
- **Риск `--compile`**: мигратор читает папку с диска, в standalone-бинарник она не вшивается —
  копировать `drizzle/` в финальный образ, путь через env (`DATABASE_MIGRATIONS_DIR`). Проверить
  сборкой образа.
- Первая миграция создаёт каналы `telegram` (`whitelist`) и `cli` (`open`).
- Env через `buildConfig`: `DATABASE_PATH`, `ADMIN_API_KEY`, `MESSAGE_RETENTION_PER_USER`,
  `IP_HASH_SALT`, `ANON_RETENTION_HOURS`.
- `compose.yml`: volume `alpha-orchestrator-data:/data`. Для виджетов `/v1/widget/*` должен быть
  доступен из интернета (туннель, как у webhook бота); `/v1/admin/*` наружу не публикуется.

## `apps/admin` — SvelteKit + shadcn-svelte + TanStack Table

### Стек

- SvelteKit 2 + Svelte 5 (runes), TypeScript.
- UI: `shadcn-svelte` (Tailwind v4, `bits-ui`): `sidebar`, `table`, `card`, `badge`, `dialog`,
  `dropdown-menu`, `tabs`, `chart` (LayerChart — графики расхода), `sonner`.
- **Все таблицы — TanStack Table**: `@tanstack/svelte-table` v9 (стабильный, peer `svelte ^5`).
  Разметка — компонент `table` из shadcn-svelte. Гайд shadcn-svelte «Data Table» написан под
  v8 (`@tanstack/table-core` + свой хелпер `createSvelteTable`). С v9 берём официальный
  адаптер и сверяемся с его API, а не копируем гайд вслепую. Для списков с серверной пагинацией
  — `manualPagination`/`manualSorting`/`manualFiltering`: состояние таблицы синхронизируется с
  query-параметрами URL, данные грузит `+page.server.ts`.
- Последние сообщения пользователя: `@humanspeak/svelte-virtual-chat`. Сообщений максимум 10,
  так что виртуализация тут скорее ради готового вида чата, подгрузка истории не нужна. Контент
  выводится как текст, не через `{@html}`.
- Граф GOAP: `@xyflow/svelte`.
- Адаптер: `svelte-adapter-bun`; запасной — `@sveltejs/adapter-node` под `bun`.

### Архитектура

- BFF: доступ к оркестратору — только из серверного кода (`+page.server.ts`, form actions для
  кнопок блокировки/белого списка, `src/lib/server/orchestrator-client.ts`). `ADMIN_API_KEY` в
  браузер не попадает. Свой клиент, не общий с `cli`/`telegram-bot`.
- Env — `@t3-oss/env-core` + `zod` по правилу CLAUDE.md.
- Каждый admin-запрос BFF передаёт id вошедшего администратора (заголовок `X-Admin-Id` рядом с
  `ADMIN_API_KEY`), оркестратор пишет его в `whitelistedBy`/`blockedBy`. Имена по этим id
  админка подставляет из своей базы.

### Авторизация администраторов — better-auth

better-auth живёт **в `apps/admin`**, а не в оркестраторе: учётки администраторов — забота
админки, а оркестратор так и остаётся за `ADMIN_API_KEY` и в браузер не смотрит.

- **Хранилище**: отдельная SQLite-база админки (`ADMIN_DATABASE_PATH`, свой volume
  `admin-data`), `drizzle-orm/bun-sqlite` + `drizzleAdapter(db, { provider: "sqlite" })`. Схему
  таблиц better-auth (`user`, `session`, `account`, `verification`) генерирует
  `@better-auth/cli generate`, миграции — `drizzle-kit`, как и в оркестраторе. Это не нарушает
  правило «базой чата владеет оркестратор»: здесь нет ни одной таблицы чата.
- **Способ входа**: только `emailAndPassword` (почта + пароль), без OAuth-провайдеров.
- **Плагины**: `admin` (даёт `createUser`, список, бан/разбан, смену пароля — всё, что нужно
  странице `/admins`) и `sveltekitCookies(getRequestEvent)` последним в списке, чтобы вызовы
  из form actions ставили cookie.
- **SvelteKit**: `svelteKitHandler({ event, resolve, auth, building })` в `hooks.server.ts`.
  `event.locals.user`/`session` он сам не заполняет — заполняем вручную через
  `auth.api.getSession({ headers })`.
- **Env**: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `ADMIN_DATABASE_PATH` — через `buildConfig`.

**Первый запуск и закрытие регистрации:**

1. `hooks.server.ts` на каждом запросе знает, есть ли хоть один администратор. Если нет —
   **любая страница редиректит на `/register`** (почта + пароль). Флаг «администратор есть»
   после первого `true` кэшируется в памяти: обратно в `false` он не возвращается, потому что
   удалить или забанить последнего администратора запрещено.
2. Первая успешная регистрация создаёт администратора и сразу логинит его (better-auth
   `autoSignIn`).
3. Как только администратор есть, **публичная регистрация закрыта**: `/register` редиректит на
   `/login`, а сам эндпоинт better-auth `/sign-up/email` отклоняется хуком
   (`hooks.before` + `createAuthMiddleware`: `ctx.path === "/sign-up/email"` и в `user` есть
   записи → `APIError("FORBIDDEN")`). Закрывать нужно именно на уровне API, а не только
   страницы — иначе можно зарегистрироваться прямым POST.
4. Дальше новых администраторов создаёт только вошедший администратор со страницы `/admins`:
   form action вызывает `auth.api.createUser({ headers, body: { email, password, name,
   role: "admin" } })` из admin-плагина. Этот путь идёт мимо `/sign-up/email`, поэтому хук
   регистрации его не блокирует, а сам `createUser` требует сессию с ролью `admin`.
5. Все учётки в этой базе — администраторы. `databaseHooks.user.create.before` принудительно
   ставит `role: "admin"`, чтобы не появилось «пользователя» без прав, который может войти.
   Пользователи чата сюда никогда не попадают.

Гонка двух одновременных «первых» регистраций теоретически возможна: проверка и вставка не
атомарны. Админка слушает только `127.0.0.1`, так что риск принят. Если понадобится —
повторная проверка в `databaseHooks.user.create.before` внутри той же транзакции.

Будущее, не в этом плане: приглашение по реферальной ссылке (одноразовый токен с TTL,
по которому `/register` снова открывается для одного человека). Новая таблица
`admin_invites`, остальная схема не меняется.

### Страницы

- `/` — дашборд: токены за сегодня / 7 / 30 дней (график по дням), топ пользователей и каналов
  по расходу, доля вызовов без usage, сколько пользователей ждёт белого списка.
- `/users` — **таблица TanStack**: имя, канал, тип (anon/identified), статус, последняя
  активность, токены за период. Фильтры: канал, статус, поиск. Сортировка по расходу/активности.
  Действия в строке и массово (выбор строк): «в белый список», «убрать из белого списка»,
  «заблокировать» (диалог с причиной), «разблокировать».
- `/users/[id]` — статус и те же кнопки, график расхода по дням, таблица расхода по моделям
  и типам вызовов, последние 10 сообщений (`svelte-virtual-chat`) со ссылками на GOAP-прогоны,
  «стереть сообщения».
- `/runs/[id]` — граф плана, таймлайн, таблица ожидаемых и фактических эффектов.
- `/goap/actions` — каталог действий.
- `/channels` — таблица каналов/сайтов: режим доступа, домены, отключение, ротация ключей
  (секретный ключ показывается один раз).
- `/blocked-ips` — таблица блокировок по IP.
- `/register` — регистрация первого администратора (доступна только пока администраторов нет).
- `/login` — вход по почте и паролю.
- `/admins` — таблица администраторов (TanStack): создать нового (почта, имя, временный
  пароль), забанить/разбанить, сменить пароль. Последнего активного администратора забанить
  нельзя.

## Фазы реализации (test-first, по одному PR-размеру на фазу)

1. **Порты в core**: `HistoryStore` (async), `UsageRecorder` на каждый вызов модели (включая
   ingest), суммарные токены в `done`.
2. **Трассировка `runPlan`**: `tracer`, события по списку выше; тесты на перепланирование,
   пропуск по предусловиям, падение действия.
3. **SQLite-слой**: `channels`/`users`/`threads`/`messages`/`llm_calls`/`plan_runs`/`plan_events`,
   миграции, реализации портов, обрезка до 10 сообщений на пользователя.
4. **Доступ**: чистая функция правила доступа, `POST /v1/access`, `403` в `/v1/messages`, кэш
   статуса. `channel`/`displayName` в запросах из `telegram-bot` и `cli`.
5. **Перенос белого списка** (низкий приоритет — Telegram-бот сейчас не главный канал): разовый скрипт импорта текущих `ALLOWED_TELEGRAM_USER_IDS` в БД,
   `telegram-bot` переходит на `/v1/access`. После этого env-переменная и проверки в хендлерах
   удаляются.
6. **Docker/compose**: volume, миграции в образе, живая проверка `--compile`-бинарника
   (сообщение → рестарт → история и расход на месте; не допущенный пользователь молча
   игнорируется).
7. **Admin API** (`/v1/admin/*`, `ADMIN_API_KEY`, `X-Admin-Id`).
8. **Скелет `apps/admin`**: SvelteKit + shadcn-svelte + TanStack Table + адаптер, закрыть трения.
   better-auth: своя SQLite, `/register` → первый администратор, закрытие регистрации (тест:
   прямой POST на `/sign-up/email` после первого администратора → 403), `/login`, `/admins`.
9. **Страницы**: `/users` (таблица, фильтры, массовые действия), `/users/[id]`, дашборд расхода.
10. **Визуализация GOAP**: `/runs/[id]`, `/goap/actions`.
11. **Веб-каналы**: visitor-токены, `/v1/widget/*`, CORS/Origin, rate limit, `blocked_ips`,
    `identify` со слиянием, суточная очистка анонимов; страницы `/channels`, `/blocked-ips`.
12. **CLAUDE.md**: `apps/admin`, владелец БД, доступ через оркестратор, веб-каналы, уроки.

Фазы 1–10 закрывают Telegram + CLI + админку. Фаза 11 — когда понадобится первый магазин.
