# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root unless noted (Turborepo fans out per package; `test` depends on `^build`).

- `bun install` — required again after renaming/moving any `apps/*` or `packages/*` directory (relinks workspace symlinks).
- `bun run test` / `bun run lint` / `bun run check-types` / `bun run build` — all workspaces via turbo. `lint:fix` and `format` run Biome over the whole tree.
- Single package: `bun --cwd apps/alpha-orchestrator test`. Single file/test: `bun test packages/core/src/goap/plan.test.ts` (add `-t "name"` to filter).
- Run a service locally: `bun --cwd apps/<name> run dev` (watch) or `start`. Each has its own `.env` — copy from `.env.example`; `compose.yml` reads the root `.env` plus `apps/*/.env`.
- Whole stack: `docker compose up --build` (includes `telegram-bot`; a single service: `docker compose up -d --build <service>`).
- `bun run test:beta-text` — builds and boots the real `llama-server` Docker image (downloads a ~770MB model, up to 15 min). Deliberately **not** part of `bun run test`; don't run it casually.
- Only `alpha-orchestrator` and `telegram-bot` have a `build` script (`bun build --compile` binaries into `dist/`); `admin-api`'s Docker image compiles the same way (no local `build` script); `cli`/`gamma-decision` run straight from source. The orchestrator's binary is still named `dist/harness`. `apps/admin` builds with Vite (`bun --bun vite build` → `build/`, plain static files — `adapter-static`).
- DB migrations (drizzle-kit, SQL committed under `drizzle/`): `bun --cwd apps/alpha-orchestrator run db:generate --name <name>` after editing `src/db/schema.ts`; same idea in `apps/admin-api` for the better-auth schema (`auth:schema` regenerates `src/db/auth-schema.ts` first). Both apps apply migrations at startup. Run `bunx biome format --write <app>/drizzle/meta` after generating — drizzle-kit writes space-indented JSON that Biome rejects.
- One-off: `bun --cwd apps/alpha-orchestrator run import:telegram-whitelist <ids>` seeds the Telegram whitelist into the DB (replaced the old `ALLOWED_TELEGRAM_USER_IDS` env check in the bot).

## GOAP code and other things not obvious from the tree

- `packages/core/src/goap/` is the GOAP planner/executor (`plan`, `runPlan`, `createTextAction`, `createDecisionAction`, MCP-backed `ToolSource`). `WorldState` is a flat key→value fact bag, not a graph; actions declare preconditions/effects, and the executor reconciles the *actual* effects (what `execute()` returns) against the expected ones. `apps/alpha-orchestrator/src/server.ts` builds the action catalog once per app instance (`buildActions`), and `/v1/messages` streams a `runPlan` run as NDJSON (`delta`/`done`/`error`). Right now the catalog has a single `generateReply` action toward goal `{ replied: true }`; Laya actions, MCP tools and per-intent goals are the planned next phases. `docs/harness-goap-orchestrator-plan.md` (in Russian) is the source of truth for design and phase status.
- `packages/core` also holds the `DecisionAgent` port (HTTP client to `apps/gamma-decision`) next to the `Agent` port; `alpha-orchestrator` is the only consumer of both.
- `apps/memory` is just a `turingdb` Dockerfile; its compose service and volume are commented out. Persistent history is SQLite in `alpha-orchestrator` now (below), turingdb isn't needed for it.
- **Users, access, usage — `docs/sessions-and-admin-plan.md` (design) and `docs/admin-api.md` (the HTTP contract between orchestrator, admin and transports; change it in the same PR as the code).** `alpha-orchestrator` owns a SQLite DB (`drizzle-orm` + `bun:sqlite`, `src/db/`): channels (general-purpose entry points: Telegram, CLI, a website, later Discord/Slack/… — `accessMode` whitelist/open; never describe them as shop-specific), chat users (identified or anonymous; anonymous ones are deleted after `ANON_RETENTION_HOURS` of inactivity), last `MESSAGE_RETENTION_PER_USER` (10) messages **per user** (shown in the admin panel; **not** sent to the model — `AGENT_MAX_HISTORY_MESSAGES = 0` in `apps/alpha-orchestrator/src/agent.ts`: the 1B model copies its own earlier replies and after a few canned "How can I help?" answers answers nothing else, measured on `llama-server` 2026-09-28; sampling penalties/temperature didn't help. `createAgent`'s `maxHistoryMessages: 0` = stateless, the exchange is still stored), an `llm_calls` usage ledger (one row per model call incl. ingest passes; never deleted with messages), and GOAP traces (`plan_runs`/`plan_events`). Access (block > whitelist) is decided by the orchestrator, not by transports: the bot calls `POST /v1/access` first and stays silent on `allowed: false`; `/v1/messages` answers an empty `403` for denied users without calling the model. Admin routes are `/v1/admin/*` under a separate `ADMIN_API_KEY` + `X-Admin-Id`. Public site-widget routes are `/v1/widget/*` (publishable key + `Origin` allowlist + visitor token, in-memory rate limits) and `POST /v1/channels/:slug/identify` (server-to-server, links an anonymous visitor to the integrating site's account). Only this process opens the DB file — everything else goes through HTTP.
- **IPs**: blocking still matches by salted hash (`blocked_ips.ip_hash`, `isIpBlocked`), but the plaintext IP is now also stored — `users.last_ip` (set by widget requests) and `blocked_ips.ip` (null on legacy rows) — so admins can see it and open a whois/geo lookup (`apps/admin/src/lib/ip.ts`). Anonymous users (and their `last_ip`) are purged with the usual retention; blocks expire.
- Admin list endpoints `GET /v1/admin/channels` and `/blocked-ips` take optional `page`/`pageSize` (no `pageSize` = all rows, used by selects); `GET /v1/admin/agents` lists the configured LLM (`beta-text`) and Laya (`gamma-decision`) agents with a live `/health` probe.
- `packages/core` ports added for that: `HistoryStore` (in-memory default; SQLite impl in the orchestrator), `UsageRecorder` (called per model call), and `RunPlanOptions.tracer` emitting `PlanTraceEvent`s.
- **Dependency versions live in the root `package.json` `workspaces.catalog`** (Bun catalogs): `elysia`, `zod`, `@t3-oss/env-core`, `drizzle-*`, `@sinclair/typebox`, `consola`, `typescript`, `@types/bun`. Workspaces reference them as `"catalog:"` — bump a version once, in the root. TypeScript is 6 everywhere (the root's own devDependency stays 7); TS 6 no longer auto-includes `@types/*`, so every tsconfig that uses Bun/Node globals needs `"types": ["bun"]`.
- `packages/elysia-kit` (`@repo/elysia-kit`) — the shared Elysia setup, used by `alpha-orchestrator`, `gamma-decision` and `admin-api` (not by `telegram-bot`, which is GramIO). `createKitApp({ observability, docs? })` = request logging (`requestLog`: one JSON line per request — method, path without query, status, duration, `x-request-id`; never bodies) + Sentry (`createMonitoring`, opt-in via `SENTRY_DSN`, reports only server faults, `isServerFault`) + `GET /health` + optional Swagger UI (`docs()` wraps `@elysiajs/openapi` with `provider: "swagger-ui"`; it replaced `@elysiajs/swagger`). `onRequestGuard(logger, decide)` + `hasBearer` do auth in `onRequest` **and** log the rejection (Elysia skips every other hook for a request rejected in `onRequest`, so a plain 401 there is never logged). `serve(app, { port, observability, onShutdown })` = `listen` + SIGINT/SIGTERM graceful shutdown + uncaught-error handlers. `retryFetch` is the outbound retry policy (idempotent methods only, backoff with jitter, `Retry-After`) — Elysia has no server-side "retry" plugin, this is for server-to-server clients (`admin-api`'s orchestrator client uses it). `observabilityEnv` (zod, `LOG_LEVEL`/`SENTRY_DSN`/…) is spread into each app's `createEnv`; apps set `emptyStringAsUndefined: true` so `SENTRY_DSN=` means off. `packages/core`'s own `telemetry.ts` still has its own `jsonReporter` (the typed LLM-event logger); the kit's logger is for HTTP services.
- **`apps/admin-api`** — the whole server side of the admin panel, an Elysia app (`/api/*`, Swagger UI at `/api/docs`, `/health`). It owns the admin accounts (**better-auth**, email+password, in its own SQLite — never in the orchestrator DB: with no admin `GET /api/session` says `setupRequired`; after the first `POST /api/auth/register` public sign-up is closed at the API level and further admins are created by an admin via `POST /api/admins`), the orchestrator client (`ADMIN_API_KEY` + `X-Admin-Id` = the signed-in admin's id on every mutation; failures map to 404/502/503 `{ message }`), and the host probe (`/proc`, `/sys/class/drm` → `GET /api/system`). Wire types are **TypeBox** (`src/schemas/`; account DTOs derived from the Drizzle table with `drizzle-typebox`), validated on every response; zod is only for env. `src/types.ts` is the only thing `apps/admin` imports (types only). better-auth is wrapped, not mounted: explicit `POST /api/auth/login|register|logout` return error **codes** (`weak_credentials`, `registration_closed`, …), never UI text; business rules (`admin-policy.ts`: no self-ban, no banning the last active admin, min password 8) run server-side. Auth is a macro (`{ admin: true }` in a `.guard`), CSRF defence is an `Origin` check on state-changing methods (`ADMIN_TRUSTED_ORIGINS`, both `localhost` and `127.0.0.1`). Local dev: `bun --cwd apps/admin-api run dev` (port 3003); its `.env` — copy `.env.example`.
- **admin-api accounts and streams**: the **super admin** is derived, not stored — the earliest-created account (`superAdminId` in `db/index.ts`, `isSuper` in `/api/session` and `/api/admins`). Only the super deletes admins (`DELETE /api/admins/:id`; codes `not_super`, `self`), nobody else can ban the super or change their password (`super_protected`). `GET /api/admins` and the orchestrator lists take `page`/`pageSize`. `GET /api/system/stream` is a WebSocket (session cookie at upgrade, its own `Origin` check — a WS upgrade is a GET and skips `foreignOriginRejection`) pushing `SystemSnapshot`s from `system/feed.ts`, whose single timer runs only while ≥1 client is subscribed (`SYSTEM_STREAM_INTERVAL_MS`, default 5000); `GET /api/system` stays for the first paint. `GET /api/agents` proxies the orchestrator's agent list.
- `apps/admin` — Svelte 5 admin panel (shadcn-svelte, TanStack Table v9 for every table, `@humanspeak/svelte-virtual-chat`, `@xyflow/svelte` for GOAP run graphs) as a **static SPA: SvelteKit with `adapter-static` (`fallback: index.html`), `ssr = false`, and no server code at all** — no `hooks.server`, `+page.server`, `+server`, `$env/dynamic/private`; the build output is plain files. It talks to `apps/admin-api` through the typed Eden client (`$lib/api/client.ts`, types derived from `admin-api`'s `App`): **Data is TanStack Query (`@tanstack/svelte-query` v6, see the next bullet)**; `load` functions in `+page.ts` only parse the URL and `prefetch()` queries into the cache (a failure becomes the error page, 401 → `/login`, via `throwAsPage`); the root `+layout.ts` fetches `GET /api/session` with `staleTime: 0` on every navigation and applies `resolveAuthRedirect` (first run → `/register`, signed out → `/login`); forms are not form actions any more — `useActionEnhance({ run })` (`$lib/components/use-action-enhance.ts`) is a `use:` action that runs a handler from `$lib/actions.ts` as a `createMutation`, toasts the result and invalidates every cached query (`queryClient.invalidateQueries()`; the ones on screen refetch). Signing in/registering empties the cache (`startsSession` in `actions.ts`), so a new session never sees the previous one's data. One-time channel keys are held in `issued-secret.svelte.ts`. **Same origin for `/api`**: Caddy (`Caddyfile`, prod) or the dev-only `vite/dev-api-proxy.ts` (dev, `ADMIN_API_URL`, default `http://localhost:3003`) forwards it, so the session cookie needs no CORS. `/performance` charts p50/p90/p99 from `GET /api/performance`; `/recommendations` (Lighthouse-style: `src/lib/system/audit.ts` scores the host against `IDEAL_MACHINE` = 100) runs client-side on the cached system snapshot; the header meter shows the same snapshot, kept current by the `/api/system/stream` WebSocket.
- **`apps/admin` table/actions conventions**: every table is `DataTable` (`lib/components/data-table.svelte`): 10 rows per page (`DEFAULT_PAGE_SIZE`, `lib/pagination.ts`) — client-side by default, or the server's own pages via its `server` prop (`?page=` in the URL, `parsePage`) for DB-backed lists (users keep their cursor pager); long cells are cut with an ellipsis, wide tables scroll sideways. Row actions are bright `IconButton`s (tooltip = accessible name; tones primary/success/warning/danger), deletes and key rotation go through `ConfirmDialog`; some tables can create but not delete (channels: disable only). Keys, ids and URLs get a prefix copy icon via `CopyValue`/`CopyButton` (`lib/clipboard.ts`). The header meter (`system-meter.svelte`) shows green/yellow/red badges (`lib/system/load-level.ts`: <70 / 70–90 / ≥90, an integrated GPU is judged by GTT) fed by the `/api/system/stream` WebSocket (`use-system-snapshot.svelte.ts`, runed's `IsDocumentVisible`: the socket is closed while the tab is hidden). `runed` is the utility library of choice for Svelte reactivity helpers. The dev proxy (`vite/dev-api-proxy.ts`) also tunnels WebSocket upgrades on `/api/*` (Caddy does it natively).
- **Live admin pages** (`GET /api/live`, one multiplexed WebSocket per tab; protocol in `apps/admin-api/src/live/protocol.ts`, `LiveTopics` maps each topic to the exact body of its REST endpoint). The browser subscribes per page (`subscribe {id, topic, params}` / `unsubscribe`), the server-side hub (`src/live/hub.ts`, topics in `topics.ts`, shared fetchers in `fetchers.ts` that the REST handlers also call) keeps ONE poll timer per `topic+params` group while it has subscribers (intervals: dashboard/users 5 s, user 3 s, channels/blocked-ips/admins/agents 10 s, performance 15 s), sends a snapshot on subscribe and afterwards only when the payload's hash changed (`upstream` error once per outage). Client: `apps/admin/src/lib/live/` (`live-client.ts` — lazy socket, closed while the tab is hidden or nothing is subscribed, resubscribes on reconnect; `use-live-query.svelte.ts` — `useLiveQuery(topic, params)` = an ordinary `createQuery` for the topic plus `bindLiveTopic` (`lib/query/live-cache.ts`), which writes every push into the same cache entry with `setQueryData`; an equal snapshot keeps the cached object). It swaps DATA, it never re-runs `load` or reloads the page (scroll, inputs, selections survive). Verified in a browser: 0 frames during 13 s idle, a new row appears ~4 s after the DB change, unsubscribe+subscribe on navigation, both sockets closed while hidden. The header meter still uses its own `/api/system/stream`. **Connection toasts** (svelte-sonner): sources report raw up/down to `reportConnection(problem, source, down)` (`lib/live/connection.ts`) — the live socket and the system socket (`onStatus`), each subscription's `upstream` errors, and every HTTP request through the Eden client (`lib/api/report-connection.ts`, `withConnectionReport` wraps the `fetcher` in `createApi`: no answer → `socket` problem, 502/503/504 → `upstream`, aborts ignored). `connection-monitor.ts` debounces (2 s, so a quick reconnect is silent) and announces state changes only; `layout/connection-toasts.svelte` (mounted in `(app)/+layout.svelte`, ru/en/kk) shows one persistent error toast per problem and a short "restored" toast. Verified in a browser: killing admin-api → toast after ~2 s, restart → restored; killing the orchestrator → "server isn't responding" via both the socket and a failed `load`. Testing gotchas: SIGTERM on admin-api does NOT drop open sockets (graceful shutdown waits for them) — use `kill -9` to simulate an outage; the "restored" toast lasts 3 s. Gotchas: Elysia sends a `message` handler's return value to the client (never `return ws.send(...)`); an admin-api **image is not rebuilt by editing source** — after backend changes run `docker compose up -d --build admin-api` (the panel then showed "WebSocket connection interrupted": the old image answered 404 for `/api/live`); parallel forks running `bun install` can leave `apps/admin/node_modules` half-populated (`svelte-kit: command not found`) — rerun `bun install` at the root.
- **`apps/admin` data layer — TanStack Query** (`src/lib/query/`). One `queryClient` per tab (`client.ts`; `QueryClientProvider` in the root `+layout.svelte`; the SPA is client-only so `load`, components and the socket feeds share it). Defaults: `staleTime` 30 s, no refetch on window focus (the sockets cover it), `retry` = `shouldRetry` (`retry.ts`: never on 4xx, once otherwise); `prefetch()` in `load` uses `retry: false` so a dead server shows its error page at once. `queries.ts` has every query: `liveQueries.<topic>(params)` (key = `topicKey(topic, params)` from `keys.ts`, `staleTime: Infinity` — the WebSocket keeps it current) and `queries.*` (session, system, allChannels for the forms' selects, goapActions, run). Query functions call the Eden client through `unwrap()` (`api/result.ts`), which throws `ApiError(status, body)`; **because every request goes through `api()`, `withConnectionReport` sees all query traffic**. Pages read with `useLiveQuery(...).current` / `createQuery(...)` + `prefetched(query)` (data the `load` guarantees). The host snapshot is the `["system"]` query fed by `/api/system/stream` (`use-system-snapshot.svelte.ts`); the recommendations page audits that same cached snapshot. **Devtools** (`@tanstack/svelte-query-devtools`, button bottom-left) are mounted in the root `+layout.svelte` behind `{#if import.meta.env.DEV}` with a dynamic import — gating with `dev` from `$app/environment` still left the devtools chunk in the production build (checked with `grep tsqd build`), `import.meta.env.DEV` removes it. After adding a dependency, `vite dev` needs `rm -rf apps/admin/node_modules/.vite` + restart ("a new version of the pre-bundle"). Gotchas: `queryOptions` is exported by `@tanstack/svelte-query`, **not** by `@tanstack/query-core`; pure modules that bun tests import (`client.ts`, `keys.ts`, `live-cache.ts`…) must import from `query-core` (svelte-query's entry pulls in `.svelte` files), while `queries.ts` and the hooks use svelte-query; the panel's queries use the global `window.fetch`, so in **dev** SvelteKit prints one "Loading … using `window.fetch`" warning per first fetch inside a `load` (harmless with `ssr = false`, absent in production builds; only the per-navigation session call uses kit's own `fetch` to keep that quiet).
- **`apps/admin` i18n (Intlayer, ru default / en / kk).** Every UI string lives in a `*.content.ts` dictionary (`t({ ru, en, kk })`, `insert()` for params; `strictMode: "strict"` makes a missing language a type error) next to its components under `src/lib/components/<feature>/`; pages under `src/routes` only compose those components. No URL prefixes (`routing.mode: "no-prefix"`): the locale is Intlayer's `INTLAYER_LOCALE` cookie → the browser's languages → ru, resolved on the client (`src/lib/i18n/browser-locale.ts` → `locale.ts`) in the root `+layout.ts`, and `setupIntlayer(data.locale)` is called **synchronously** in the root `+layout.svelte` (not in `$effect`), before any child calls `useIntlayer`. `admin-api` stays language-neutral: it returns error **codes** (`{ error: "weak_password", min: 8 }`) that the client localizes; `$lib/system/audit.ts` returns ids + variants + raw facts, never text. Numbers/dates/ms/GB go through `useFormat()` (`$lib/i18n/format.ts`, Intl-based — units come from Intl, not dictionaries). TanStack column headers must be functions (`header: () => $content.x.value`), not strings, or they won't follow a locale switch.
- `apps/snake-benchmark` — an experiment, not a service (no Dockerfile, not in compose): Laya drives Snake to measure decision latency on this hardware, ported from mizorewww/laya-mlx's MLX/Apple-only Snake demo (Apache-2.0). ## Architecture

Turborepo monorepo (Bun workspaces), hexagonal style. **Naming**: the project is PleiadesOrchestra
(Overlord reference) — each agent-shaped service is named after a Pleiades Six Stars maid with a
greek-letter role prefix: `apps/alpha-orchestrator` (formerly `apps/harness`), `apps/beta-text`
(formerly `apps/albedo` — Yuri Alpha/Lupusregina Beta/Narberal Gamma are the in-lore names, "albedo"
the character/persona and "laya" the model stay as informal names in prose below, only the *paths*
changed). See `docs/harness-goap-orchestrator-plan.md`'s "Ребрендинг" section for the full mapping
and rationale.

- `packages/core` (`@repo/core`) — LLM client library: Vercel AI SDK, OpenAI-compatible provider pointed at `albedo` (served by `apps/beta-text`), bounded per-thread conversation memory, structured telemetry. Exposes a single `Agent` port (`handleMessage`/`resetThread`). No transport-specific code, and no HTTP server of its own — it's a library, imported by `apps/alpha-orchestrator`, not deployed standalone.
- `apps/alpha-orchestrator` (formerly `apps/harness`) — the actual orchestrator service: an Elysia app (`POST /v1/messages`, `POST /v1/threads/:id/reset`, `GET /health`), served via `.listen()` (Elysia wraps `Bun.serve` internally — still no Express), and the *only* consumer of `@repo/core`. Normalizes incoming text with `transferum` (pure operator-composition pipeline — see the `transferum` skill for the library's patterns) before it reaches the LLM, then calls into `@repo/core` to talk to `albedo`. Auth is a manual `Authorization: Bearer <HARNESS_API_KEY>` check in an `onRequest` hook, not the `@elysiajs/bearer` plugin (see Lessons learned for why) — `/health` is exempted by pathname, unauthenticated. `createApp(deps)` in `src/server.ts` returns the Elysia instance; tests call `app.handle(request)` directly (Elysia's own recommended unit-test pattern), no listening port needed. Conversation history, users and usage live in its SQLite DB (see the users/access section above). `POST /v1/messages` already runs through the GOAP planner (see the GOAP section above); the planner code itself lives in `packages/core/src/goap/`.
- `apps/telegram-bot` — GramIO adapter (webhook, not long polling — avoids "Conflict: terminated by other getUpdates request" whenever the process restarts). Thin: asks the orchestrator's `POST /v1/access` whether the sender is allowed (silent if not) + forwards to `apps/alpha-orchestrator` over HTTP (`HARNESS_BASE_URL`/`HARNESS_API_KEY`, env var names unchanged by the rename). No LLM/memory/normalization logic of its own — all of that now lives in `apps/alpha-orchestrator`.
- `apps/cli` (`albedo` command) — a Bun CLI on `@bunli/core`, another thin `apps/alpha-orchestrator` HTTP client (same `HARNESS_BASE_URL`/`HARNESS_API_KEY` contract as `apps/telegram-bot`; duplicates its own small `harness-client.ts` rather than sharing one, matching the sibling-apps-are-independent pattern here). Two subcommands: `send -m "text" [-t threadId] [-u userId]` (streams the NDJSON reply to stdout) and `reset -t threadId`. `@bunli/core` has **no default/root command** (see Lessons learned) — there's no bare `albedo -m "text"`. Install with `bun link` from inside `apps/cli`, then run via `bunx albedo send -m "..."`; without linking, `bun --cwd apps/cli run start send -m "..."` works too. `send` prints a usage line to stderr after the reply: time-to-first-token (measured client-side, no server support needed), tokens/sec, and — only if the `LLM_CONTEXT_SIZE` env var is set to the model's actual `n_ctx` (there's no auto-discovery; must match what `albedo` is configured with) — tokens used out of the context window. The underlying `AgentStreamEvent`'s `done` variant (`packages/core/src/types.ts`) carries `elapsedMs`/`inputTokens`/`outputTokens` for this — any consumer of `@repo/core`, not just the CLI, gets it.
- `packages/pleiades-widget` — the site chat widget: a framework-agnostic `<pleiades-chat>` web component (launcher in a corner, default bottom-left, + side panel) that talks to the public Widget API (`docs/admin-api.md`). **Hard budget: 10 kB brotli**, checked by `size-limit` inside `bun run build` (~5.3 kB now) — so it is vanilla TSX on a tiny own JSX factory (`src/ui/jsx.ts`), PostCSS-compiled nested CSS (`postcss.config.js`), no framework. Dead ends: an empty Svelte 5 custom element is ~11 kB brotli (Svelte 4 ~2.6 kB, but the user chose vanilla), `@humanspeak/svelte-virtual-chat` isn't needed (the server keeps ≤10 messages per visitor). Layers: `src/lib` (UI-free, unit-tested: config validation, session store, API client, chat controller), `src/ui` (small components returning DOM + `render`/`setOpen` handles), `src/element.ts` (attributes → lib + ui). Security: only the publishable `pk_` key is accepted (`sk_` is refused), `https` only except localhost, credentials omitted, text via `textContent`; an origin the channel doesn't allow surfaces as a network error (403 without CORS headers). ## Workflow

- **Test-first**: write the test before the implementation, then make it pass. Don't write code without a failing test first.
- **Don't test the library, test your code**: for zod/t3-env schemas, only test transforms/logic you actually wrote (e.g. a custom `.transform()`). Don't write tests asserting that a required field throws when missing, or that `.url()` rejects a bad URL, or that `.default()` applies — that's testing zod, not the app.
- **Env validation**: use `@t3-oss/env-core` + `zod` for environment variable parsing/validation. Do not use `env-var`. Don't build the `createEnv(...)` singleton at module top-level in a file that's also imported by tests — it eagerly reads `process.env` and breaks importing the module under test env. Split: a pure `buildConfig(env)` factory (testable) in one file, and a thin `export const config = buildConfig(process.env)` singleton in a separate file that only runtime code imports.
- **Lint/format**: Biome (`biome.json` at repo root, tabs + double quotes). `bun run lint` (turbo, per-package), `bun run lint:fix` / `bun run format` at the root for the whole tree.
- **Production build for Bun apps**: `bun build ./src/index.ts --compile --target=bun-linux-x64-musl --outfile dist/<name>` produces a real standalone binary (Bun runtime embedded, no `node_modules` needed at runtime) — don't assume this won't work because of dependencies; it does, even for apps with several npm deps. The musl target lets the final Docker image be a plain `alpine` base. That binary still dynamically links `libstdc++`/`libgcc` (same as the `llama-server` binary in the root Dockerfile) — install those two packages in the final Alpine stage or it'll fail with relocation errors.
- **On failure or architecture change**: when something breaks, a real lesson is learned (wrong assumption, dead end, limitation discovered the hard way), or the architecture is changed, record it in this file at the end of the task so it isn't repeated.
- Don't create files/scaffolding outside what's explicitly asked for in the current task.
- **Delete confirmed-dead code/infra**: once something is established as no longer going to be used, it's fine and preferred to actually delete it rather than leaving it lying around "just in case". Don't let confirmed dead ends linger.

## Lessons learned

- IronClaw (nearai/ironclaw) cannot work with small self-hosted CPU-only LLMs: its agentic harness bundles ~15000 tokens of compiled-in system skills (32 skills, unconditionally seeded at onboarding, not removable via env vars, config.toml, CLI, or direct file/DB edits — they're compiled into the binary) plus a hard ~30s internal timeout on LLM calls. A 1B model on a few CPU cores can't process that much prompt in time. Don't try to force IronClaw onto a small local model again — use the custom hexagonal core/adapter setup under `packages/core` + `apps/*` instead (see `docs/telegram-bot-plan.md`). The experiment (service, volume, `ironclaw/` dir) was deleted for good on 2026-08-03 — don't recreate it.
- `railway service delete` does **not** delete a volume attached to that service — it's left behind, orphaned (`Attached to: N/A`). Delete it separately with `railway volume delete -v <volume-name>`.
- A monorepo-wide `.dockerignore` that excludes `bun.lock` (added for the root llama.cpp `Dockerfile`, which doesn't need it) silently breaks any other Dockerfile in the repo that does a real `bun install` — Docker just reports the file missing from the build context. Keep `.dockerignore` generic (`**/node_modules`, `dist`, `.git`, `.idea`, `*.md`) and never exclude package-manager lockfiles.
- A bare `node_modules` line in `.dockerignore` does **not** reliably exclude nested `apps/*/node_modules` in this Docker/BuildKit setup — found 2026-09-23 when a stale local `apps/telegram-bot/node_modules` (untouched since 2026-08-03) leaked into a `COPY apps/telegram-bot apps/telegram-bot` build step and broke it (`cannot copy to non-directory: .../node_modules/@gramio/auto-answer-callback-query`), since the multi-stage build's own `bun install` had already populated a real directory at that path and the host copy collided with it. Fixed by changing the pattern to `**/node_modules`. Confirmed by reproducing with the stray directory present, removing it (build succeeds), then restoring it with the fixed pattern (still succeeds) — don't assume a bare directory-name pattern in `.dockerignore` matches at any depth without checking.
- When testing a Dockerfile locally by hand (not through `bun test`), remember `docker run -e VARNAME` only forwards a variable that is actually *exported* in the host shell. Sourcing a plain `KEY=value` `.env` file (`source .env`) does not export anything — use `set -a; source .env; set +a` first, or Bun's own auto-loading won't help since it's a different process.
- Don't reach for `pino` for low-volume apps (a personal bot, a few log lines a minute): it's built for high-throughput batched writes, its single-argument form does **not** accept a plain `{ write() }` object as a destination (silently falls back to real stdout instead of your test double — verified empirically, don't assume), and its pretty-printer (`pino-pretty`) alone pulls in ~25 transitive packages. `consola` (createConsola + a custom `ConsolaReporter`) does the same job with ~7 packages, and is trivially testable: pass an in-memory reporter object, no fake Node stream needed.
- `bun test` sets `NODE_ENV=test` automatically. `consola` lowers its default log level when it detects a test environment (via `NODE_ENV`), which silently drops `.info()` calls — including in application code under test, not just consola's own test suite. Anything that logs via consola and must not depend on environment (like telemetry) needs an explicit `level: LogLevels.info` (or higher) passed to `createConsola`, not the default.
- `bun install --frozen-lockfile` validates against the `package.json` of **every** workspace member in the lockfile, so a Dockerfile that copies only its own workspaces' `package.json` breaks as soon as any other workspace is added (`error: lockfile had changes, but lockfile is frozen` — it did, when `apps/cli`, later `apps/admin`, `packages/pleiades-widget` appeared). Fixed for good by `turbo prune <app> --docker`: every service Dockerfile starts with a `prune` stage (`bunx turbo@2.10.9 prune <app> --docker`), installs from `out/json` + `out/bun.lock` and builds from `out/full` — no per-workspace `COPY` lists, a new workspace needs no Dockerfile change. Consequence: an image contains only the workspaces its app depends on (`gamma-decision` has no `packages/core`); don't `COPY` other workspaces by hand.
- `curl --retry N` does not cover every transient failure — a mid-transfer connection reset (`curl: (56) Recv failure`) during `apps/beta-text/entrypoint.sh`'s ~770MB GGUF model download wasn't retried, and a plain retry restarts from byte 0 anyway. Fixed with `-C -` (resume) plus `--retry-all-errors --retry 10`; needed for any large download over a flaky link, not just this one.
- `llama-server` logs everything — including plain INFO lines (`I slot print_timing: ...`) — to **stderr**, with no flag to change that (`--log-file` writes to a file, not stdout). Railway (and most log viewers, historically the reason this was caught) classify severity by stream, not content, so every line showed up red/"error" in the dashboard despite being normal operational output. Fixed by appending `2>&1` to the `exec llama-server ...` in `apps/beta-text/entrypoint.sh` to merge stderr into stdout.
- `createOpenAICompatible` (Vercel AI SDK) silently drops token usage on streamed responses (`result.usage`'s `inputTokens`/`outputTokens` resolve `undefined`, no error) unless constructed with `includeUsage: true` — that's what makes it send `stream_options: { include_usage: true }` on the wire, which is what makes `llama-server` (and OpenAI-compatible streaming in general) include a trailing usage chunk at all. Set in `packages/core/src/agent.ts`'s `createOpenAICompatible(...)` call.
- Elysia's lifecycle hooks are order/scope-sensitive in a way that matters for auth. `.onBeforeHandle()` (and anything registered via `.use()`) only applies to routes declared *after* it in the same instance — that's how `GET /health` stays exempt from a later auth hook just by being declared first, no explicit path check needed. But body-schema validation (`t.Object(...)`) runs *before* `onBeforeHandle`, so an unauthenticated request with a missing/malformed body got a `422` validation error instead of the intended `401` — auth never ran. Fixed by moving the auth check into `.onRequest()` instead (runs pre-routing, before any body parsing/validation), with an explicit `pathname === "/health"` bypass since `onRequest` isn't scoped by declaration order the way `onBeforeHandle` is. Also skipped the `@elysiajs/bearer` plugin for this reason — it only decorates context inside the `onBeforeHandle`-scoped lifecycle, too late for this ordering requirement.
- When migrating `apps/alpha-orchestrator` (then still named `apps/harness`) off a hand-rolled `(request) => Response` to Elysia, first instinct was to normalize Elysia's error responses (`PARSE` → `400`, `VALIDATION` → `422` by default) back to the old hand-rolled plain-text `400`s via a global `.onError()`. Deleted that after checking: no consumer (`apps/cli`/`apps/telegram-bot`'s `harness-client.ts`) parses the error body or branches on the exact status code — both just do `if (!response.ok) throw new Error(...)`. Elysia's default `VALIDATION` body is also strictly more useful than the old `"Invalid body"` string (names the exact offending field). Don't reintroduce that normalization without a concrete consumer that needs it.
- Elysia auto-decodes dynamic path params (`:id` capturing a `%2F`-containing segment yields the decoded value in `params.id`) — don't add a manual `decodeURIComponent()` on top, that would double-decode. Verified empirically (`app.handle()` against a probe route), not documented explicitly on elysiajs.com's route/handler pages as of this writing.
- `@bunli/core` (used by `apps/cli`) has no default/root command — its `findCommand()` requires an exact positional match against a registered command name, with no fallback to "the only registered command" or the CLI's own name. A bare `albedo -m "text"` invocation isn't achievable with it; every call needs an explicit subcommand (`albedo send -m "text"`). Don't assume a single-command bunli CLI can drop the subcommand keyword.
- Laya (`mizorewww/laya-mlx`, `receptron/laya`) is not a chat LLM and isn't swappable with `Vikhr-Llama` behind one endpoint — it's an open-source, Jev-compatible "System-1" typed-decision model (state + typed `choice`/`score`/`noul` questions in, calibrated-probability answers out, no text generation). Its GGUF export is built by `ggmlc`, not llama.cpp, and fails to load in `llama-server`; the MLX build is Apple-Silicon-only. The viable path is `@receptron/laya`, which runs it via `onnxruntime-node` — a native N-API addon that needs glibc and doesn't bundle reliably into a `bun build --compile` standalone binary. Gave it its own sidecar, `apps/gamma-decision` (glibc `oven/bun:1` base, no `--compile`, plain `bun run`), instead of forcing it into `apps/alpha-orchestrator`'s musl/alpine `--compile` image. `packages/core` talks to it over HTTP via a new `DecisionAgent` port, same shape as the existing `Agent` port talking to `albedo`.
- Dropped Railway entirely (2026-09-23) in favor of local-only deployment on the actual target hardware (CPU-only, resource-constrained — see the GOAP orchestrator plan's hardware section). Deleted `apps/*/railway.toml`, the Railway-only `prod.test.ts` smoke tests (`test:prod` script, formerly in `apps/albedo`/`apps/telegram-bot`), and the VictoriaMetrics telemetry reporter (`createVictoriaMetricsReporter`, `VICTORIA_METRICS_*` env vars) — Sentry is the planned replacement for that observability gap, not yet wired in. `compose.yml` is now the only deployment path, not just a local-dev convenience. Historical Lessons-learned entries above that mention Railway are kept as-is — they're still factually accurate records of what broke back when Railway was in use, not claims about current infra.
- Elysia `t.Optional(t.UnionEnum([...]))` does **not** leave a missing field `undefined` — it fills in the enum's *first* value. Found in `apps/alpha-orchestrator`'s admin API: a user list request with no `?status=` returned only `allowed` users, and a PATCH omitting `accessMode` would have silently reset it. Use `t.Optional(t.Union([t.Literal(...), ...]))` for optional enums (regression-tested).
- `bun build --compile` does not embed drizzle's migrations folder — `migrate()` reads it from disk at runtime. `apps/alpha-orchestrator/Dockerfile` copies `drizzle/` into the final image and points `DATABASE_MIGRATIONS_DIR` at it; verified by running the built image against an empty volume.
- `apps/admin` needs TypeScript 6 (`@sveltejs/kit` and `svelte-check` only declare TS `^5 || ^6` peers) — which is why the whole repo moved to TS 6 via the catalog: with two TS versions Bun links **two copies of `elysia`** (peer-dep hashing), and Eden's `Treaty` rejects an `App` from the other copy ("types have separate declarations of a private property"). It has a nested `apps/admin/biome.json` (extends the root) that turns off unused-import/variable rules for `.svelte` files, since Biome can't see usages in markup.
- CSRF: `admin-api` refuses state-changing requests whose `Origin` isn't in `ADMIN_TRUSTED_ORIGINS` (no `Origin` = not a browser = passes). `localhost` and `127.0.0.1` count as *different* origins, so both are listed by default (`http://localhost:3002`, `http://127.0.0.1:3002`); opening the panel on another port/host means extending that list and `BETTER_AUTH_URL`. (Before the split this was SvelteKit's own CSRF check plus `csrf.trustedOrigins` in `vite.config.ts`.)
- `/proc` and `/sys` aren't namespaced by Docker: any container (e.g. `apps/admin-api`) reads the **host's** CPU (`/proc/cpuinfo`, `/proc/stat`), RAM (`/proc/meminfo`) and GPU load/VRAM/GTT (`/sys/class/drm/card*/device/*`) with no extra mounts. That's how the admin header shows host metrics — don't add a privileged sidecar or an orchestrator endpoint for it.
- `N_GPU_LAYERS=0 docker compose up beta-text` does **not** reach the container — compose only interpolates host env into `${...}` in `compose.yml`, and `beta-text` takes its env from `env_file`. A CPU-vs-GPU comparison run that way silently measured GPU twice; compare with a separate `docker run ... -ngl 0` container instead.
- A relative DB path in an `env_file` silently moves the DB **off** the mounted volume: `apps/admin/.env` (now `apps/admin-api/.env`) had `ADMIN_DATABASE_PATH=./data/admin.db` (right for bare `bun run dev`), which the compose `env_file` applied over the Dockerfile's `/data/admin.db` — inside the container that resolved to `/app/data`, the container layer, so every recreate wiped all admin accounts while the mounted volume stayed empty. Fixed by pinning `ADMIN_DATABASE_PATH: /data/admin.db` in compose `environment:` (which wins over `env_file`), like `alpha-orchestrator`'s `DATABASE_PATH`, and moving both DBs to host bind mounts (`./data/`). The same hit `apps/admin-api` again with `ADMIN_MIGRATIONS_DIR=./drizzle` copied into its `.env`: inside the container it resolved to nowhere and the compiled binary crashed on start with `Can't find meta/_journal.json`. So `apps/admin-api/.env` must not set `ADMIN_DATABASE_PATH`/`ADMIN_MIGRATIONS_DIR` (the defaults suit local dev) and compose pins both container paths. When adding a stateful service, set its data path explicitly in compose and check `docker inspect` mounts + where the file actually appears.
- `apps/admin`: every npm package goes in **`devDependencies`** — everything is bundled at build time and the runtime image is Caddy + static files, so there is nothing to install at runtime. (`bun add -d`; the old reason — SvelteKit externalizing `dependencies` from the Bun server build — is gone with the server.)
- The admin theme (tweakcn, in `src/routes/layout.css` — the file `components.json` points shadcn-svelte's CLI at) uses Oxanium, which has **no Cyrillic** at all; `--font-sans` is `"Oxanium Variable", "Exo 2 Variable", sans-serif` so ru/kk text (incl. Kazakh ә ғ қ ң ө ұ ү һ і, which live in Cyrillic-ext) falls through per glyph to Exo 2. Check Cyrillic + Cyrillic-ext coverage before swapping fonts. Fonts are self-hosted `@fontsource-variable/*`, not a CDN.
- shadcn-svelte's `Card.Content` (this "vega" style) is `flex flex-col` by default and tailwind-merge keeps it: `class="flex flex-wrap …"` still stacks children vertically — add `flex-row` explicitly.
- "Error 200" in `apps/admin` dev = the error page rendered for a **client-side** failure (the response itself was 200). Root cause found 2026-09-25: on any content change vite-intlayer rewrites *every* `.intlayer/dictionary/*.json`, and Vite sent one `full-reload` per file — 18–46 reloads within a second — so route modules failed to load mid-reload. Fixed by the dev-only plugin `apps/admin/vite/coalesce-intlayer-reloads.ts` (swallows per-file reloads under `.intlayer/`, sends one debounced `full-reload`; measured: exactly one reload per change). `hooks.client.ts` now logs the real client error to the console and the error page shows its message. Dependency changes (`bun add`/`remove`) while `vite dev` runs can still leave a tab in a broken state — restart the dev server then. Also: `pkill -f "<pattern>"` in a Bash call whose own command line contains that pattern (e.g. the restart in the same call) kills the calling shell — stop and start in separate calls.
- **Don't name variables in the root `.env` after standard OS variables.** Bun auto-loads the `.env` of its cwd, so the root `.env` leaks into *every* `bun`/`bunx` run from the repo root — including the MCP servers Claude Code starts via `bunx`. It had `TEMP=0.3` (llama-server's temperature), and `TEMP` is also the temp-dir variable, so bunx/Node wrote their caches into a `./0.3` directory in the repo (136 MB). Renamed to `LLM_TEMPERATURE` (root `.env`, `apps/beta-text` Dockerfile/entrypoint). The root `.env` still has other generic names (`PORT`, `THREADS`, …) that bun processes started in the root will see — keep that in mind.
- In `compose.yml`, `${VAR:?msg}` is evaluated for **every** service, including ones behind an inactive profile — a required var of an opt-in service (e.g. `gemini-mcp`'s cookies) would break plain `docker compose up`. Opt-in services use `${VAR:-}` and let the app refuse to start instead.
- The root `.dockerignore` excludes `*.md`; a Python package whose `pyproject.toml` declares `readme = "README.md"` can't build without it — re-include it (`!apps/gemini-webapi-mcp/README.md`). Also excluded: `**/.venv`, `**/__pycache__`. Versioned `ghcr.io/astral-sh/uv:<x.y.z>-python3.12-*` images are Debian **trixie** (no `-bookworm` variant for pinned versions) — pair with `python:3.12-slim-trixie` so the copied venv's interpreter path matches.
- Renamed the project to PleiadesOrchestra and the agent-shaped services to the Alpha/Beta/Gamma scheme (2026-09-23, same session as the Railway drop above): `apps/harness` → `apps/alpha-orchestrator`, `apps/albedo` → `apps/beta-text`, `apps/laya-api` → `apps/gamma-decision`. `apps/telegram-bot`/`apps/cli`/`apps/memory` are transport/infra, not "agents" in this scheme, so kept their names. Deliberately did **not** rename: env var names (`HARNESS_API_KEY`/`LLM_BASE_URL`/`LAYA_API_KEY` etc. — `LLM_*` was already generic, not albedo-specific, and renaming the rest would touch every `config.ts`/`.env` for no functional benefit), `harness-client.ts` filenames in `apps/cli`/`apps/telegram-bot` (still descriptive of what they talk to), the `albedo` CLI bin name in `apps/cli`, or the "Альбедо"/laya persona names in prose and system prompts (those are product/character identity, orthogonal to which directory serves them — Albedo canonically isn't even one of the Pleiades Six Stars maids, she outranks them, so the Beta rename is a service-identity choice, not a lore claim about the character). Compose volumes were renamed too (`albedo-models`→`beta-text-models`, `laya-models`→`gamma-decision-models`), which means one one-time model re-download on first `docker compose up` after this change — not data loss, the old volumes are just orphaned (same caveat as the Railway-volume lesson above; delete them by hand if reclaiming disk space matters: `docker volume rm <old-name>`). Ran `bun install` after the directory moves to relink workspace `node_modules` symlinks — required any time an `apps/*`/`packages/*` directory is renamed, not just this once.

- **Elysia + `t.Optional(t.UnionEnum(...))`** fills a missing field with the first value (see the orchestrator lesson above); `admin-api` hit it again with `accessMode` (an omitted PATCH field became `whitelist`). Use `oneOf()` (`src/schemas/common.ts`, a `t.Union` of `t.Literal`s) inside `t.Optional`, and `t.UnionEnum` elsewhere. Also: a `t.Union` typed as an *array* (`TLiteral[]`) breaks Elysia's response and Eden body typing — `oneOf` returns a tuple type on purpose.
- `app.handle(new Request("http://x/path"))` 404s on every route: Elysia slices the path at a fixed offset, so the host must be at least ~9 characters — use `http://localhost/...` in tests. Also `onAfterResponse` runs just after the response is returned (tests need a tick before asserting on logs), and a request rejected in `onRequest` skips all other hooks (`onAfterResponse`, `mapResponse`, `onError`).
- Vite's `server.proxy` did nothing for `/api` in `apps/admin` dev: vite-intlayer's dev middleware rewrites `req.url` to `/ru/api/...` before it, and SvelteKit's dev handler answers 404 for non-routes. `vite/dev-api-proxy.ts` is a first-in-list plugin that proxies by `req.originalUrl`. Also: `vite dev` may bind only `[::1]` (a browser resolving `localhost` to IPv4 gets "connection refused") — pass `--host 0.0.0.0` when testing from another tool, and after editing `vite.config.ts` check with `ss -ltnp` that a restart didn't leave two servers on the same port.
- `apps/pleiades-plugin` (a WXT browser extension, in progress) is excluded from the workspace (`"!apps/pleiades-plugin"` in the root `workspaces.packages`), so it's not in `bun.lock` or turbo. Its `postinstall: wxt prepare` needs its sources next to `package.json`, so it must stay out of any install that only has `package.json` files; remove the negation once it should build with the rest.

Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Use `bun test` instead of `jest` or `vitest`
- Use `bun build <file.html|file.ts|file.css>` instead of `webpack` or `esbuild`
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`
- Use `bun run <script>` instead of `npm run <script>` or `yarn run <script>` or `pnpm run <script>`
- Use `bunx <package> <command>` instead of `npx <package> <command>`
- Bun automatically loads .env, so don't use dotenv.

## APIs

- `Bun.serve()` supports WebSockets, HTTPS, and routes. Don't use `express`.
- `bun:sqlite` for SQLite. Don't use `better-sqlite3`.
- `Bun.redis` for Redis. Don't use `ioredis`.
- `Bun.sql` for Postgres. Don't use `pg` or `postgres.js`.
- `WebSocket` is built-in. Don't use `ws`.
- Prefer `Bun.file` over `node:fs`'s readFile/writeFile
- Bun.$`ls` instead of execa.

## Testing

Use `bun test` to run tests.

```ts#index.test.ts
import { test, expect } from "bun:test";

test("hello world", () => {
  expect(1).toBe(1);
});
```

For more information, read the Bun API docs in `node_modules/bun-types/docs/**.mdx`.
- Elysia hook scope again: hooks only cover routes declared *after* them, a `beforeHandle` on a `.ws()` route is typed to the route's response schema (can't return a 403 there), and a WebSocket upgrade is a GET, so the CSRF `Origin` guard (state-changing methods only) never sees it — `admin-api` checks `Origin` on the stream route itself. A fake `fetch` typed `typeof fetch` fails type-checks under Bun (the type also demands `preconnect`); use a narrow `FetchLike` type in tests.
- This Bun version ignores `bun --cwd <dir> <script>` for some subcommands (`bun --cwd apps/admin add …` → "Script not found", `run check-types` printed help): `cd <dir> && bun …` is reliable. Also, in zsh `echo == x` fails (`==` is an expansion) — quote it. `npx @sveltejs/mcp …` fails on the repo's `devEngines` (bun only); use `bunx @sveltejs/mcp svelte-autofixer <file>` to validate `.svelte` files.
- zsh: a loop variable named `path` is tied to `$PATH` — `for path in …` wipes the command search path (`command not found: curl`). Name loop variables anything else (`route`, `p`).
