# @repo/core internals

See root `CLAUDE.md` for monorepo commands, workflow, code style and repo-wide lessons.

## Overview

LLM client library: no HTTP server, no transport code. Consumed by `alpha-orchestrator`, `telegram-bot`, `cli` (Bun source import, `exports: ./src/index.ts`). `src/index.ts` is the public surface. Inside the package (`src/`, `eval/`) import through the alias `#core/<path under src>` without `.ts` (`package.json` `imports`: `"#core/*": "./src/*.ts"`; a folder is `#core/goap/index`).

HTTP model calls go through the Vercel AI SDK: `ai`, `@ai-sdk/openai-compatible` (chat/reply model on `beta-text`), `@ai-sdk/typesafe-ai` (decision models via `experimental_decide`, talking to `gamma-decision`). Versions are pinned **exactly** in the root catalog because `experimental_*` APIs change in patch releases.

## Ports and adapters

- `Agent` (`agent.ts`, `createAgent`) — `handleMessage` / `resetThread`; text model; optional `temperature` (unset = nothing sent, server default).
- `DecisionAgent` (`decision-agent.ts`, `decision-types.ts`) — typed questions to `gamma-decision` or any Laya server; `modelId` (default `laya`) is the request-body model.
- `FunctionCallAgent` (`function-call-agent.ts`) — json_schema-constrained argument filling on `delta-function-call` or Ollama; config `temperature` (default 0) and `providerOptions` (e.g. `{ reasoningEffort: "none" }` -> wire `reasoning_effort`; a literal `reasoning_effort` key gets overwritten); helpers `repair-arguments.ts`, `validate-arguments.ts`, `ground-arguments.ts` (also drops keys the schema lacks: a provider that ignores `json_schema` wrote `query` for a size tool).
- `laya-calibrate.ts` / `laya-fit.ts` / `laya-calibration.ts` — Laya's confidence refitted on our data: one temperature per (question type x option-count bucket), applied to returned probabilities (`calibrate`, `withCalibration(agent, LAYA_CALIBRATION)`; argmax never changes, a bucket not in the table keeps the shipped one). `bun run calibrate` fits from `eval/data/laya-*.json` (NLL, k-fold, held-out ECE, coverage at the threshold) and rewrites `laya-calibration.ts`; collect data with `bun eval/collect-intents.ts` and `bun laya --samples` (apps/benchmark). `decideInRounds` returns the winner's `probability` (lowest over rounds) -> `IntentVerdict.confidence`. Numbers: `apps/docs/content/en/drafts/lessons-learned.md`.
- `choice-rounds.ts` — `decideInRounds` / `planChoiceRounds`: a `choice` question with many options is asked in rounds (≤10 options and ≤192 estimated tokens each; the winner of a round is the last option of the next). Laya shares one 192-token `head_max_len` between all options (over it, options and instructions are silently cut) and uses temperature 0.1 from 11 options (probabilities saturate). A question that fits is one call. Used by the message-intent and tool-intent questions (2 calls each with the 11-12 intents).
- `HistoryStore` (`history.ts`), `ConcurrencyLimiter` + `withConcurrencyLimit` / `withDecisionConcurrencyLimit` (`concurrency-limiter.ts`) wrap agents, `withTimeout` (`timeout.ts`), `recordCall` (`record-call.ts`, single reporting path: telemetry line + `llm_calls` row), `telemetry.ts` (`logMessageEvent`/`logLlmState`, OpenTelemetry GenAI field names, JSON to stdout).

## GOAP (`src/goap/`)

`plan.ts` (planner, priority queue in `heap.ts`), `executor.ts` (`runPlan`, reconciles actual vs expected effects), `text-action.ts`, `decision-action.ts`, `webmcp-actions.ts`, `tool-source.ts` + `mcp-client.ts` (MCP-backed `ToolSource`), `world-state-store.ts`, `run-lock.ts`. `WorldState` is a flat key->value fact bag; actions declare preconditions/effects. Intent logic: `message-intent.ts`, `intent-taxonomy.ts` (a `Taxonomy` of the channel's presets, the shop's by default; the data, word rules and tool-name rules live in `packages/intent-presets`, one folder per preset), `intent-memory.ts` (shop-domain layer, see root "Domain"). `tool-choice.ts` (`chooseTool`; `askedOptions`: a question about a changing tool's enum options is answered from the schema): the no-set mode. Orchestrator-side wiring and the intent pipeline: `apps/alpha-orchestrator/CLAUDE.md`.

Enum parameters (`createParameterChoiceAction` in `webmcp-actions.ts`): every string enum of a tool gets a `choose:<tool>.<param>` step, a precondition of the tool via `param:<tool>:<param>`. Required: nothing said -> the first option; one extra option `not_in_list` (asked for something the list lacks, «tomatoes» on an emoji topping list): the step writes `missingParams` with `options` + `notInList`, the tool is not called and the reply offers the list (the visitor wait then redoes the choice: the checkpoint drops `parameterFlag(tool, param)`). Optional: one extra option `not_said` (never sent to the site); `not_said`, a probability under 0.5, or a failed call leave the parameter unset, and the step still sets its flag so the tool is never blocked. A value already in the state is kept. `withChoiceReport` (`usage-collector.ts`, outermost decision agent) hands every choice answer with all its probabilities to the surrounding `collectTokens`, and the call's `LlmCallRecord.choices` carries them to the ledger.

**Several things in one message («buy A, B and C»)** — `splitProductList` (`product-request.ts`) splits on `,`/`;`/«and»/«и» conservatively (a comma list ends at its last «and»; bare «A and B» only when both sides ≤2 words or the second starts with a count; `FIXED_PAIRS` like «mac and cheese» never split). The list travels as JSON-string facts (`shopping-list.ts`: `requestedItems`, `foundItems`, `missingItems`; named unlike tool parameters so `buildArguments` doesn't copy them); `query`/`quantity` stay the first item. One WebMCP wait is still one call, so `fan-out.ts` makes a search tool run once per item and an add tool that takes one product run once per found item: the cursor (`fanOut:<tool>`) and findings ride in `ActionResult.waiting.facts`, which the executor merges into the checkpoint. An add tool with a list parameter (found from the schema alone, `findListParameter`: array of objects with a string name field + integer count) gets everything in one call, filled by `buildArguments` without the function-call model.

**An action on every item of a list the site shows («очисти корзину», «remove everything»)** — same fan-out, the list comes from a tool's answer (`list-removal.ts`). A tool whose NAME reads (`get_/list_/view_…`) is intent `readState` (effect `listRead`; a tool role, never offered to Laya or as a message intent: `LAYA_INTENT_DESCRIPTIONS`). An edit tool whose schema says «0 removes» (`removesAtZero`) is `removeFromCart`. `asksForAll` (`message-cues.ts`, closed list) + `scopeFacts` write `scopeAll`; `bindListScope` then makes a remover that needs an item (`scopedPreconditions`) wait for `listRead` and keeps only the reader named closest to it (`get_cart` for `update_cart_item`); a remover with no required params (`clear_cart`) is untouched and wins by cost. `parseListedItems` reads every line of the answer (count «2 ×», price/size cut, leading `#id` = the entry's id) into `listedItems`; `removeEach` (`fan-out.ts`) calls the remover once per item, `removalArguments` fills the name field and the number that removes at 0 from the schema alone; a remover with a list parameter gets everything in one call. An answer that lists nothing and says «empty» ends the step truthfully (`listEmpty`); a list it cannot read fails the step. Limit: a site that removes only by an id its list answer does not show cannot be served. `goalForIntent` checks fact AND value (`inCart: false` was «producible» by add tools: the root of the old `no_plan`).

Commands: `bun --cwd packages/core test`; evals `bun run eval:intents`, `eval:tools`, `eval:choose-tool` (`chooseTool` per message on four demo sites; `DECISION_BASE_URL`/`DECISION_API_KEY`/`DECISION_MODEL`), `bench:plan` (in `packages/core`, cases in `src/goap/intent-cases.ts`).

## Lessons

- **Alias is `#core/*`, not `@/*` or `#/*`** — tsconfig `paths` apply only inside the package's own `bun check`: apps that import core by source fail on `@/` in their type check. `package.json` `imports` resolve per package everywhere, but Bun 1.4 does not resolve the bare `#/` prefix.
- **`createOpenAICompatible` needs `includeUsage: true`** — otherwise streamed token counts are `undefined` (it must send `stream_options: { include_usage: true }` to llama-server).
- **A failed GOAP run must not keep its full WorldState as checkpoint** — only a WAITING run keeps it; every other end keeps just `SESSION_FACTS` (stale `webmcp:*:result = "error"` once infected the next message). Enforced orchestrator-side.
- **IronClaw won't work with small local models** — ~15k token system prompt + 30s timeout. Use this custom core/adapter setup instead.
- Laya can't load in `llama-server`; see `apps/gamma-decision/CLAUDE.md`.

## Task decomposition

`goap/task-decomposition.ts`: `decomposeMessage` (delta, `{intent, text, after?}`), `looksLikeSeveralTasks` / `hasOrderWord` (language cues, no product words), `runnableTasks` (words confirm guarded intents, no-op and repeated `select` dropped), `mustAskOrder` (`tasksConflict` of `@repo/intent-presets`). The queue that runs the tasks is in alpha-orchestrator. `bun run eval:decompose`. `goap/understanding.ts` (alpha-understand): `translateTexts` (plain batch translation to English, `{texts: string[]}` same order, used by `english-only`); `understandMessage` (one `FunctionCallAgent` call: `{en, tasks:[{intent, text, items:[{name, quantity>=0}]}]}`; unusable -> `undefined`, unknown-intent tasks dropped), feeds the same `runnableTasks`/`mustAskOrder`; the prompt makes every count a digit in the English text (delta reads it there), `items[].quantity` stays the source of truth.

## Enum choice steps and `statedAttributes`

`createParameterChoiceAction` (`goap/webmcp-actions.ts`) reads the turn fact `statedAttributes` (JSON `{name, value}[]` from `understandMessage`; `matchingAttributes` in `goap/attribute-match.ts` is the lexical matcher, shortcut: embeddings would be needed when words do not overlap, upgrade when a site's params need it). Decision table: value already in state -> keep; fact absent (alpha-understand failed/off) -> ask gamma as before; attribute matches the parameter (name/description/enum values) -> ask gamma with "The visitor said: name = value"; no match and optional -> flag set, param unset, no call; no match and required -> ask gamma (nothing said = first option).

## Today, missing parameters, answering a question

`understandMessage` takes `{replyTo, history, today, pending}`: with `replyTo` (+ `history`, what was said before it, oldest first; `conversationContext` cuts both from the thread's newest messages) a short answer («да», «2», «the cheapest one») becomes the complete request in `en`, the rule sits in the `en` field's own line (below it the model kept translating «yes»); a refusal or a message that stands alone ignores the quote, and the message is labelled «NEW … write en for this one» (without the label voxtral swapped in the visitor's earlier question). `eval:answers` (36 cases: answer / topic change / long chain): last exchange 10/12, 18/18, 6/6; the whole chain the same; no context 7/12, 17/18, 4/6. The 2 answer misses are the word cue «order» = addToCart, not alpha; `today` ("Today is 2026-10-27 (Tuesday)") makes alpha write dates as `YYYY-MM-DD` and times as `HH:MM`; with `pending` ({request, asked}) the tool also returns `answersPending` (does the message supply what the assistant asked). Turn facts `TODAY_FACT`/`TIME_ZONE_FACT` reach delta through `factsForModel`. A tool step whose required arguments are still unfilled returns `toolResult:<tool> = false` plus the fact `MISSING_PARAMS` (JSON `{tool, params:[{name, description}]}`) and does not call the browser; the app turns that into a question to the visitor.
