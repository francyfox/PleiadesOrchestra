# wordpress-plugin internals

See root `CLAUDE.md` for monorepo commands, workflow and style. Plan: `docs/trust/drafts/wordpress-plugin.md`.

## Overview

WordPress plugin `pleiades-chat` (display name Pleiades Assistant; PHP 7.4+, GPLv2+; the bundled widget is BSD-3). Not a JS package apart from `build` and the tests of the tool logic.

- Tree (WooCommerce-style): `pleiades-chat/pleiades-chat.php` is a thin bootstrap (header, constants incl. `PLEIADES_SITE_URL`/`PLEIADES_PANEL_URL`, requires `includes/class-pleiades-plugin.php`); one class per `includes/class-pleiades-*.php`: `options` (the single option `pleiades_assistant`, defaults, `sanitize`, `languages()`, `fields()`, read from the generated `includes/widget-i18n.json`), `context` (page facts, prints `<pleiades-chat>`), `assets` (enqueue + `wp_add_inline_script` `window.PleiadesWp` before the core script; PHP never echoes JS), `recipes` (CPT, kits, `the_content`). `includes/admin/`: `class-pleiades-admin` (menu, plugin row links), `class-pleiades-settings` (Settings API, `manage_options`, nonce by `settings_fields`, tab router), `class-pleiades-settings-tab` (abstract), `settings/class-pleiades-tab-{general,localization}`. Both tabs post to the same option; `Pleiades_Options::sanitize` only touches a tab's fields when they were posted. `uninstall.php` deletes the option only (recipes and kit meta are site content). `languages/` is the Domain Path . `PLEIADES_DEFAULT_AGENT_URL` is the hosted service `https://albedo.shalotts.site`; `PLEIADES_TERMS_URL`/`PLEIADES_PRIVACY_URL` point at the site's legal pages. `readme.txt` has the mandatory "External services" and "Source code" sections: keep them true when what is sent changes.
- Localization tab (heading/greeting live only here, not on General): select `lang` (`''` = automatic, no overrides) + per language `l10n[lang][field]`. Languages and fields come from the widget's own `i18n.ts`: `bun run build` writes `includes/widget-i18n.json` (`scripts/i18n.ts`, committed; `includes/i18n.test.ts` fails when it is stale). Fields: `heading|greeting|placeholder|examples` -> the attributes of the same name (examples = JSON array from lines), every other text key -> the widget's `labels` attribute (JSON object merged over the locale dictionary, `parseLabels` in the widget, unknown keys dropped). Inputs show the widget default as placeholder; empty = default. Legacy top-level `heading`/`greeting` (before 0.5) stay in the option, are no longer edited, and fill in as fallback for the selected language (and are printed when `lang` is automatic). A new widget language/key needs only the widget change + a build.
- Admin UI is translated (text domain `pleiades-chat`, `languages/`): the build regenerates the `.pot` from the PHP literals, compiles `ru_RU.po` -> `.mo` with its own tiny compiler (no msgfmt needed) and fails if a string has no Russian. Edit `languages/pleiades-chat-ru_RU.po` by hand when adding a string (one-line msgid/msgstr pairs only). Links inside translated text: `sprintf` with a `%1$s` anchor (see the key help on General). Verify: `wp site switch-language ru_RU` (core language is installed), look at the page, switch back to `en_US`.
- PHPDoc on all PHP (WordPress inline-documentation standard): file docblock with `@package Pleiades_Chat`, a docblock per class/constant/method with `@since`, typed `@param`/`@return`; keep it in step when changing PHP.
- Renamed from `pleiades-assistant` (0.4.0): an installed old copy must be deactivated by hand, WordPress sees a new plugin; option, CPT and meta names did not change.
- `assets/js/tools-core.js` — pure functions on `globalThis.PleiadesWpCore` (tool list with schemas and annotations, argument to request mapping, nonce refresh, same-origin check, response shaping). Tested by `tools-core.test.ts` (`bun test`). Descriptions stay generic (any shop domain).
- `assets/js/tools.js` — browser wiring: fetch, `document.modelContext.registerTool`, mini cart refresh (`wc_fragment_refresh` + `wc/store/cart` invalidate), stale-nonce retry (403 -> `GET /cart` -> retry once).
- `assets/js/pleiades-widget.js` — copied from `packages/pleiades-widget/dist` by `bun run build` (git-ignored). `dist/pleiades-chat.zip` is the installable plugin.

## Recipes and kits (0.2.0)

- CPT `pleiades_recipe` (public, REST, archive `/recipes/`, activation flushes rewrites). Meta, all `show_in_rest`: `servings` (int), `time_minutes` (int), `ingredients` (array of `{sku, quantity, note}`). Kit = WooCommerce **grouped** product in category `kits` with product meta `_pleiades_kit` = JSON text `[{"sku","quantity"}]` (the grouped children hold the products, the meta the quantities). SKUs resolve to products at render time; a deleted product drops out.
- `the_content` filter on a single recipe/kit prints the ingredient list (recipes) and a hidden "Add all" button (`.pleiades-add-all`, `data-items`); `assets/js/tools.js` un-hides it and runs `addAll` (Store API, nonce retry). Without a widget key only core + tools load, on those pages, and `cfg.tools` is false so no WebMCP tool is registered.
- `window.PleiadesWp.recipes` / `.kits` (`{name, url, servings, time_minutes, items:[{id, name, quantity}]}`) feed `bundleTools(cfg)` in `tools-core.js`: `list_recipes`, `add_recipe_to_cart({recipe, servings?})`, `list_kits`, `add_kit_to_cart({kit})`; `recipe`/`kit` are enums of the names (core's "named options" picks them over `add_to_cart`). Servings scale quantities up (ceil); one failed item (out of stock) does not stop the rest and is listed under `missing`.
- Limit: all recipes/kits (max 100 each) are printed into every page. `bundles()` was ~270 queries per page, so it is cached in transients `pleiades_bundles_<type>` (1 h), cleared on `save_post`/`delete_post` of recipes and products (`flush_cache`) and in `uninstall.php`; a meta-only write without `save_post` (wp-cli `post meta update`) leaves it stale up to the TTL.

## Security notes

- The inline `window.PleiadesWp` is encoded with `JSON_HEX_TAG|AMP|APOS|QUOT`. Titles are shop data an Author can write (CPT uses `post` capabilities); on WP 7.1 core already escapes `<script` in inline scripts and Authors' titles are kses-stripped, so the flags are defence in depth for older WP.
- Password-protected recipes/kits are excluded from `bundles()` (`has_password => false`) and get no ingredient list (`post_password_required()`).
- Recipe meta is validated by the REST schema (`servings`/`time_minutes` 0..9999 + `absint`, ingredients max 100 rows, `quantity` 1..9999, `sku`/`note` max 200). REST creates the post before it rejects bad meta, so a 400 can leave a post behind.
- `Pleiades_Options::sanitize` takes untrusted POST values: every field must tolerate a non-string (PHP 8 `TypeError`). Tests: `apps/e2e/tests/wordpress/plugin/security.spec.ts`.

`window.PleiadesWp.pages` (cart, checkout, account URLs, WooCommerce only) go into the `open_page` description via `withPages` in `tools-core.js`, so the model knows where to send the visitor.

Without WooCommerce only `search_site`, `get_page`, `open_page` are registered. No checkout tool; `open_page` is same-origin only.

## Load order, navigation

- The widget installs the polyfill at mount and dispatches `pleiades:webmcp-ready` on `document`; `tools.js` registers immediately if `document.modelContext` exists, else on the event.
- Navigation (`navigateSoon` in `tools.js`, used by `open_page` and by `search_products` when it has hits: the shop results page, `searchPageUrl` in `tools-core.js`; no `on_sale` URL, WooCommerce has none): the tool returns first, sets `sessionStorage["pleiades-wp-open"]`, the reloaded page re-opens the panel and the widget restores the thread (`history()`, last 10 messages). **During a widget turn the navigation waits for `pleiades:turn-end`** (the widget dispatches `pleiades:turn-start` / `-end` on `document`; 60 s timer as the way out; outside a turn it goes after 50 ms; the last call wins). Reason: the next step of the server's run comes back on the response of the tool-result request, which a reload kills (the reload's `pending` check then answers "none" while the server is still planning, and the turn dies silently). Tools never throw to the caller: an error comes back as `{content, isError:true}` because Chrome's native WebMCP replaces a thrown message with "invocation failed". `product_id`/`productId` count as `id`.
- **Error contract (tool failures never carry the shop's text).** A failed tool returns `{content:[{text}], isError:true}` whose text is JSON `{error_code, status?, hint?}`: `error_code` is one of `ERROR_CODES` in `tools-core.js` (the same closed list as `TOOL_ERROR_CODES` in `packages/core/src/goap/tool-error.ts`; a test in `tools-core.test.ts` keeps them equal). Producers: `toolError(code, extra)` (thrown by `need` -> `MISSING_ARGUMENT` with `argument` + our own `hint`, `findBundle` -> `NOT_FOUND`, `open_page` -> `NOT_ALLOWED`), `codeFromResponse(data, status)` for a REST failure (maps the response's `code` field via `STORE_CODES`, read from real Store API answers; `rest_invalid_param` -> `INVALID_QUANTITY` when `quantity` is the bad param else `MISSING_ARGUMENT`; unmapped: 404 `NOT_FOUND`, 401/403 `NOT_ALLOWED`, else `UNKNOWN`), `errorPayload(e)` (the result; a `TypeError` from `fetch` is `NETWORK`, any other foreign error `UNKNOWN`). **The shop's `message` is never read or forwarded**; `hint` is OUR text for a calling model (orchestrator ignores it). `add_*_to_cart` bundle tools report `missing[].reason` as the code and `summarize` words it from the code. New WooCommerce `code` seen in the wild: add one line to `STORE_CODES` + a case in `tools-core.test.ts`; a new enum value: core list, core template, this list.

## Local WordPress + WooCommerce

```
bun run --cwd packages/wordpress-plugin build      # widget must be built: bun run --cwd packages/pleiades-widget build
docker compose -f compose.wp.yml up -d
```

`compose.wp.yml` is its own compose project (`pleiades-wordpress`), apart from the main stack. `wordpress-setup` (`dev/setup.sh`, wp-cli, idempotent) installs core, WooCommerce, the sample products (clothing with variations), activates the plugin and, if `WORDPRESS_PLEIADES_KEY` (+ `WORDPRESS_PLEIADES_AGENT_URL`) are set in the root `.env`, presets the settings. Site `http://localhost:8088` (`WORDPRESS_PORT`), admin / admin. Re-run setup: `docker compose -f compose.wp.yml up wordpress-setup`. The plugin dir is mounted read-only, so rebuild assets on the host.

PHP lint (no PHP on the host): `docker run --rm -v $PWD/packages/wordpress-plugin/pleiades-chat:/p php:8.3-cli sh -c 'for f in $(find /p -name "*.php"); do php -l $f; done'`.

Copy the wasmer demo shop (202 products with variations, kits, recipes; no images): `bun packages/wordpress-plugin/dev/pull-demo.ts [site]`, then `docker compose -f compose.wp.yml run --rm -T -v $PWD/packages/wordpress-plugin/dev:/dev-data:ro --entrypoint wp wordpress-setup eval-file /dev-data/import-demo.php` (~80 s, idempotent by SKU; the WooCommerce sample products stay next to it).

Theme: `WORDPRESS_THEME=kadence` (classic, free, from wordpress.org; cart/checkout become shortcode pages; setup builds a block+shortcode home page with hero, categories, sale and best sellers, a Primary menu and a header cart; Starter Templates import is not scriptable), `storefront` (classic) or `twentytwentyfive` (block, default: WooCommerce's block pages are recreated); rerun `wordpress-setup` to switch. Block vs classic is decided by `wp_is_block_theme()`, not by theme.json (Kadence ships one). Demo import sideloads product pictures from the source site's URLs in `demo-data.json` (8 s per file, 5 min cap, idempotent) and gives categories a product picture. The plugin is theme-independent; only the demo site changes. Not tested yet: caching plugins.

## Showing cart writes (`refreshCart` in `tools.js`)

- Classic: `wc_fragment_refresh` (mini cart), `update_checkout` (checkout order review), and on the shortcode cart page the `.woocommerce` block is re-fetched and swapped (`wc_fragment_refresh` does not touch the cart table; WooCommerce's own Update button does the same fetch).
- Block: `wc-blocks_added_to_cart` / `wc-blocks_removed_from_cart` events on `document.body` and `wp.data.dispatch("wc/store/cart").invalidateResolutionForStore()` (each alone refreshes the Cart/Checkout blocks; on pages without them `wp.data` is absent and the events reach the lazily loaded mini cart block).

## Tests

- Unit: `bun test pleiades-chat` (`assets/js/*.test.ts`: pure core and `tools.js` wiring with fake globals; `includes/i18n.test.ts`: generated i18n files are in sync).
- Browser (needs `make wp-up`, demo data; skip if WP is down): `cd apps/e2e && bunx playwright test wordpress` (specs in `apps/e2e/tests/wordpress/{plugin,tools,flows}`, helpers in `support/`). `tools/*` call every tool through `document.modelContext` (polyfill and, in `native-webmcp.spec.ts`, Chrome's own); `flows/` drives the widget with a scripted fake agent across real reloads. Block theme is the default; for a classic one run `WORDPRESS_THEME=kadence docker compose -f compose.wp.yml up wordpress-setup` first (the cart specs adapt).
