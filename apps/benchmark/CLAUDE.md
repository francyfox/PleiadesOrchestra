# benchmark internals

See root `CLAUDE.md` for monorepo commands, workflow, code style and repo-wide lessons.

## Overview

Every benchmark of the repo as one bunli CLI (not a service, not in compose). `bun start` shows a menu; `bun start <name>` or the script runs one directly (`--help` lists flags). Every bench writes to `results/<bench>/<timestamp>.<ext>` (gitignored; `resultPath` in `report/`), `--output` overrides the path (`snake` writes only with `--headless`).

- `bun tools` — delta (Qwen3-1.7B) argument accuracy on the complex cases: one request per kind of site, filled field by field (`fillOnce` from `@repo/core`, answer budgets 48 tokens for the "which optional fields" step, 128 per field). Shows request -> arguments with source words coloured by kind, then a table (all-fields accuracy, per kind, p50/p90, tokens, delta calls). `--laya` hands enums and booleans to Laya in one pass and delta fills the rest.
- `bun openrouter` — the same cases on hosted models behind OpenRouter, one column per model (`--models a/b,c/d`, default 4 cheap candidates; `OPENROUTER_API_KEY`). Routes with `provider.require_parameters` (only providers that honour `json_schema`); a model that fails shows 💥. A few cents per run. Hosted p50 was 2.8–5.2 s against ~840 ms of the local Qwen3-1.7B, accuracy tied at 17% on the 6 cases (keywords and query are the weak fields for every model).
- `bun laya` (module `choices`) — Laya accuracy on enum/boolean decisions alone (given / unsaid / refused), the share of `tools --laya`. `--samples file` saves every raw answer with its right answer (`packages/core/eval/data/laya-choices.json`) for `bun run calibrate` in core.
- `bun efficiency` — beta alone (the orchestrator's reply model through its `POST /v1/chat/completions` pass-through, so both sides have the same text model; the shop's tools in an AI SDK tool loop, `--max-steps`) against the orchestrator with beta, on a seeded faker mock shop (`efficiency.shop.ts`: the `McpClient` port of `@repo/core`, Basketful-shaped tools, any department) and 7 cases, each in English and Russian (`-ru`, product names stay English), judged only by the shop's state, never by the reply's words: the exact cart they leave, and for a question the product a search answer showed (`shown()`; `efficiency.cases.ts`). The orchestrator is driven as the widget drives it (visitor, thread per case, `/v1/widget/tools`, every `tool_call` run on the mock and posted to `/tool-results`); a warm-up message pays the catalog's one-time classification. Success, time, steps (model + tool calls), tokens, cost (each call at its model's OpenRouter price, `loadPrices`; a model not listed at `--price-in/--price-out` per 1M); `--runs N` (default 6) passes over all cases, the report shows averages and a setup block (models, temperatures). Writes as it goes, into one run folder `results/efficiency/<timestamp>/` (`--output` names it): `report.txt` (rewritten after every finished iteration with the averages so far; the header says `name: k/N iterations` and marks a partial report) and one pretty-printed `<iteration>-<case id>.json` per case run in `beta-alone/` and `orchestra/` (shop tool calls, cart, beta steps / the admin request details), so an interrupted run keeps everything done. Infrastructure failures (HTTP 5xx/429, network, 60 s timeout, error body in a 200, model unavailable; `efficiency.infra.ts`, 3 retries at 2/5/15 s) are recorded as `status: "error"` with `errorCategory`, apart from `ok: false` (the contender did the wrong thing): success and means skip them, the report has an `errors` row/column. Before starting it checks `GET /health` and one tiny completion; 5 error runs in a row stop the run (partial report, temperatures restored). `--concurrency N` (default 1) runs up to N case runs of one contender at once (contenders stay sequential); latency with N > 1 includes contention, and for the orchestra the widget's rate limits (`WIDGET_MESSAGES_PER_MINUTE` etc. in the orchestrator's env) must be raised, else it waits out 429s. Without `ORCHESTRA_ADMIN_API_KEY` the orchestrator's tokens are the reply model's only (the `done` line) and its temperatures stay as they are; with it, every `llmCalls` row of the request, and beta-text/delta run at temperature 0 for the bench (`efficiency.settings.ts` sets it through the admin API and restores the original configs in `finally` and on SIGINT/SIGTERM; a SIGKILL leaves 0 behind).
- `bun snake` — Laya latency playing Snake (live board or `--headless`); `--threads 1,2,4` compares onnxruntime threads in-process (`bun sweep`).

All three call Laya through `createDecisionAgent` (AI SDK `experimental_decide`): the server model when `LAYA_BASE_URL` is set, otherwise `laya/laya.model.ts`, an in-process decision model over `@receptron/laya`. Same code path either way; one pass and ignored `--threads` for a server.

## Structure

`src/index.ts` is the composition root (createCLI, commands, menu). Everything else is `src/modules/<name>/` with `<name>.<suffix>.ts`: `.command.ts` bunli command, `.ts` main factory/class, `.service.ts` pure logic, `.types.ts`, `.view.ts` terminal rendering, `.cases.ts` fixtures, plus `.model.ts` / `.server.ts` / `.prompt.ts` / `.fields.ts` where a module has more than one role. No barrels; factories `create*`/`load*` take a deps object.

- `config` — `buildConfig(env)` + `config.service.ts` singleton.
- `menu`, `report` (`accuracyMark`, `metricTable`, `pct`), `stats` (`summarizeLatency`, `summarizeRuns`, one percentile).
- `delta` — `DELTA_MODEL` (a test keeps it equal to delta's Dockerfile `MODEL_URL`), llama-server lifecycle in Docker (`startServer`/`connectServer`/`ensureModel`), `createDelta` (per-field filling), prompts (`delta.prompt.ts`, `delta.fields.ts`, `delta.service.ts`).
- `laya` — `loadLaya` (server or in-process), `createLayaModel` (the adapter; mapping unit-tested with a fake Laya), questions/answers <-> tool arguments (`laya.service.ts`).
- `tools`, `choices`, `snake`, `efficiency` — one folder per command: cases, judging, view, command. `SnakeGame` is the only class (stateful).

## Env (`apps/benchmark/.env`, see `.env.example`)

- `DELTA_BASE_URL` — a running Ollama/llama-server (root, with or without `/v1`); unset: `bun tools` starts delta's image in Docker. `DELTA_API_KEY`, `DELTA_MODEL` (Ollama needs the name, e.g. `qwen3:1.7b-q8_0`).
- `LAYA_BASE_URL` — the server root (client appends `/v1/systemone`), `LAYA_API_KEY`. Empty/unset: Laya loads in-process on CPU.
- `bun efficiency`: `ORCHESTRA_BASE_URL` + `ORCHESTRA_API_KEY` (HARNESS_API_KEY; beta alone), `ORCHESTRA_PUBLISHABLE_KEY` + `ORCHESTRA_ORIGIN` (a web channel and one of its allowed origins; without them only beta alone runs), optional `ORCHESTRA_ADMIN_API_KEY`.

## Notes

- CPU by default, 4 threads. `tools --gpu` offloads to Vulkan, meaningful only where the whole model fits in VRAM (the dev iGPU has 0.5 GB).
- Cases are English only (the translator runs before delta/Laya in production; `efficiency` also has Russian twins, it goes end to end through the translator) and vary the domain (CLAUDE.md "Domain: not one shop"): extend with other domains before trusting 100% figures.
- Reference numbers (6 complex cases, Ollama `qwen3:1.7b-q8_0`): all fields ~33%, p50 ~840 ms; with `--laya` ~17%, p50 ~640 ms. `bun laya` on a GPU server: 64/87 decisions, p50 ~33 ms; the same weights in-process on 4 CPU threads: same accuracy, p50 ~400 ms.
- Qwen3 in Ollama ignores `chat_template_kwargs`: it needs `reasoningEffort: "none"` in `providerOptions` (camelCase; a literal `reasoning_effort` key is overwritten), otherwise it thinks ~1000 tokens and the schema leaves an empty object.
- The 48/128 answer budgets cut Qwen3's runaway "thinking" inside JSON strings, which used to run to the old 512-token cap.
- Laya reads option names as text: `price_low` lost to `price_high` on "cheapest first" until `readable()` turned machine values into words.
- In-process Laya rounds probabilities to 4 decimals; the adapter declares that in `rounding`, or `experimental_decide` rejects distributions that sum to 1.0001.
- Hosted endpoints: `uniqueItems` is rejected by some providers' grammar converters (DeepInfra: "Unimplemented keys"), and OpenRouter answers HTTP 200 with the error in the body, which the SDK reports as "Invalid JSON response"; the choice schema uses `maxItems` instead. `reasoning_effort` together with `require_parameters` finds no provider for a non-reasoning model (404): `Endpoint.providerOptions` replaces the default `reasoningEffort: "none"` (an Ollama/Qwen3 need).
