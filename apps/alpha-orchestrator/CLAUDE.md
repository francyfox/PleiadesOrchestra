# alpha-orchestrator internals

See root `CLAUDE.md` for monorepo commands, workflow, code style and repo-wide lessons.

## Code layout

Follows the root "Code style" convention (`src/index.ts` composition root with config, DB, retention jobs, `serve`; `src/app.ts` `createApp(deps)`; `src/modules/<name>/`). What is specific here:

- `*.instance.ts` singletons (e.g. `alpha-understand.instance.ts`) — only `index.ts` and other `*.instance.ts` import them.
- Test helpers: `database.testing.ts` -> `testDb()`, `http.testing.ts` -> `setupAdminApp()`/`admin()`/`json()`.

Modules: `access`, `active-runs`, `agent-settings`, `agents`, `alpha-understand`, `auth`, `billing`, `blocked-ips`, `channel-directory`, `channels`, `completions`, `config`, `database`, `decisions`, `english-only`, `goap`, `history`, `http`, `identify`, `messages`, `performance`, `persona`, `plan-runs`, `prices`, `providers`, `rate-limit`, `reply`, `retention`, `run-binding`, `run-stream`, `security`, `stats`, `streaming`, `subscriptions`, `telegram-whitelist`, `text`, `threads`, `usage`, `usage-recorder`, `visitors`, `widget`, `world-state`.

## Commands

- Dev/run: `bun --cwd apps/alpha-orchestrator run dev` (watch) or `start`; copy `.env.example` to `.env`. Binary: `bun --cwd apps/alpha-orchestrator run build` -> `dist/harness` (`bun build --compile`).
- Seed the Telegram whitelist (one-off): `bun --cwd apps/alpha-orchestrator run import:telegram-whitelist <ids>`.
- DB migrations (drizzle-kit): after editing the schema run `bun --cwd apps/alpha-orchestrator run db:generate --name <name>`. Migrations are applied at startup. Then `bunx biome format --write apps/alpha-orchestrator/drizzle/meta` and `bun --cwd apps/alpha-orchestrator run db:snapshot` (see `drizzle/init.sql` below).
- **`bun build --compile` doesn't embed drizzle migrations** — the Docker image copies `drizzle/` and sets `DATABASE_MIGRATIONS_DIR`.
- Docker: `turbo prune` Dockerfile, Alpine final stage (musl binary + `libstdc++`/`libgcc`).

## GOAP planner

`packages/core/src/goap/` — `plan`, `runPlan`, `createTextAction`, `createDecisionAction`, MCP-backed `ToolSource`. `WorldState` is a flat key→value fact bag; actions declare preconditions/effects; the executor reconciles actual effects against expected ones.

`buildActions` in `modules/goap/goap.service.ts` builds the action catalog once per app instance. `POST /v1/messages` streams `runPlan` as NDJSON (`delta`/`done`/`error`). Design and phase status: `docs/trust/drafts/goap-actions.md`.

**Only SESSION_FACTS survive between requests** — a failed or completed run keeps only `SESSION_FACTS` (`storeOpen`, `store`, `lastProduct`); only a WAITING run (paused for a browser tool) keeps its full state for `resumeReply`. This prevents stale `webmcp:*:result` facts from poisoning the next message.

**User-facing progress (flow lines)** — `GoapAction.describe(state, phase)` → `RunPlanOptions.onStep` → NDJSON `step` lines `{id, phase: running|done|failed, text}` → `ChatMessage.steps` in the widget. Texts are per tool *intent*, bilingual (`webmcp-steps.ts`, `step-text.ts`, language from `page:lang`), never per site. `streamPlanRun` persists them into `plan_runs.steps` (JSON, `StoredStep`) so they survive a reload.

**Flow requests (admin `/flow`)** — a *request* = chain of `plan_runs` linked by `plan_runs.root_run_id`. `ActiveRuns` holds in-memory events of runs executing now. The BFF (`modules/requests`, `buildRequestView`) merges DB + registry into `RequestView` nodes: `prompt → translate → understand → steps → result` with per-step time, tool args, tool answers, effects, model calls.

**External model servers**: env picks base URL, model, temperature and concurrency per model — `LLM_*` (beta), `FUNCTION_CALL_*` (delta), `LAYA_*` (gamma; `LAYA_MODEL`) name the servers; Ollama + Qwen3 needs `reasoning_effort = "none"` on its model in providers.toml. `probeAgents` tries `/health`, and for text/function-call falls back to `{base}/models` (Ollama has no `/health`). Model parameters (temperature, reasoning effort, extra body) and provider keys live in `configs/providers.toml` (`modules/providers`, seeded from the env servers when missing, and an existing file without a `systemone` provider gets the env Laya one at start, 0600, git/docker-ignored); `POST /v1/admin/providers-toml/check` runs the save's checks without writing; `configs/providers.schema.json` (editor schema from the zod schema, `bun run providers:schema`, a test fails when stale) is referenced by the file's first line `#:schema`; an agent picks provider + model (`agent_settings`), the model's `types` (a list: a multimodal model has several, e.g. `["language", "image"]`; the old single `type` still reads) must include the agent's: `language` (default; beta/delta, OpenAI chat), `decision` (gamma-decision) (alpha-understand is a language agent too); a mismatch is a 400. Type names follow the AI SDK's model factories: `language`, `embedding`, `image`, `video`, `speech`, `transcription`, `reranking`, `decision`  (agents use only `language`, `decision`; the others just describe a provider's catalog; the panel shows the names in English); one provider holds models of several types (OpenRouter: chat + `liquid/d1-ultra`). A decision model is asked at the provider's `decisions_url` (default `base_url`): a root without `/v1` (local Laya or TypeSafe Jev, `POST {root}/v1/systemone`) or a URL ending in `/decisions` (OpenRouter `https://openrouter.ai/api/alpha/decisions`), which is posted to as it is. Files written before model types (provider `type = "systemone"`) still load: the provider's type becomes its models' type, and a stale `type` is never written back. A file from the Opus-MT days still loads too: a `type = "ctranslate2"` provider and every `translation` model are dropped on read (`dropLegacyTranslator`), and the next save writes the file without them. The decision agent is rebuilt on save (`decisions.instance`), `LAYA_CALIBRATION` applies only to `laya*` models (d1, pplx-decider, Jev keep their own probabilities), and its test button makes one tiny decision. Contract in `admin-api.md`. `GET /v1/admin/agents` answers with the previous probe of the same specs and refreshes in the background (a down agent took 3 s per page open). Examples in `.env.example`.

**Removal of every item** — `prepareNewMessage` writes `scopeAll` (`scopeFacts`) and binds the catalog (`bindListScope`, also in `prepareResume`): read tool → remover per item (`packages/core` CLAUDE.md). Reply: `replyFromTemplate:removal` (`createRemovalReplyAction`, ru/en/kk, «already empty» from the site's own answer). A `checkout`/`removeFromCart` where no step ran gets an honest «nothing was done» prompt in `replyChunks`, never the bare message.

**`recordCall`** (`packages/core/src/record-call.ts`) is the single reporting path: telemetry line + `llm_calls` row. `LlmCallKind` values: `text`, `decision`, `classify` (`translate` only in old rows, never written). Tokens of decision calls are exact and come from the model, not an estimate: `DecisionAgent.decide` returns only answers, so the adapter reports the response `usage` through `reportTokens` and the recorder wraps the call in `collectTokens` (`packages/core/src/usage-collector.ts`, `AsyncLocalStorage`; rounds add up).

## Delta function-call agent

`apps/delta-function-call` (Qwen3-1.7B, port 8282) writes JSON arguments of WebMCP tool calls. `FunctionCallAgent` in `packages/core/src/function-call-agent.ts` — json_schema-constrained completion, `temperature 0`. Called from `createWebMcpActions({ functionCallAgent })` (`argumentsFor` in `goap/webmcp-actions.ts`).

Pipeline: llm output → `repair-arguments.ts` (fences/`<think>`/trailing commas/closing brackets/type coercion) → `validate-arguments.ts` (required/type/enum/items) → up to 2 correction attempts → `buildArguments` fallback → if still missing required field: step fails (`toolResult:<tool> = false`).

Facts named like a parameter are merged OVER delta's answer (`argumentsFor`). Only string/number facts reach the model (no planner flags); only the last *search* answer is shown. Qwen3 thinking is off (`enable_thinking=false`). The model reads `userMessageEn`; a non-English message without a translation (no translator, or it failed) skips delta — `buildArguments` only.

Delta is always called even if facts already look valid — `search_products` has real filters (`department`, `dietary`, `max_price`) that need NL understanding; filter accuracy is worth the ~1.6 s per call.

Real-stack check: `REAL_STACK=1 bunx playwright test buy-cheese` in `apps/e2e`.

## Intent classification

`classifyMessageIntentDetailed(..., rules: "guarded")` in `prepareNewMessage` (`reply.service.ts`):

1. **Lexical rules** (`message-cues.ts`) for `checkout`/`removeFromCart` only — these are never taken from Laya alone.
2. **Site memory** — `IntentMemory` (`modules/intents`): per-channel naive Bayes on `intent_examples` rows with `status = approved`. Built from `normalizeIntentText`. Silent below 0.85, never for `checkout`/`removeFromCart`.
3. **Laya** on the English translation (not the original; no page/lang) for what rules and memory don't claim. Answers are stored in `intent_examples`: `pending` (decide nothing until an admin approves/rejects/corrects in `/intents`), or, when the CALIBRATED confidence (`withCalibration` in `index.ts`, table `LAYA_CALIBRATION` in core) is >= `LAYA_AUTO_APPROVE_CONFIDENCE` (default 0.85), `approved` with `approved_by = auto` and the memory rebuilt. `confidence` is kept on the row and on the `classify` ledger row (`llm_calls.confidence`). `llm_calls.choices` (JSON, NULL for non-decision calls) holds `[{ question, chosen, options: { option: probability } }]` for every choice question of the call (intent rounds, `chooseTool` rounds, `choose:<tool>.<param>` steps), filled by `withChoiceReport` in `index.ts`; `GET /v1/admin/requests/:id` returns it on each `llmCalls` row. Never for `checkout`/`removeFromCart`. An admin verdict sets `approved_by = admin`.
4. Fallback: `chat`.

Not a reason to approve: a reached goal only proves the plan was executable, not that the intent was right (the confidence threshold is the only automatic approval). `recordCall` logs each decision as `kind: classify`, `provider` = `laya`/`memory`/`rules`.

**Presets per channel** (`channels.intent_sets` -> `ReplyDeps.taxonomy(channelId)` = `resolveTaxonomy`): Laya's options, a tool's preconditions/effects, the guards and the word rules come from the channel's merged presets (`packages/intent-presets`); the classified-catalog cache key includes the preset ids. A channel with no set takes the shop preset for those dependencies (`app.ts`, marked `shortcut`).

**Channels without an intent set** (`channels.intent_sets` empty; new channels start so, rows from before the column read `["shop"]` and keep the flow above; `ReplyDeps.intentSets`): `prepareByTool` (`reply.service.ts`) skips the shop intents. Order: words of checkout/removal -> the guarded flow above; a buy message that says a tool's own option (`matchSpecialist`) -> that tool; an intent the words give («buy» = addToCart) narrows the offer to the tools whose effects are that intent's (one such tool = taken without a model, ledger source `words`; none = every tool); then `chooseTool` (`packages/core/src/goap/tool-choice.ts`): the site's tools (only actions with their own `toolResult:<name>` effect; the `choose:<tool>.<param>` helper steps are not tools) go to Laya in groups of 8, each with `chat` and `other`, then the group winners meet in a final round. The groups read the tool's name (`search products`; a one-word name keeps the description): with descriptions «find sneakers» chose `get_current_product` on Laya. The last round (the final, or the only group) reads name + description (≤200 chars): names alone crowned `add_staples_to_cart` for «buy Toilet Paper, Laundry Detergent». Dangerous tools are never offered. A chosen tool that changes something and has enum options (`GoapAction.options`) gets one boolean decision, «does the visitor only ask which choices there are?» (`askedOptions` in `tool-choice.ts`; a search or reader never: «do you have tomatoes?» is searched): yes (≥0.5) = no tool call, turn fact `askedOptions` (JSON `{tool, options}`) and `replyChunks` lists those values («what sizes are there?»). The goal is `toolResult:<tool>`; the tool's preconditions still come from its shop-taxonomy intent (a search still precedes an id-based add). `other`, a final probability under 0.5 or a non-option = `unclear`: fact `clarifyOptions`, the reply model asks. Measured on the WooCommerce demo (`wp-local`): 8 of 8 scenarios end in the same cart as the same task done by hand through the shop's WebMCP tools (cart, recipe, kit, variation, search, list).

**Tool cues** (`tool-cues.ts`) classify intent from the tool NAME (not description). A read/edit tool is `other`; `specialistPenalty` adds cost per qualifier word (`add_recipe_to_cart` loses the tie to `add_to_cart`).

**Named options** (`packages/core/src/goap/specialist.ts`): a message that says one of a tool's string-enum values (`add_recipe_to_cart.recipe = "Weeknight Beef Tacos"`) picks that tool over the plain one. `prepareNewMessage` writes `specialistTool` + the value + `catalogSearched`/`requestParsed` into the state and `preferSpecialist` (also in `prepareResume`) drops that action's cost; no search, no delta for the value.

Eval: `bun run eval:intents` / `bun run eval:tools` in `packages/core` (cases in `src/goap/intent-cases.ts`). The all-rules mode (`rules: "all"`) is the eval default; production uses `"guarded"`.

## alpha-understand (translation and understanding)

Agent id `alpha-understand` (admin role `understand`), built in `modules/alpha-understand/alpha-understand.instance.ts`: a `FunctionCallAgent`, temperature fixed 0, default server and model = beta-text's env (`LLM_*`) and beta's picked model until it has its own (`refresh()` in `agent-settings.service.ts`). There is no other translator (Opus-MT/CTranslate2 was removed, see `lessons-learned.md`).

**First thing `initialState` does** (before Laya, before beta-text): ONE call (`understandMessage`, `packages/core/src/goap/understanding.ts`, ledger `actionName: "alpha-understand"`, kind `decision`) returning `{en, tasks:[{intent, text, items:[{name, quantity}]}]}`; counts are written as digits in `en`/`text` (delta reads them there). Its `en` is the `userMessageEn` fact (original `userMessage` stays) and, for ONE task, the facts `query` (first item), `quantity` (0 = removal), `requestedItems` (several items) and `requestParsed` (the parse step is skipped). Item names are written in the channel's `catalogLanguage`. Two or more tasks and decomposition allowed (intent sets or `severalTasks`): the queue is built from them (`prepareSeveralTasks`, no delta decomposition call; `QueuedTask.items` set the facts per task). Any failure (error, timeout, unusable JSON, not configured): the message goes on UNtranslated (no `userMessageEn` for non-Latin text; delta is skipped and arguments are built from the facts), then the old decomposition path. **`attributes`** (what the visitor states besides product and count: size, diet, sort order, guests…; missing = `[]`) become the turn fact `statedAttributes` (JSON, `attributeFacts`; per task in `QueuedTask.attributes`); it gates the `choose:<tool>.<param>` steps (see `packages/core/CLAUDE.md`). Not done: the task's intent does not replace Laya's classification. **Today:** the request starts with `Today is YYYY-MM-DD (Weekday)` and alpha writes relative/partial dates as full dates and times as 24h `HH:MM` in `en`/task text. Turn facts `today` (`TODAY_FACT`: body `clientDate`, else the server's UTC date from `deps.now`) and `timeZone` (body `timeZone`, only when sent); neither is a session fact; delta sees both (`factsForModel`). **Visitor wait:** see `missingParams` below.

**Catalog language** (`channels.catalog_language`, default `en`, `catalogLang` fact): `createProductRequestAction` uses the English text only for `en` catalogs; `extractProductRequestRu` (rules on the original) for `ru`; the shopper's words for any other language.

**Laya gets English only** (`modules/english-only`, `withEnglishOnly` wraps the `DecisionAgent` in `index.ts`): every non-Latin string of a decide call (tool descriptions, enum values, option keys, a message that has no English text) is collected and translated by alpha-understand in ONE batch (`translateTexts`, schema `{texts: string[]}`, same order), cached; option keys are sent translated and mapped back. No alpha-understand, a failed call, a wrong count or an answer still in another script = `UntranslatableError`, the call is not made (intent: words/chat; tool catalog: not registered, the next registration tries again; parameter choice: first option).

## Product request extraction

`extractProductRequest` peels verbs/politeness/containers from the English text (rules, no model). Used only for `en` catalogs + an English text. Uses the rules only when `isSimpleRequest` (≤3 words, or a command verb with no clause words, ≤12 words); otherwise `query` fact is left unset and delta reads the whole English text.

**`SESSION_FACTS` includes `lastProduct`** (first in-stock product of the last successful search). `reuseLastProduct(state)` (intent `addToCart` only) fires when `namesNoProduct` (all words are filler: purchase verbs, politeness, «now/теперь», pronouns, digits — lists `FILLER_EN`/`FILLER_RU` in `product-request.ts`). It copies `product`, `query`, `quantity`, `requestParsed` into initial state; the search still runs (an id-based add tool such as WooCommerce `add_to_cart(id)` can only get the id from a search answer, otherwise the small model invents `id: 1`).

## Users, access, channels

`alpha-orchestrator` owns a SQLite DB (`drizzle-orm` + `bun:sqlite`): channels (`accessMode` whitelist/open), chat visitors (table `visitors`, id unchanged, generated `name` = `adjective_animal_xxxxxx` from `visitors/visitor-names.ts`, not unique, backfilled at startup by `backfillVisitorNames`; identified or anonymous; anonymous purged after `ANON_RETENTION_HOURS`), last `MESSAGE_RETENTION_PER_USER` (10) messages **per user** (stored but NOT sent to the model — `AGENT_MAX_HISTORY_MESSAGES = 0`; 1B model copies earlier replies after a few exchanges), `llm_calls` ledger (never deleted with messages), GOAP traces (`plan_runs`/`plan_events`).

Access (block > whitelist) decided by the orchestrator, not transports: bot calls `POST /v1/access` first, stays silent on `allowed: false`; `/v1/messages` returns empty 403 for denied users.

**Channel ownership**: `channels.owner_id` (admin-api account id, NULL = staff-owned, no FK: another database). `GET /v1/admin/channels`, `/stats`, `/usage`, `/visitors`, `/requests`, `/blocked-ips` take `ownerId` and keep only that owner's channels (blocked IPs: no global ones); `/visitors/:id` and `/requests/:id` 404 with a foreign `ownerId`, `POST /visitors/bulk` skips foreign visitors when the body has one; `POST /v1/admin/channels` accepts it; `DELETE /v1/admin/owners/:ownerId/channels` (`ownerChannelsRoutes`) deletes them with everything that cascades, while `llm_calls`/subscriptions keep their rows with `channel_id` NULL (FK `set null`). The orchestrator does no authorization of its own here; admin-api decides who may pass which `ownerId`.

Admin routes: `/v1/admin/*` under a separate `ADMIN_API_KEY` + `X-Admin-Id`. Widget routes: `/v1/widget/*` (publishable key + `Origin` allowlist + visitor token, in-memory rate limits). `POST /v1/channels/:slug/identify` (server-to-server, links anonymous visitor to site account).

IPs: blocking by salted hash (`blocked_ips.ip_hash`), plaintext `blocked_ips.ip` (null on legacy rows) and `visitors.last_ip` for admin display. Anonymous visitors purged with `ANON_RETENTION_HOURS`; blocks expire.

Channel lookup is `Map`/`Set` (`channel-directory`, `invalidate()` after admin writes). `FixedWindowLimiter` prunes at most once per window. Widget guard does "last seen" writes only after origin/IP checks pass.

## Reply service

**Reply rules (persona `FIXED_RULES`)**: the widget already shows the turn's `step` lines, so the reply does not list what was done; it is a 1-2 sentence consultant answer (failure or not found is still said plainly). Choices go at the very end as a numbered list `1. <option>` (max 9, each a phrase the visitor can send back, text before it never repeats them); links only from the site's answers as `[title](https://...)`. **`replyTo`** (widget `POST /v1/widget/messages`, `POST /v1/messages`; <=2000 chars): the assistant message the visitor answers. Turn fact `replyTo` (`REPLY_TO_FACT`, not a session fact), quoted into the alpha-understand request and into `replyChunks`; untrusted like the message. Without one (a typed answer; only a picked button sends it) `initialState` takes the thread's last assistant message from the history, and the messages before it as `history` (`conversationContext` in core, window `CONTEXT_MESSAGES` = one exchange, `shortcut`; `eval:answers` measured the whole chain no better on 6 long chains): alpha then writes `en` as the complete request the answer makes («хочу купить томат» → «томата нет, предложить томатный сок?» → «да» = «buy tomato juice»), and every step after it reads that text. A message that makes sense alone, or a refusal/thanks, ignores the quote. `bun run eval:answers` (`albedo eval --name answers`).

**`missingParams` and the visitor wait**: when a tool's required arguments are still missing after delta + `buildArguments`, the step does not call the site and does not count as a site failure: it writes the fact `missingParams` (JSON `{tool, params:[{name, description}]}`), `replyChunks` tells the reply model that nothing was done yet and to ask for exactly those details by meaning, and the run counts as succeeded. `saveCheckpoint` then keeps the state the plan REACHED at the question (`reached`, before the reply-only run; minus `missingParams` and the failed tool's `toolResult:<tool>`, so the step is planned again) and the goal, plus the fact `visitorWait` (`VISITOR_WAIT_FACT`, JSON `{request, asked}`) — no `awaitedTool`, so `pending`, `awaitedCheckpoint` and the 60 s `expireStaleWaits` branch ignore it; it expires after `VISITOR_WAIT_TIMEOUT_MS` (10 min, quietly, no marker). The next message: `initialState` loads the checkpoint, gives alpha-understand `pending` (what was asked + the waiting request) and alpha answers `answersPending`. True: the starting facts are merged with the answer (`userMessageEn` = old + new, `statedAttributes` merged, new wins by name), `joinRequest` to the old run, goal = the saved goal, and `prepareNewMessage` returns that plan without classifying (delta fills the arguments again). False/no alpha: the wait is dropped and the message is a new run. Only the end of a plain (no task queue) run waits; shortcut: `clarifyOptions` and `conflictingTasks` could use the same fact, not built yet.  Steps that finished before the question are not repeated (their facts are kept).

`ReplyService.startReply` / `resumeReply` in `modules/reply/reply.service.ts`. `streamPlanRun` (`modules/run-stream`) streams NDJSON + persists steps after the terminal line.

**Several products** («buy A, B, C»): facts `foundItems`/`missingItems` (JSON) make `replyFromTemplate` and `replyChunks` list every added item and the ones not found; the fan-out mechanism is in `packages/core/CLAUDE.md`.

**`replyFromTemplate`** (`modules/goap/goap.service.ts`) — templated reply for a completed purchase: no beta-text call, streamed as one `delta`, cost 1, preconditions `inCart + messageIntent: addToCart`. Language from `page:lang` (ru/en/kk, else message's script).

**`replyChunks`** hands the reply model the outcome: cart addition, newest `webmcp:*:text` answer (≤800 chars), or failed `toolResult:*`. Before this fix beta-text answered «as an AI I can't find apples» even when the site had listed them.

**Several tasks in one message** (`modules/tasks`, `prepareSeveralTasks` in `reply.service.ts`): with a site catalog, intent sets on the channel and an English text with list cues (`looksLikeSeveralTasks`), delta splits (when the `alpha-understand` step answered, its tasks are used and delta is not asked) the message (`decomposeMessage`, each task has its own `text`). `runnableTasks` drops a checkout/removal the words do not confirm, tasks no site tool can do (also delta's stray `select`) and a repeated `select`; `mustAskOrder` (conflict pairs live in the shop preset, `taskConflicts`) with no order word like "then" runs nothing and the reply asks (fact `conflictingTasks`). Otherwise a queue of ordinary single-intent runs: the rest of the tasks are the fact `taskQueue` and what finished tasks did is `taskOutcomes` (JSON), so a WAITING checkpoint keeps them. `streamPlanRun` sends no terminal line for a run with tasks behind it and asks `next` (`ReplyService.openStream`) for the following run, a new `plan_runs` row joined to the same root, streamed in the same response (a resumed `tool-results` response included). Each task re-reads the thread catalog (`resolveDynamicActions`) and starts from the turn facts + SESSION_FACTS only. Only the last task has the reply goal; the template replies are off after earlier tasks, `replyChunks` hands the text model every outcome (a failed task reads `NOT done`). Limits: the wait timeout (`BROWSER_WAIT_TIMEOUT_MS`, `waiting-runs`) counts per browser call and drops the rest of the queue with the checkpoint; channels without intent sets are decomposed only with the channel switch `severalTasks` (admin channel dialog; the tasks then take the shop preset's intents); `ru` catalogs read the full original message in `userMessage`.

**Widget errors**: three types — `network` (no answer, locks composer), `request` (terminal `error` with `code: "task_failed"` — shown as `s.request` + server's `hint` ≤400 chars, never locks), `failed` (other server fault). A failed task triggers a second `runPlan` with `replyOnly` goal so beta-text explains the failure and passes the site's advice on; the request stays `failed` in admin but the turn ends with a normal `done`.

**History stores raw user text** — `userMessageRaw` (`typedText`: NFC, `\n` line ends, control chars except newline/tab dropped). `createTextAction({ toHistoryText })` → `IncomingMessage.historyText` → agent appends `historyText ?? chunks.join(" ")`. Before this fix multi-line messages were stored flattened.

**Language** — the widget sends `lang` (en/ru/kk) and `langChosen` (true only for a pick in its header) with every message/tool result; `pageFacts` writes them as `page:lang` (wins over the URL's) and `ui:langChosen`, step lines read `page:lang`. Reply language rule (`answerLine`, `goap.service.ts`), one closing line of every `replyChunks` wrapper: channel `persona.defaultLang` (fact `persona:lang`) > the visitor's pick > "Answer in the language of the visitor's message quoted above." (no script guessing; template replies use `replyLanguage`, which does guess by script because there are only ru/kk/en). All wrappers are English and quote the ORIGINAL message (`userMessage`): a Russian wrapper made the model answer in Russian. The visitor's message is stored in the history when the run starts (`initialState`, fact `userStored`; `historyText: ""` tells the agent to store only the reply and to leave that newest user turn out of the context), so a reload mid-run shows it.

## Channel persona (reply prompt)

`modules/persona`. The reply system prompt is **always built from parts** (`buildReplyPrompt`): the admin's `instructions` (role text, multi-line, <=2000 chars, every line quoted with `> ` so it stays visibly inside its own section) + persona slots (name, tone, greeting, forbidden topics, hand-off contact, language; one line each) + the fixed rules block (`FIXED_BLOCK`, always last, not editable). No `undefined` prompt: a channel without a row gets `DEFAULT_REPLY_PROMPT` (default persona: name "Альбедо", neutral role/tone, not shop-specific); the orchestrator's text agent uses the same as its built-in prompt, so cli/telegram get it too. `@repo/core`'s own default is a short neutral one.

**Storage = overrides only.** `channel_persona` columns hold what the admin changed; `""` / empty list = standard (`DEFAULT_PERSONA`). `savePersona` also stores a value equal to the default as `""`, so improving a default reaches every channel that never customized that field. `getPersona` = overrides over defaults.

Admin API: `GET/PUT /v1/admin/channels/:id/persona` -> `{ persona (in effect), defaults, prompt, fixed }`; `POST .../persona/preview` takes unsaved values, returns the same shape, writes nothing. The UI never copies the rules: it shows `prompt`, with the `fixed` tail marked read-only.

## MCP catalog (WebMCP)

**Crash recovery (`modules/pending`)** — `GET /v1/widget/threads/:id/pending` (widget guard, own thread) answers `none | waiting {callId, tool, arguments, tasksLeft} | interrupted {runId, prompt, tasksLeft} | expired {prompt, tasksLeft}`; nothing is replayed server-side. `waiting` = the checkpoint's `awaitedTool` + `awaitedArgs` facts (JSON, written by `saveCheckpoint`) while `state.planRunId` is the thread's newest run. `interrupted` = the newest run has `plan_runs.interrupted` (set at startup by `markInterruptedRuns`: no trace, `duration_ms = 0`; admin `/flow` shows status `interrupted`). `expired` = the `expiredRequest` fact (JSON `{prompt, tasksLeft}`) that `expireStaleWaits` leaves instead of dropping the wait; read once by `pending`, dropped after a day. Cancel: the widget POSTs `/tool-results` with `cancelled: true` (same validation as a result: callId = the checkpoint's run, tool = the awaited one); `cancelWait` writes a run row with one `cancelled` trace event (joined to the request; /flow status `cancelled`), drops the checkpoint and the rest of the task queue (conversation facts stay) and the stream is one `{type:"cancelled"}` line. No model call, nothing is claimed: the tool may have run. `interrupted` is told once (fact `interruptedSeen` in the thread's checkpoint). `tasksLeft` of `interrupted` is read from the last wait's checkpoint (approximate).

Sites announce tool catalogs on panel open via `POST /v1/widget/tools`. `mcp_catalogs`: one row per distinct catalog per channel, key = `hashTools` (canonical JSON of name/description/schema, order-independent). Same hash keys `ReplyService`'s in-memory LRU of classified catalogs (32). Widget re-announces on `toolchange` event (debounced 300 ms). Newest 5 versions kept per channel; no TTL (invalidation by content).

Elysia drops body fields not in schema — `inputSchema.required` was once lost here.

## Gotchas

- In `app.handle` tests (root lesson: use `http://localhost/...`), `onAfterResponse` runs after the response is returned (tests need a tick). A request rejected in `onRequest` skips all other hooks.
- `SqliteWorldStateStore` existed and was tested but wasn't wired in `index.ts` until 2026-09-29 — always verify `createApp(...)` in `index.ts`, not just that the dependency type accepts the field.

## `drizzle/init.sql` (first-time setup)

One generated SQL file with the full schema, seed data and the `__drizzle_migrations` rows (so the migrator sees all existing migrations as applied). After every `db:generate`, run `bun run db:snapshot` (`scripts/db-snapshot.ts` → `src/modules/database/database.snapshot.ts`, which runs the real migrator in a temp DB and dumps it). `database.snapshot.test.ts` fails if the committed file is stale. Services keep applying incremental migrations at startup; init.sql is only for provisioning a fresh DB (`sqlite3 db < drizzle/init.sql`).

## Billing (Polar)

`modules/billing`: `POST /v1/billing/polar`, mounted only with `POLAR_WEBHOOK_SECRET`, outside both bearer keys (`isOpenPath`). Signature, replay (`billing_webhooks`) and out-of-order rules: `admin-api.md` ("Polar webhook"). Events map to accounts by Polar `customer.external_id` (= admin-api user id). `order.paid`/`order.refunded` fill `orders`; a credits order (`POLAR_CREDITS_PRODUCT_ID`) tops up `credit_ledger` once. `credit_ledger` is append-only, **micro-USD integers** (1 TR = 1_000_000), balance = SUM (`modules/ledger`); `SqliteUsageRecorder.flush` debits each priced call of an owned channel (`usage`, ref = `llm_calls.id`; failure is logged, never fails the reply; prices come from the price book's cache). `ChannelDirectory.suspension(channel)` is the enforcement point: it caches each owner account's standing (`standingOf`, read from DB on first use, kept until `refreshStanding(accountId)`; an `ok` standing with `until <= now` reads as `plan_expired`, no timer; staff channels never suspend). Refresh is called by the Polar webhook route (`onAccountChanged`, applied events only) and by `SqliteUsageRecorder.flush` (`onDebited`, once per debited account per flush; wired in `usage-recorder.instance.ts`). Checked in `WidgetGuard.authorize` and `POST /v1/widget/visitors` (`402 { code: "channel_suspended" }`) and in `POST /v1/access` (`reason: "suspended"`). `modules/standing`: pure `accountStanding(plan, balance, now)`. `modules/account-billing`: `GET /v1/admin/accounts/:accountId/billing`. `modules/subscriptions`: admin list by account (`/v1/admin/subscriptions?accountId=`); the hand-made channel link is gone. `modules/finance`: `GET /v1/admin/finance?from&to` (model spend, USD revenue net of refunds, per-order `@repo/tax` losses, net profit; pure `financeOf`). `modules/prices`: OpenRouter price list (cache a day, failure = no prices) behind the `costUsd` of `/v1/admin/usage`.
