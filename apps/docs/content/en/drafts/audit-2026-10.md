# PleiadesOrchestra audit, October 2026

Snapshot: `master` @ `ebeec97` (2026-10-13). Scope: security, performance (through a Rust developer's eyes), product/marketing, modularity and external LLM providers, competitors.

Finding statuses: **[P0]** fix before any public deployment, **[P1]** in the next sprint, **[P2]** a planned improvement.

## 1. Security

### [P0] The WebMCP polyfill runs the site's tools on a `postMessage` from any window

`packages/pleiades-widget/src/lib/webmcp/webmcp-polyfill.ts:663`: the `message` listener on the site's window answers `WEBMCP_GET_TOOLS_REQUEST` and **executes** `WEBMCP_EXECUTE_TOOL_REQUEST` without checking `event.origin`, and the answer goes out with `targetOrigin "*"`.

Scenario: an attacker opens the shop with `window.open()` (or the shop is embedded as an iframe in someone else's page, or the shop's page has a third-party ad iframe with access to `window.parent`). They `postMessage` the shop's window, and the polyfill runs `add_to_cart`, `checkout`, `search_orders` and so on **with the visitor's cookies**, then sends the result (orders, cart, personal data from the tool's answer) back to the attacker. In effect it is a cross-origin CSRF that can read the response. The polyfill is installed unconditionally when the widget mounts (`src/element.ts:184`). Google's version is a demo; it must not move into a library for other people's sites in this form.

Fix:
- The request handler (the "tool provider" role) is off by default; it is enabled by an attribute `expose-tools-to="https://a.example,https://b.example"`.
- `if (!allowedOrigins.has(event.origin)) return;` and answer to `event.origin`, not `"*"`.
- The same in `getRemoteTools`/`executeTool`: check the answer's `event.origin`, not only its `source`.
- Generate `requestId` with `crypto.randomUUID()`, not `Math.random()`.
- Test: a message from a foreign origin does not call `executeTool`.

### [P0] Spoofing the IP through `X-Forwarded-For` bypasses the rate limit and IP blocks

`apps/alpha-orchestrator/src/modules/widget/widget.service.ts:96` takes the **first** element of `X-Forwarded-For`. Cloudflare *appends* the client IP to the end of an existing header, so the first element is set by the client itself: `X-Forwarded-For: 1.2.3.<random>` gives every request a new "IP". As a result `WIDGET_IP_MESSAGES_PER_MINUTE`, `WIDGET_VISITORS_PER_HOUR_PER_IP` and IP blocks do not work.

Fix: behind Cloudflare, take `CF-Connecting-IP`. In general, take `X-Forwarded-For` from the right, skipping N trusted hops (`TRUSTED_PROXY_HOPS=1`). Make the mode explicit in config: `CLIENT_IP_SOURCE=socket|cf-connecting-ip|xff-rightmost`.

### [P1] Services are published on `0.0.0.0`

`compose.yml`: `3000:3000` (the orchestrator, including `/v1/admin/*` and the transport `/v1/messages`), `8181` (beta-text), `8282` (delta, `API_KEY` **empty** by default, i.e. no auth), `8090` (gamma). On a LAN or a VPS without a firewall this is an open LLM endpoint and admin API protected by one bearer key. Kali-MCP was meant as a source of actions "per thread". If its connection were ever fixed (see below), it would give remote command execution on behalf of an anonymous widget visitor.

Fix: `127.0.0.1:` on every port except those really needed outside. Do not publish internal services at all: the compose network is enough for them. Make `FUNCTION_CALL_API_KEY` required (`:?`), like `LLM_API_KEY`.

### ~~[P1] Kali MCP: dead and dangerous code~~ (removed 2026-10-13)

`kaliActions` was filled asynchronously while `threadActionsFor` was computed synchronously, so it was always `undefined`. "Fixing" it would have given any widget visitor command execution in Kali. Removed: the block in `index.ts`, `KALI_MCP_URL` in the config and `.env.example`, `packages/core/src/goap/http-mcp-client.ts` (used only by Kali). `threadActionsFor` stays: it is a test seam. Types and tests of `@repo/core` (291) and `alpha-orchestrator` (281) are green. The local `apps/alpha-orchestrator/.env` still has a `KALI_MCP_URL` line: it affects nothing and can be deleted by hand.

### [P1] Unbounded bodies and resources of public endpoints

- `POST /v1/widget/tool-results`: `result: t.Unknown()` (`widget.ts:248`) with no size limit. `toolResultText` first does `JSON.stringify` of the whole object and only then cuts it to 4000 characters. Bun's default `maxRequestBodySize` is 128 MB. Set `maxRequestBodySize` in `serve()` (for example 64 KB for the public API) and check the length before serialising.
- `POST /v1/widget/threads` is not rate-limited, so one token can create endless `threads` rows.
- `ReplyService.webmcpCatalog` (`app.ts:128`) is a `Map<threadId, actions>` without eviction. It grows with the number of threads until a restart. It needs an LRU/TTL tied to `ANON_RETENTION_HOURS`.
- `POST /v1/widget/tools`: the client sends the catalog. Every new catalog hash costs one Laya call per tool. A visitor can cycle through catalogs and load gamma-decision. Options: sign the catalog on the site's side (with the `sk_` key through a server-side `POST /v1/channels/:slug/catalog`), or allow classification only for catalogs an admin approved. An unapproved catalog is handled by rules (`tool-cues.ts`) without Laya.
- `tool-results` accepts a result for **any** `tool`, not only the one the checkpoint waits for (`callId` is not checked). Not a hole (the visitor only affects their own session), but a way to confuse the planner. Check `tool` and `callId` against the checkpoint's `WaitingOn`.

### [P1] admin-api: login brute force

better-auth is wrapped in `auth.api.*` calls, so its built-in rate limiter (which works only in the HTTP handler and only with `NODE_ENV=production`) does not apply to `POST /api/auth/login`. Today the loopback binding softens this, but whoever opens the panel to the outside gets unlimited password guessing. Add a `FixedWindowLimiter` by IP+email on login/register and a minimum password length of 12. "The first to register = superadmin" is a race on a fresh install: a one-off setup token from the logs/ENV is better.

### [P2] Other

- The Alpine/bun Docker images run as **root** (no `USER`). Add an unprivileged user, `read_only: true`, `cap_drop: [ALL]`, as already done for `gemini-mcp`.
- `.env.example` contains working keys (`local-dev-harness-key`, `local-dev-admin-key`). Someone will deploy them as they are. Better: empty values and a `bun run setup` script that generates keys (`openssl rand -hex 32`).
- `ConcurrencyLimiter` (`packages/core/src/concurrency-limiter.ts`) is a queue with no limit and no `AbortSignal`. If a client disconnects while waiting for a slot, its request still runs later. It needs a queue limit answering 503/429 and `acquire(signal)`.
- Prompt injection through tool answers and `customerContext` is unavoidable, but its consequences are worth limiting: the side-effect intents (`checkout`, `removeFromCart`) are already protected from "memory" and Laya. Add a UI confirmation in the widget for tools with `annotations.destructiveHint`/`readOnlyHint: false` (WebMCP supports it), and do not run them without a click.
- `.DS_Store` and `.idea/` are committed to the repository (including `dataSources.xml`, which may contain DB paths and names).

### What is done well

Separate transport and admin keys; `timingSafeEqual` over digests; visitor tokens stored only as sha256; IPs hashed with a salt; a CSRF Origin check in admin-api, WS upgrades included; the Cloudflare tunnel lets only public paths out; the widget renders text through `textContent`/`x-text`, uses the Alpine CSP build and no `sk_` keys; `checkout` is never taken from Laya/memory.

## 2. Performance (through a Rust developer's eyes)

Overall: the TS layer is not the bottleneck by itself. 95% of the latency is three model calls in a row (translate → Laya → delta ~1.6 s → beta-text). But there are places where the runtime pays extra, and one place that blocks the event loop.

### [P0] The synchronous FFI translation blocks the event loop

`translate-engine.ts:127`: `lib.symbols.tr_translate(...)` is synchronous, and `translateMessage` is called right in the request handler. 30–60 ms per message (up to 4 CTranslate2 threads, more under load), and all that time Bun sends no NDJSON chunk to other streams and accepts no connections. With 10 simultaneous messages the tail latency grows in steps.

Fixes, in order:
1. Move translation into a `Worker` (Bun workers + `postMessage` of strings) with a pool of 1–2. The FFI handle lives inside the worker.
2. Or build `libtranslator` with an async API (`tr_translate_async` + a callback through `JSCallback` with `threadsafe: true`).
3. In Rust this is an evening's work: `ct2rs` (CTranslate2 bindings) + `napi-rs`/C ABI, `tokio::task::spawn_blocking`, batching several messages into one `translate_batch`. CTranslate2 is more efficient on batches.

### [P1] The GOAP planner: O(n²) frontier and string signatures

`packages/core/src/goap/plan.ts`:
- The frontier is an array with a linear minimum search and `splice`, i.e. O(F) per pop and O(F²) in total.
- `signature()` does `Object.entries → sort → JSON.stringify` on every expansion: allocations and string sorting in the hot loop.
- Every node iterates over all actions, though an `effectKey → actions` index is possible.

With ~15–20 static actions this is microseconds. But a site's WebMCP catalog adds as many actions as the site has tools (the 20 KB limit is dozens of tools), and the breadth regression becomes noticeable. What a Rust developer would do:
- **Intern the facts**: at `buildActions` time give every `(key, value)` pair an index and store preconditions/effects as bitsets (`Uint32Array` or `bigint`; in Rust `u128`/`FixedBitSet`). Then `unsatisfied` and `resolve` are `AND`/`ANDNOT`, and the signature is the bitset itself (a key in `Map<bigint,…>`), with no strings and no sorting.
- **A binary heap** instead of the linear search (≈30 lines, no dependency needed).
- **An effect index**: `Map<factIndex, GoapAction[]>`, expanding only actions that close at least one fact of `remaining`.
- **An A\* heuristic**: the number of unsatisfied facts × min(cost) is admissible and cuts expansions.
- Benchmark: `bun:test` + `mitata` on a synthetic catalog of 50/100/200 actions, with a threshold in CI.

A separate Rust module just for the planner is not needed: with bitsets JS will cope. Rust is justified where native code already exists, i.e. in the translator.

### [P1] A SQLite write on every widget request

`touchVisitor` does 2 `UPDATE`s in a transaction on **every** authorised request, `GET /threads/:id/messages` included. In WAL mode that means fsyncs at checkpoints and contention for the single writer lock with the `plan_events` writes. Coalesce: update `lastSeenAt/expiresAt` only if more than 60 s passed since last time (the 24 h TTL does not suffer). Also add `PRAGMA synchronous = NORMAL` (safe in WAL) and `PRAGMA temp_store = MEMORY`.

### [P1] Prepared statements and hot queries

Drizzle on `bun:sqlite` rebuilds the SQL on every `.get()`/`.run()`. The hot path (`findVisitor`, `isIpBlocked`, `isOwnThread`, `touchVisitor`) needs `.prepare()` once at startup. That gives ×2–5 per DB query and less garbage for the GC.

### [P2] The rest

- `LLM_MAX_CONCURRENCY=4` with `PARALLEL=1` on llama-server: requests still queue on the server, only invisibly. Align the values (`LLM_MAX_CONCURRENCY = PARALLEL`) or raise `PARALLEL` to 2–4 with `--cont-batching`. For a 1B model on an iGPU batching is almost free in memory (KV ~0.6 GB at 2048 ctx per slot).
- **Speculative/prefix cache**: the system prompt is the same for all requests. llama-server has `--cache-reuse` and `cache_prompt: true`, which save prefill on every delta/beta call.
- **Pipeline parallelism**: translation and the Laya classification on the English text run strictly in sequence, and that is right. But `worldStateStore.load` and `resolveDynamicActions` can run in parallel with translation.
- **A template reply instead of beta-text** (`replyFromTemplate`) is the best optimisation in the project. Extend it: for a `search` with results, answer with a template listing the products, and call the 1B model only for "chatter" and explaining errors.
- `JSON.stringify(body.customerContext)` and `JSON.stringify(body.webmcpTools)` only to check the length: checking `Content-Length` before parsing is cheaper.
- `ConcurrencyLimiter.release` uses `queue.shift()` (O(n)). With an unbounded queue that is a problem; after a queue limit (see §1) it is not.
- gamma-decision takes 1.5 GiB RAM, more than anything else. Check int8 quantisation of the ONNX model and `intra_op_num_threads`. For the bounded set of decisions (intent, tool class) the replacement candidates are a distilled classifier (fastText/a linear model on embeddings, <50 MB, <1 ms) with Laya as a fallback. `IntentMemory` (naive Bayes) already moves that way.

## 3. Product and marketing: why small businesses and developers find it hard to adopt yet

### What gets in the way now

1. **The bot's default personality is "Ты — Альбедо: циничный, сверхэффективный AI-интерфейс"** ("You are Albedo: a cynical, hyper-efficient AI interface", `packages/core/src/agent.ts:41`), and it is used in replies to shop customers (`agents.instance.ts` does not pass a `systemPrompt`). A shop owner does not need a cynical bot, and the tone and name cannot be set per channel.
2. **The delta prompt is hard-wired to "online grocery shop"** (`function-call-agent.ts:61`), which contradicts the "not one shop" rule in CLAUDE.md. An electronics shop gets argument filling with grocery examples.
3. **The entry barrier**: 6 containers, 4 `.env` files, Vulkan groups, a Cloudflare token (`tunnel` with `:?`: without the token the whole `docker compose up` fails), manual channel setup. For a small business owner this is insurmountable. For a developer it is "an evening of setup".
4. **The "try it in 2 minutes" path is hidden**: the landing and playground exist, but live in another repository (`shalotts/src/routes/[[locale=locale]]/landing/pleiades-orchestra`), and the README does not link them. The plan is to bring up `apps/docs` on SveltePress and move them there (see §7.1).
5. **The README promises "No GPU required"**, but needs 3.5 GiB RAM and 4+ cores per site. That is honest, but it should be framed as an advantage: "runs on a €10/month VPS".
6. **Gaps in the docs**: `CLAUDE.md` points to `docs/harness-goap-orchestrator-plan.md`, which does not exist. There is no "connect your site in 15 minutes" guide with `registerTool` examples for different domains (not only cheese and milk).
7. **AGPL**: a stopper for SaaS integrators and agencies (the BSD widget is right, but the server needs a clear commercial path). `COMMERCIAL.md` must state the price as the landing does: **$500, one-off**. Today it says "The price is shown at checkout" and "at the Licensor's discretion", while the landing already says $500. The mismatch looks like a hidden price and scares off exactly the integrators who need a predictable estimate. Keep the price in one place and check it on every landing change.
8. **No value metrics for the owner**: the admin panel shows tokens, latency and plans, which matter to an engineer. The owner cares about other things: "how many add-to-carts the bot made", "chat to order conversion", "top queries with no matching product".

### Recommendations: small business

- **Platform plugins** matter more than "MCP for any site". A WooCommerce/Shopify App/1C-Bitrix/InSales/Tilda plugin that registers the WebMCP tools itself (`search_products`, `add_to_cart`, `get_cart`, `order_status`) from the platform's API. The owner installs the plugin and the bot works. This is the main adoption lever.
- **A channel persona** in the admin panel: name, tone, default language, greeting, forbidden topics, escalation contacts. Stored in `channels`, used as the beta-text system prompt.
- **Handoff to a human**: a "call an operator" button forwarding to the owner's Telegram bot (the transport exists). Without it a small business will not trust the bot with its customers.
- **FAQ/knowledge base without a RAG monster**: upload 20–50 "question–answer" pairs (delivery, returns, opening hours), search with BM25/embeddings, answer with a template. That is 60% of retail questions, closed without an LLM.
- **A "what the bot did this week" report** by email or Telegram: dialogues, add-to-carts, products not found (a direct signal for the assortment).
- **A hosted plan** (Pleiades Cloud) priced per site, not per "resolution". Competitors charge $0.50–$1.00 per conversation/resolution (see §5), while small models give us a cost of kopecks. That is the main price advantage and it must be said out loud: "a fixed N ₽/month, no per-dialogue fee".
- **Privacy as a feature**: data does not go to OpenAI, everything is on your own server. For Russia/CIS (152-FZ) and the EU (GDPR) it is a selling point and belongs in the headline of the README and the landing.

### Recommendations: developers

- **`npx create-pleiades` / `docker run pleiades/allinone`**: one image with the orchestrator and llama-server (no Laya and delta) plus SQLite, configured with one `.env`. The full stack is for advanced users.
- **An SDK for registering tools**: `@shalotts/pleiades-tools` with helpers like `defineTool({ name, schema: z.object(...), execute })` (Zod → JSON Schema), and a `pleiades dev` test bench that shows how the planner sees the catalog (each tool's intent, classification, a dry run of the plan).
- **OpenAPI → tools**: import the shop backend's OpenAPI spec into server-side MCP tools, i.e. without a browser.
- **A public orchestrator API** (`/v1/messages`) with documentation and per-channel keys instead of one `HARNESS_API_KEY`, so developers can build their own transports (WhatsApp, VK, Avito).
- **Example sites in different domains** in `examples/`: electronics, clothing, service booking (a barbershop), reservations. Both marketing and an extension of the eval sets (CLAUDE.md itself admits the grocery bias).
- **Honest benchmarks** in the README: "task success X% on N scenarios, p50/p95 latency, on such and such hardware" against GPT-5-nano through the same pipeline. This is the main argument for the "GOAP + small models" approach.
- **CI**: today there is only the widget's workflow. The `intlayer-*.yml` workflows watch the `main` branch while the main branch is `master`, so they **never run**. A shared `bun run lint && check-types && test` workflow on PRs is needed, with a badge in the README.

## 4. Modularity and external APIs (when local models are not enough)

### Current state

- All three roles (text / decision / function-call) are already behind ports in `@repo/core`: `Agent`, `DecisionAgent`, `FunctionCallAgent`. A good base.
- `Agent` and `FunctionCallAgent` use the OpenAI-compatible protocol, so any cloud provider plugs in by changing `LLM_BASE_URL`/`FUNCTION_CALL_BASE_URL`. But the provider choice is global for the whole instance, with no fallback and no per-channel policy.
- `DecisionAgent` (Laya) is gamma-decision's proprietary HTTP protocol, with no external equivalent.

### Target architecture: a model router

```
                        ┌──────────── ModelRouter ────────────┐
  GOAP action ─ role ─► │ policy(channel, role, attempt, ctx) │
  (text|decision|      │   ├─ primary:  local (llama-server)  │
   function-call|      │   ├─ fallback: cloud (OpenRouter /   │
   translate)          │   │            Gemini / OpenAI /     │
                        │   │            YandexGPT / GigaChat) │
                        │   └─ budget / circuit breaker       │
                        └──────────────────────────────────────┘
```

1. **A provider registry** (`packages/core/src/providers/`): an interface `ModelProvider { id, kind: "openai-compatible" | "anthropic" | "google" | "laya", capabilities: {jsonSchema, tools, streaming}, pricing? }`. Adapters through the Vercel AI SDK (`@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, `@ai-sdk/openai-compatible`), which is already a dependency.
2. **A per-channel policy** in the DB (`channel_model_policies`): for each role, `primary`, `fallbacks[]`, `escalateOn` (`timeout`, `invalid_json`, `validation_failed`, `low_confidence`, `no_plan`), a monthly budget in $. Provider keys are stored encrypted (AES-GCM, the key from ENV); the admin panel shows only a mask.
3. **Escalation points already in the code**:
   - delta: after 2 failed correction attempts (`repair → validate → correction`), hand the call to a cloud model **before** the mechanical `buildArguments` fallback;
   - Laya: on `confidence < threshold`, or the `chat` class for a long message, a cloud classification through `generateObject` with an enum schema;
   - beta-text: if the reply is empty, cut off or looping (a repetition detector), retry on a cloud model;
   - the planner: `no_plan` after all replans → a cloud "advisor planner" that picks a tool from the catalog by name (the result is validated by GOAP preconditions; the planner stays in charge).
4. **Decision through an LLM**: a `DecisionAgent` adapter over any model with a JSON schema (`{choice: enum}`), so gamma-decision becomes optional. That gives a "light install" mode without 1.5 GiB for Laya.
5. **Circuit breaker and budget**: on 5xx or timeouts a provider is switched off for N seconds. When the channel's budget runs out, local models only. Cost accounting goes into the existing `llm_calls` (the `provider`/`model` fields exist; `costUsd` needs adding).
6. **Observability**: on the request page (`/flow`) the admin panel shows which model really answered and why there was an escalation. That sells the hybrid: "92% of requests local, 8% cloud, $0.40 a month".
7. **The translator behind a port too**: `Translator` with `ctranslate2-ffi` (today), `cloud` (DeepL/Yandex/LLM) and `none` implementations. Plus languages beyond ru→en (kk, uk, de…): Opus-MT exists for many pairs, and the model can be chosen by `channel.languages`.

Recommended cheap fallbacks (prices from third-party aggregators; check with the vendors): GPT-5 nano ≈ $0.05/$0.40 per 1M tokens, Gemini 2.5 Flash-Lite ≈ $0.10/$0.40, Gemini 2.0 Flash-Lite ≈ $0.07/$0.30. At 300–500 tokens per escalation, a thousand escalations cost less than $0.30. For Russia, YandexGPT Lite and GigaChat Lite are also worth it (data localisation). Through OpenRouter one key gives all models and a built-in fallback.

### Service modularity

- **Compose profiles**: `minimal` (orchestrator + beta-text), `standard` (+ delta), `full` (+ gamma, translate). Today `tunnel` with `:?` breaks startup without Cloudflare; move it into a `public` profile.
- **A plugin API for GOAP actions**: today new actions are added by editing `goap.service.ts`. A `registerActionPack({ name, actions, intents?, cues? })` is needed: domain packs (shop, service booking, support) as separate workspace packages. This directly serves the rule "domain meaning lives in intent-taxonomy/message-cues/tool-cues": move those files into `@repo/pack-retail`.
- **Server-side MCP tools per channel** (not only the browser's WebMCP): `channels.mcp_servers` with a URL and a token. Then a site without a JS integration (or a CRM) connects from the server. The `connectHttpMcpClient` + `createMcpToolSource` code exists and goes to waste (see Kali).

### Positioning

The free niche: **"a self-hosted AI salesperson that really presses buttons on the site, runs on a cheap server without a GPU and charges nothing per dialogue"**. The closest direct competitor is Persona.js (the same WebMCP approach): it has no backend of its own and no small models, but its frontend is ahead of ours (approval gates). DOM agents (page-agent) need no site markup, but need a big model. Our GOAP + structured tools is the right bet for 1–2B models, and it must be proven with a benchmark.

Risks:
- WebMCP is only in a Chrome origin trial (M149–M156). The API already moved from `navigator.modelContext` to `document.modelContext`, and `provideContext` was removed from the draft. Betting on the polyfill is justified, but it needs protection (§1) and an eye on the spec.
- Persona/CopilotKit may add a light backend of their own. Our moat is the cost of ownership and offline operation; they must be measured and shown.

### What to take from competitors

- From Persona: **approval gates** for changing actions, and showing "the bot wants to add X to the cart — confirm?".
- From page-agent: **a fallback without markup**: if a site has no WebMCP tools, generate basic ones (`search`, `navigate`) from `<form>` elements and links. The polyfill already partly does this (`form[toolname]`).
- From Tidio/Gorgias: **one-click install** on e-commerce platforms and metrics in money.
- From Typebot: **visual scenarios** for the owner (greeting, quick buttons "Delivery", "Returns", "Operator").
- From Chatwoot: **an operator inbox**, or integration with it (Chatwoot has an Agent Bot API: Pleiades can connect to Chatwoot as a bot and get operators "for free").

## 7. Design after the discussion (2026-10-13)

### 7.1 Landing, playground, docs

The landing and playground already exist in `shalotts/src/routes/[[locale=locale]]/landing/pleiades-orchestra`. The plan is `apps/docs` on SveltePress and moving them there. Notes:
- Svelte 5 is already used in `apps/admin`, so shared components (the embed snippet, the widget attribute table) can move into a workspace package instead of two copies. The admin panel's FAQ (`faq.content.ts`) is also worth reusing as a source for the docs.
- The playground is the main sales tool. It must have **different domains** (a shop, service booking, electronics), not only Basketful. It is both a demo and an eval set (see §7.2).
- The playground's public endpoint (commit `853c963`) goes through the same limiter as ordinary widgets. A demo needs separate quotas, otherwise one "Hacker News" tab will bring the model down.
- The README needs links to the landing, playground and docs, plus a GIF: "said → the bot found → put it in the cart".

### 7.2 Why the widget does not understand other demos' tools

A tool's type is decided in two steps today: `tool-cues.ts` (by **name**) and Laya (the question "Which online-shop action does this tool…"). On someone else's site the names differ (`addItem`, `cart.put`, `bookSlot`), and Laya's answer to an "online shop" question for a non-shop is noise. Then delta gets a grocery prompt. The error accumulates at every layer.

Proposal: **a big model at catalog "compile" time, small models at run time.**

1. The catalog is already hashed (`hashTools`) and saved in `mcp_catalogs`. When a **new** hash appears, a strong model analyses the catalog once (a cloud model on the channel's key, or the local Qwen3-1.7B as a fallback). For each tool the model returns: the intent from the taxonomy, the parameter roles (`query`, `productRef`, `quantity`, `filter:*`), whether the tool supports an **array of items**, side effects (read-only / destructive), and 3–5 example calls "request → arguments" for this site.
2. The result is stored as `catalog_profiles` (by hash) with a `pending/approved` status, like `intent_examples` today. The admin panel has a "Site tools" screen: a table of intents, editing, "run an example". Analysing one catalog is one call of ≈1–3k tokens, i.e. **a fraction of a cent**, once in the catalog's life. This is the best place for an external API: the cloud is needed only when the site changes, and at run time everything stays local.
3. Signals from the **schema**, not only the name, without a model: `properties` with `query|q|search|term` → search; `product_id|sku|productId` + `quantity` → add; `items: array<{…quantity}>` → batch-add. This goes into `tool-cues.ts` and works before the analysis.
4. Delta gets **this site's examples** from `catalog_profiles` instead of hardcoded grocery examples. Few-shot for a specific schema gives a 1.7B model more than any general rules. The general system prompt stays domain-neutral.
5. Eval: every new demo site in the playground is a set of `benchmark tools` cases. The metric "exact argument match" per domain, not only groceries.

### 7.3 "I want this, this and that": why delta puts everything into `query`

This is a **structural** problem, not only a prompt one. `WorldState` is a flat bag of scalar facts: it has one `query`, one `product`, one `quantity`. Regressive GOAP builds a plan for **one** goal and cannot loop. Even a perfect delta cannot express "three searches and three adds": the state has no room for a list. Delta honestly does the only thing it can: glues everything into one `query`.

Proposal: a thin **HTN layer over GOAP** (tasks → subtasks), keeping GOAP as the planner of one item:

```
message ─► list parsing ─► [ {query:"milk", qty:2}, {query:"bread"}, {query:"cheese", note:"hard"} ]
                                   │
           ┌───────────────────────┼───────────────────────┐
           ▼                       ▼                       ▼
   GOAP(item 1): search→add   GOAP(item 2)            GOAP(item 3)
           └─────────── outcome: added 2/3, "hard cheese: not found" ──► template reply
```

1. **List parsing** (`parseShoppingList`) is a separate action **before** delta. Rules first: separators `,`/`;`/«и»/«а также»/"and"/a line break, numbers and units. The rules cover most cases. If the rules are not sure, delta with a **separate** schema `{items:[{query, quantity?, note?}]}` (`response_format: json_schema`; 1.7B copes with such a schema because the task is narrow). The result is a `taskList` fact (a JSON string) and `taskCursor`.
2. **A task executor** in `run-stream`: for each item, `runPlan` with item-scoped facts (`query`, `quantity`) and the shared `SESSION_FACTS`. GOAP and checkpoints stay as they are. A pause on a browser tool (`WAITING`) saves `taskList` + `taskCursor` into the checkpoint, and `resumeReply` continues from the current item.
3. **Batch optimisation**: if the add tool's entry in `catalog_profiles` takes an array of items, then after all searches there is **one** add call (fewer browser round trips).
4. **Partial success** is a normal outcome. A template reply: "Added: milk ×2, bread. Not found: hard cheese — see [similar]". beta-text is not needed here.
5. Tests first: `parseShoppingList` in ru/en/kk, different domains ("a T-shirt in M and two pairs of socks", "an HDMI cable and an adapter").

### 7.4 Non-obvious scenarios: "I want to cook lasagne"

A 1B model must not **compose** a recipe: it must **fetch** a ready structured list. To keep groceries out of the core (the "not one shop" rule), this generalises to **bundles**: a recipe for groceries, an outfit for clothing, a PC build for electronics, a repair kit. A knowledge source layer behind one port `KnowledgeSource.findBundle(goal) → {items[], source, confidence}`, in order:

1. **The site's tool**, if there is one (`get_recipe`, `get_bundle`, found by the catalog analysis of §7.2).
2. **The channel's bundles** in the DB: a `bundles` table (`channel_id`, `title`, `items` JSON, `embedding`). The admin uploads them or confirms generated ones.
3. **A shared base** (optional, a per-domain pack): an open recipe dataset with search through sqlite-vec. Check the dataset's license first (some recipe datasets are non-commercial).
4. **A cloud model / web search**: only if 1–3 gave nothing, and only with the channel's external API enabled. The answer is coerced to the `{items:[…]}` schema, saved to `bundles` as `pending`, and after confirmation reused for free. A web fetch with HTML parsing on a 1B model is slow and unreliable, so only through a cloud model or a structured source (schema.org `Recipe` JSON-LD parses without a model).

After that the bundle becomes the `taskList` of §7.3 and runs through the same loop. Before adding to the cart the widget shows the list with checkboxes (an approval gate): the user unticks what they already have.

### 7.5 Caching steps and a vector database

What is worth caching. The planner takes microseconds; caching it is pointless. The expensive calls:

| Step | Cost today | Cache key | What to store |
| --- | --- | --- | --- |
| Intent classification (Laya) | ~hundreds of ms | message embedding | the intent (`IntentMemory`, naive Bayes, already exists) |
| List parsing (§7.3) | 0–1.6 s | message embedding | the `items[]` **template** |
| delta arguments | ~1.6 s per call | `(catalogHash, tool, role slots)` + query embedding | an **argument template** with slots (`{"query": "$item", "max_price": "$price"}`), not literals |
| Catalog classification | Laya × N tools | `hashTools` | `catalog_profiles` (§7.2) |
| Bundle/recipe | cloud | goal embedding | `bundles` (§7.4) |
| Final reply | 1–2 s | — | do not cache: replace with templates where possible |

Principles:
- **Cache templates, not values.** "Find rice under 3 dollars" and "find buckwheat under 5 euros" are one template `{query:$item, max_price:$n}`. A literal cache would almost never hit. **Caveat:** this works only if the slots are already extracted. How to extract them: see §7.5.1.
- **Two levels**: an exact match of the normalised text (like `normalizeIntentText`) → semantic search by embedding with a threshold (cos ≥ 0.92, tune on eval) → the model.
- **The same lifecycle as intents**: `pending` → the admin confirms → used. Auto-confirm only when it matches a successful outcome **and** has no side effects (read-only tools). For `checkout`/`removeFromCart` the cache is forbidden, as now.
- **Invalidation** by `catalogHash`: the site changed its schema, so the template cache of that catalog is not used.
- **Embeddings**: a local multilingual model is needed (the multilingual-e5-small / bge-m3-small class, ~100–500 MB), run with `llama-server --embedding` in the same image as beta/delta. Being multilingual, it will later let us skip translating a message just to search the cache.

**sqlite-vec vs TuringDB**

| | sqlite-vec | TuringDB |
| --- | --- | --- |
| Model | A SQLite extension, the `vec0` virtual table | A separate in-memory graph engine (column store), a Cypher-like language |
| Vector search | Exact kNN (brute force); IVF is reported to be coming, not verified in releases | A built-in kNN index, EUCLID/COSINE metrics, a vector tied to a node/edge id |
| Integration with us | `db.loadExtension()` in the existing `bun:sqlite`: **the same DB, the same transactions, the same backup** (`./data/…`), a `channel_id` filter in one SQL | A separate container and a network call; the SDK is Python only, no JS client or HTTP API visible in the docs |
| Resources | Zero extra processes; 10–100k vectors × 384 dim is a few ms by brute force | A separate process, everything in RAM |
| Strengths | Simplicity, consistency with the rest of the data, works offline | Graphs and multi-hop relations, git-like versions and commits, time travel |
| Risks | Pre-1.0, one main maintainer; on Alpine/musl `vec0.so` must be built by us (plain C with no dependencies: add it to the existing `native` stage of the Dockerfile) | No license stated in the docs (check LICENSE in `turing-db/turingdb`); `apps/memory` used a `nightly` image; one more service on top of six |

#### 7.5.1 Clarification: slot templates do not solve the main problem

The `{query: $item}` template helps **only if it is already known which words are the product**. Pulling the slot out of «ну короче мне бы гречки пару пачек плиз» ("well, like, I'd want a couple packs of buckwheat pls") is the main task, and a cache does not solve it. Moreover, a phrase has two independent axes:

1. **The frame**: what to do: find / buy / compare / unclear. "Find buckwheat" and "I want buckwheat" are one entity but different frames.
2. **The slots**: with what: product, quantity, price, unit, filter.

A cache can learn only **frames**: a channel has dozens of them, repeated by every shopper. Slots are endless, and caching them is pointless. So the cache must be built not as "message → arguments" but as "frame → intent + where to put the slots". The slots are then extracted **by subtraction**: everything that is neither frame nor a typed slot is a product candidate.

**The pipeline (cheap → expensive):**

```
"ну короче мне бы гречки пару пачек плиз"
 1. normalisation: case, ё→е, stemming/lemma for matching (гречки→гречк)
 2. typed slots by regex (reliable, no model):
      {qty}=2 ← "пару", {unit}=pack ← "пачек", {money}, {number}, {percent}
 3. the channel+language frame dictionary: «ну», «короче», «мне бы», «плиз» are known
    non-product words → strike them out
 4. remainder = product candidate(s): «гречки»; the list is split on «, / и / and» (§7.3)
 5. check by an oracle, the SITE's search: 0 results → the candidate is wrong → step 6
 6. a miss at any step → delta/Laya over the whole message (as now)
 7. step 6 succeeded → alignment: delta's query is matched against the message's
    words; words outside the query feed the frame dictionary (candidate → shadow →
    active, no admin — §7.5.3)
```

**Where the frame dictionary comes from.** Not from linguistics but from the statistics of the channel's successful runs. A word that appears in successful requests with **different** products and never lands in `query` is a frame word ("find", "I want", "please", "I'd like"). A word that lands in `query` and finds products is a product word. This generalises the existing hand-written `FILLER_EN`/`FILLER_RU` and `LEADING`/`TRAILING` in `product-request.ts`: the same lists, but learned per channel/language and promoted automatically by statistics (§7.5.3). The initial filling is today's hand-written lists.

**The product dictionary (gazetteer)** is a second, free source: every successful search returns the site's product names. Their lemmas are the channel's "this is definitely a product" dictionary. Then «хочу гречку» ("I want buckwheat") is recognised without a model: «гречк» is in the gazetteer, «хоч» in the frames. Embeddings are needed here for **frames**, not whole messages: the masked `find {item}`, `look for {item}`, `do you have {item}` sit next to each other in the vector space, and a new frame can inherit the intent of the nearest confirmed one.

**Noise and languages.** Stemming (Snowball ru/en/kk, a few KB, no model) is needed only for **matching** against the dictionaries. What goes into `query` is the original form or the gazetteer lemma, i.e. the name the site itself returned. Frames need no English translation: each language has its own dictionaries. That removes part of the Opus-MT errors («купить творог» → "buy some cottage").

**Example: «найди гречку и купи 200 грамм» ("find buckwheat and buy 200 grams"): what goes where.** The whole phrase with concrete values is not stored anywhere: the next shopper will write "find rice and buy a kilo", and a literal record would not fire.

| Part | Where it goes | Record |
| --- | --- | --- |
| «найди», «купи» | frame dictionary | `найд* → search`, `куп* → addToCart` |
| «гречку» | product dictionary (from the site's answer) | `гречк → «Гречка ядрица 900 г»` |
| «200 грамм» | nowhere, a regex every time | `{weight: 200 g}` |
| the whole phrase | template cache, mask only | `найди {item} и купи {weight}` → plan `[search(item), add(item, weight)]` |

This example has two traps the parsing must handle **before** the cache:

1. **One product, not two.** The part «купи 200 грамм» has an empty product slot, so it belongs to the previous part's product. The list splitter (§7.3) does not cut on «и» ("and") blindly: a part with no product inherits the previous part's product, and a part with a new product becomes a new item. `reuseLastProduct` does something similar today, but only between messages, not within one. Test cases: «найди гречку и купи 200 грамм» → 1 item, 2 actions; «найди гречку и купи рис» ("find buckwheat and buy rice") → 2 items.
2. **Weight is not quantity.** If the site sells 900 g packs, `quantity: 200` puts 200 packs in. The slots are typed: `{qty}` (pieces: "2", "a couple", "two"), `{weight}`/`{volume}` (g, kg, ml, l), `{money}`. Code, not the model, turns them into an argument: a product sold by weight (the tool schema takes a weight, or the unit is in the name, "/kg") gets the weight; a packed product is rounded up to whole packs by the weight in its name ("900 г" → 1 pack), and the reply says so ("I added 1 pack of 900 g — it is not sold in smaller amounts"). If the pack weight is not recognised, ask instead of guessing. Today `extractProductRequest` understands only piece counts (digits, number words, dozen); `{weight}` needs adding.

**When the cache is not used, and that is fine**: the remainder is empty or longer than ~4 words, the remainder has unknown words that are in no dictionary, there is a negation or a comparison ("not like last time", "something for pasta"). All of that goes to the model. The cache is there so that frequent simple phrases bypass delta, not to understand language.

#### 7.5.2 "I want buckwheat": find or buy?

Today `message-cues.ts` treats «хочу / надо / мне нужно / I want / I need» as a weak `addToCart` rule, so «хочу гречку» **puts the product in the cart at once**. Which product is decided by `firstListedProductName`: the first one in stock from the search answer, of any pack size and price. This is not a language question but a **product policy**, and it must be explicit:

- Introduce a `want` frame (an underspecified intent) and do not reduce it to `search` or `addToCart` at the classifier level.
- **A channel policy** `wantMeans: search | addToCart | ask`, `search+offer` by default: run the search (no side effects) and show 1–3 cards in the widget with an "Add to cart" button (the approval gate from §1). The click is an explicit confirmation, and no model is needed for it.
- **Learn from behaviour**: "Add to cart" clicks after `хочу {item}` are a confirmation of the frame by the shopper (§7.5.3); no admin is needed for it. A learned frame cannot drop the card and add to the cart directly: running a side effect directly is only for frames from the hand-written list in code, as with `checkout` today.
- The exception, no questions asked: a quantity or an explicit verb ("I want 2 buckwheat", "I want to buy buckwheat") is `addToCart`. A quantity is a strong purchase signal, and it is caught at step 2 of the pipeline.
- The same mechanism is needed for "I need something for pasta" (`want` + an abstract object). That is not a product search but a bundle (§7.4), and such a request goes to the model or to `bundles`.

**sqlite-vec measurement** (2026-10-13; v0.1.9 through `bun:sqlite` 1.4.2; 12 threads; dim 384 (cosine), a file with WAL and `synchronous=NORMAL`, 10 channels through a `partition key`, k=5, random normalised vectors):

| N vectors | Bulk insert (1 transaction) | Single insert, p50 | kNN over the whole table, p50 / p95 | kNN within one channel, p50 | File size |
| --- | --- | --- | --- | --- | --- |
| 1 000 | 71 ms (14k vec/s) | 0.05 ms | 4.5 / 5.0 ms | 0.47 ms | 30 MB |
| 10 000 | 2.0 s (5k vec/s) | 0.57 ms | 7.1 / 7.5 ms | 0.73 ms | 31 MB |
| 100 000 | 20.9 s (4.8k vec/s) | 0.44 ms | 69 / 72 ms | 7.0 ms | 306 MB |

At 100k in memory (`:memory:`): float, insert 1.0 s, kNN 39 ms; binary quantisation `bit[384]` (`vec_quantize_binary`), insert 0.55 s, kNN over 50 candidates **5.9 ms**. "Binary search → float rescoring over 50 candidates" is the standard way to speed search up 6–7× at a small loss of accuracy.

Conclusions:
- Search is an exact scan, so the time grows linearly with N: ~0.7 ms per 1k vectors at 384 dim. A `partition key channel_id` divides the time by the number of channels. For a multi-channel orchestrator that is a free speedup, to be used from day one.
- Our real scale is hundreds to thousands of templates and bundles per channel, i.e. **< 1 ms per search**. That is three orders of magnitude less than one delta call (~1.6 s), so a vector cache pays off from its first hit.
- Writing one row is ~0.5 ms. It can be written synchronously, right in the handler.
- Bulk loading into a file is bound by blob writes (~5k vec/s). Importing a 100k dataset takes ~20 s: do it as a background task, not at startup.
- Disk space: the file grows in chunks of 1024 vectors per partition, so even 1k vectors over 10 channels took 30 MB. At ~3 KB per vector (384×float32), 100k vectors is ~300 MB. `bit[384]` takes 32× less. Keep floats for rescoring only where really needed.
- The embeddings themselves (`llama-server --embedding`, a small model) will cost ~5–30 ms on CPU: that is the main price of the cache, not sqlite-vec.

**Recommendation: sqlite-vec.** Our volumes (hundreds to thousands of templates and bundles per channel) are where brute force in the same SQLite beats any network call. "Bundle → items → products" relations fit ordinary tables fine. TuringDB makes sense only if a real graph task appears: a catalog ontology, multi-hop "compatible with / replaces / part of" relations, recommendations over the purchase graph. For that case, hide the vector store behind a `VectorStore` port in `@repo/core`, so the replacement stays local. `apps/memory` (a Dockerfile with turingdb nightly) is not used and not wired into compose; by the CLAUDE.md rules it should be deleted.

#### 7.5.3 Frame and product dictionaries: storage and learning without an admin

Added 2026-10-14.

**Storage: SQLite is the source of truth, a `Map` is the hot path.** Words need no vectors: step 3 of the pipeline (§7.5.1) is an exact stem match (`хоч`, `найд`, `плиз`), not semantic closeness.

- A drizzle table `frame_words`: `channel_id, lang, stem, role (frame|product), intent NULL, status, seen_count, distinct_users, distinct_products, query_hits, shadow_agree, shadow_total, updated_at`; unique key `(channel_id, lang, stem)`.
- In memory, a `Map<"channelId:lang", Map<stem, Entry>>` with only `active` entries. Loaded from SQLite on the first access to a channel and dropped for the channel on any promotion or demotion. There is one process, so that is enough.
- The gazetteer works the same way, but is also dropped by `catalogHash`.
- sqlite-vec is needed one level up, for **frame masks** (`find {item}`, `do you have {item}`): a new mask inherits the intent of the nearest confirmed one. That is `vec0` in the same DB, kNN per channel < 1 ms (measured above), no in-memory cache needed.

**Principle: protection lives in execution, not in learning.** Then a dictionary error lowers the parsing quality but breaks nothing:

- **A product word got into the frames** → the remainder is empty or wrong → the site's search (step 5) gives 0 or other products → delta (step 6) → the alignment sees the word in `query` → the entry is **demoted automatically**. The error fixes itself.
- **A frame word is not recognised** → it stays in the remainder → a cache miss, the message goes to delta. No harm.
- **A learned frame with a side effect** (`addToCart`, `removeFromCart`, `checkout`) is never run at once: the shopper sees a card with a button (the approval gate from §1). A click confirms the frame; a refusal or a rephrase refutes it. Only frames from the hand-written list in `message-cues.ts` run at once.

**An entry's lifecycle**: `candidate → shadow → active → demoted`:

| Status | How it gets there | Affects parsing |
| --- | --- | --- |
| `candidate` | a word outside `query` in a successful run | no, only counters in SQLite |
| `shadow` | the promotion thresholds are passed | no: the dictionary guesses, delta decides, the results are compared |
| `active` | shadow agreement ≥ 95% over ≥ 20 comparisons | yes, it goes into the `Map` and skips delta |
| `demoted` | the word is in the `query` of a successful run, or striking it out gave 0 results where products were found without it | no; promotion again needs doubled thresholds so the entry does not flip back and forth |

**Promotion thresholds** (tune on eval):
- ≥ 10 successful runs and ≥ 5 **different** products next to it, otherwise «ядрица» ("kernel", as in buckwheat kernel) becomes a frame because it always stands next to buckwheat;
- 0 hits in `query`;
- the lower Wilson bound of the "outside query" share ≥ 0.9, protection against small samples.

**What counts as success.** Without a reliable outcome signal the dictionary learns from garbage. Success: the search returned > 0 products **and** the shopper did not rephrase the request or write "not that" / "no" within ~60 s. A strong signal is a card click or "Add to cart". All of this is already in `plan_runs`/`plan_events`.

**Poisoning protection**: the thresholds count **different `user_id`s** (≥ 3–5), not runs; one user's contribution to the counters is capped per day. Frames with a side effect still go through the card, so the worst outcome of an attack is an extra card.

**The admin's role is to watch, not to decide**: a read-only "learned / demoted" feed, a manual blocklist as an emergency switch, and per-channel metrics "share of messages bypassing delta" and "share of demotions". With a high demotion share the channel's thresholds rise automatically.

**Where the scheme comes from.** Not one paper but a combination of known approaches:
- **Dictionary bootstrapping**: Riloff & Jones (1999) learn a dictionary of context patterns and a dictionary of entities at the same time, each feeding the other; those are our frame dictionary and gazetteer. Snowball (Agichtein & Gravano, 2000) and NELL (Carlson et al., 2010) keep what they find as a candidate until confidence thresholds; hence `candidate → active`.
- The main risk of bootstrapping is **semantic drift**: one wrong entry drags new ones along. Hence the thresholds over different products and the automatic demotion; Curran et al. (2007) limit drift by mutual exclusion of categories, and with us a word cannot be both a frame and a product.
- **Shadow** comes from code rollout practice (shadow mode / dark launch, GitHub's Scientist library): the new logic runs in parallel, the results are compared but not applied.
- Overall this is a **model cascade** (FrugalGPT, Chen et al., 2023): the cheap level is tried first, the expensive one on uncertainty. The cheap level learns from the expensive one's outputs (self-training with a teacher). It is not distillation in the strict sense (Hinton et al., 2015: training on the teacher's soft probabilities).

The names and years are from memory; check them before citing outside the audit.

#### 7.5.4 Next stage: distilling delta into a small model

Tang et al. (2019, arXiv:1903.12136) distil BERT into a one-layer BiLSTM: ~100× fewer parameters, ~15× faster, on paraphrase, NLI and sentiment tasks; for small data, augmentation (from memory: masking, part-of-speech word replacement, n-gram sampling). We already have the same "expensive teacher → cheap student" scheme: the teacher is delta (Qwen3-1.7B) + the site's search as the oracle. A BERT teacher is not needed; the technique is.

**Is BERT overkill?** Not in speed: a BERT-base-class encoder on CPU is tens of ms per short phrase, far cheaper than Qwen 1.7B, and multilingual-e5-small from §7.5 is itself from the BERT family. What is expensive is maintaining a trained model:

| | Frame dictionary (§7.5.3) | Trained student |
| --- | --- | --- |
| How many examples are needed | dozens per channel, learns in operation | thousands, batch training |
| A new site or domain | starts from the hand-written lists and works at once | retraining or hoping it generalises |
| Fixing one error | demote the entry, instantly | a word cannot be "unlearned", only retrained |
| Explainability | you see which word struck out what | none |
| Infrastructure | a SQLite table + a `Map` | training, model versions, eval, runtime |

The second difference: the paper solves sentence-level tasks, while we also need **sequence labelling** (BIO: where in the phrase the product is), not only a phrase classifier.

**Order:**
1. **Now**: regexes + frame dictionary + gazetteer (§7.5.1, §7.5.3).
2. **When the dictionary hits its hit-rate ceiling**: e5-small embeddings + kNN over confirmed frame masks (sqlite-vec). The model is already in the plan, no training needed.
3. **When the log has accumulated**: distillation: **one shared multilingual** model (not one per channel), fine-tuned on delta's outputs across all channels: intent + BIO product labelling. The log of successful runs that feeds the dictionary is the training set. The student is a fine-tuned small encoder (the same e5-small), not a BiLSTM from scratch: simpler and usually more accurate. It switches on as one more cascade level before delta, in the same shadow mode as the dictionary.

### 7.6 Agent profiles and per-channel settings

> **Dropped (2026-10-20):** models are instance-wide — staff pick them on the Agents/Models tabs (`providers.toml`), channels never override them. The persona part was built separately (PO-6).

One orchestrator, many channels, so everything that affects behaviour must resolve **per channel, inheriting from a default**:

```
agent_profiles            -- "our" defaults + user-made ones
  id, role (text|decision|function-call|embed|translate|catalog-analyzer),
  provider (local|openai-compatible|anthropic|google|…), base_url, model,
  api_key_enc (AES-GCM, key from ENV), params JSON (temperature, max_tokens…),
  system_prompt, is_builtin

channel_agent_settings    -- the channel's overrides
  channel_id, role, profile_id, fallback_profile_ids JSON,
  escalate_on JSON, monthly_budget_usd

channel_persona           -- what the shopper sees
  channel_id, bot_name, tone, default_lang, greeting,
  forbidden_topics, handoff_contact

reply_templates           -- template replies by event and language
  channel_id NULL(=default), event (added|partial|not_found|checkout|error), lang, text
```

- The admin panel's "Agents" section shows the built-in profiles (beta/gamma/delta) as **read-only**, with a "Copy and edit" button. That way the default can always be updated with a release, and the user's edits are not overwritten.
- The system prompt is assembled from parts: `core rules` (ours, immutable: JSON format, no inventing) + the channel's `persona` + `domain examples` (from `catalog_profiles`, §7.2). The user edits only the last two, so they cannot break the contract with the parsers.
- **Prompt versions**: every edit is a new version, a "run the channel's eval" button before activation, one-click rollback. `llm_calls` keeps the prompt version, and `/flow` shows which version answered.
- `replyFromTemplate` already exists; move it to `reply_templates` so the texts come from the DB, not from code.
- `ChannelDirectory` already caches channels in memory with `invalidate()`. Profiles and personas go there too, with no DB queries per message.

### 7.7 Elysia 2 beta: move now?

**No, do not move now. Make a trial branch and return to the question after the stable release.**

Arguments "for" in the future: a 50%+ smaller bundle, 30%+ faster startup, less memory, AOT compilation at build time. That fits `bun build --compile` binaries and "runs on a cheap VPS".

Why not now:
- The authors themselves call it a beta, "not a stable release", with possible oddities after the rewrite, and keep the beta status until the plugin ecosystem moves to v2.
- We depend on `@elysiajs/openapi` (in `elysia-kit` and the root catalog) and `@elysiajs/eden` (the admin panel's typed client). The 2.x plugins are published under the new `@elysia` scope, and the announcement does not mention OpenAPI's fate. Eden, per the announcement, understands the new error format, but `apps/admin` relies on exact `Treaty` type inference. We already had a lesson about two copies of `elysia` and a broken `Treaty`.
- The breaking changes hit our key places: the `onRequest` → `request` hooks (all the auth, per the lesson "auth in onRequest"); the route argument order (the schema before the handler, every route); WebSocket became opt-in (`.use(websocket())`) and `.ws()` changed its signature (the live hub and system stream in admin-api); errors moved to RFC 9457 `problem+json`, and a 500 in production hides the message. The widget relies on **empty bodies** with 401/403/404/429, admin-api on its own error codes; both need rechecking. Plus `resolve` is removed and `guard` overrides by default instead of adding. Another question: is better-auth compatible (it is wrapped by hand, which makes it easier).
- The codemod covers about 95%, but the remaining 5% are exactly the auth hooks and WebSocket, i.e. security.

Trial plan (1 day, no merge): a `spike/elysia-2` branch → `bunx @elysia/codemod@latest` over `packages/elysia-kit`, `apps/alpha-orchestrator`, `apps/gamma-decision` (not admin-api: it has WS and Eden) → `bun run test` (especially `auth*.test.ts`, `widget.test.ts`) → measure RSS, startup time and binary size against 1.4. If the gain is noticeable and `@elysia/openapi` is ready, move after the stable 2.0, starting with the orchestrator and ending with admin-api and admin.
